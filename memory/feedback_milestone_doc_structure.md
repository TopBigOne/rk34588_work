2026-11-08 用户看了我写的 `day4_rga/doc/3_理解M3的需求和代码.md`，说"写的不好；你不要和 M1、M2 扯在一起；直白地说 M3 干了什么，输入是什么，输出是什么，用到了哪些 MPP、V4L2 或 Linux 技术点；实际业务场景有哪些"。

我第一版的问题：通篇"和 M2 比""M2 篇第 X 节"，读者得先读懂 M1、M2 才能看懂 M3；还塞了 review 坑、问答、下一步，重点被冲淡。

**Why:** 用户把每篇文档当成独立的学习材料和以后的查阅资料，要一眼看清这个里程碑本身是什么、学到了哪些技术点、在实际产品里有什么用。

**How to apply:**
- "理解 Mx"文档的骨架：① 干了什么（一句话 + 数据流 + 步骤表带行号）② 输入 ③ 输出（含实测）④ 用到的技术点，按 MPP / V4L2 / RGA / Linux 分表，每行"调用 + 行号 + 在这里做什么"，最后一小节写这次的重点 ⑤ 实际业务场景 ⑥ 怎么运行
- 不写"和上一个里程碑比""见 M2 篇"；需要的知识直接在本篇讲清
- review 坑、问答这类内容别塞进去，除非用户要
