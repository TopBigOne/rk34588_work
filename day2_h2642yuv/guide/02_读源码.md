### 和编码对比：解码几乎不用配参数

编码要设宽高、stride、码率、GOP、profile…… 一大堆；**解码只设了一个 `split_parse`**。宽高、profile 这些都写在码流的 SPS 里，解码器自己读。

### ⚠️ 官方文档和代码不一致的地方

## 2. 主循环：`dec_simple()` 62～259 行

### 2.1 读一块码流，填进 packet（75～100 行）

| 行号 | 代码 | 说明 |
|---|---|---|
| 76 | `reader_read(cmd->reader, &slot)` | 从文件读一块（默认 **4KB**，见第 4 节） |
| 81 | `pkt_eos = slot->eos` | 读到文件尾了没有 |
| 83～92 | `if (pkt_eos) ... reader_rewind` | `-n` 帧数没到就**从头再读**（循环解码测速用），到了就标记结束 |
| 94～97 | `mpp_packet_set_data / size / pos / length` | 把这一块数据填进 packet（`data = pos = slot->data`，`size = length = slot->size`） |
| 99～100 | `mpp_packet_set_eos(packet)` | 最后一包带上 EOS 标志 |

### 2.2 送进去（106～114 行）

```c
if (!pkt_done) {
    ret = mpi->decode_put_packet(ctx, packet);
    if (MPP_OK == ret) {
        pkt_done = 1;
        ...
    }
}
```

- 成功：`pkt_done = 1`，这一包送完了。
- **失败**（输入队列满）：什么都不做，`pkt_done` 还是 0。走到 245～255 行：`msleep(1)` 后回到 102 行的 `do`，**再送同一包**。
- 这就是"队列满时等待重试"。248～254 行的注释说：1080p 硬件解一帧大约 2ms，所以等 1ms 足够。

### 2.3 取出所有能取的帧（117～237 行）

```c
do {
    ret = mpi->decode_get_frame(ctx, &frame);
    ...
    if (frame) {
        if (mpp_frame_get_info_change(frame)) { ... }   // ⭐ 137～166
        else { ... 正常图像 ... }                       //    167～206
        frm_eos = mpp_frame_get_eos(frame);             //    207
        mpp_frame_deinit(&frame);                        //    208 ⭐ 每一帧都要释放
        get_frm = 1;
    }
    ...
    if (get_frm) continue;    // 拿到了就接着拿
    break;                    // 拿不到了就回去送下一包
} while (1);
```

| 行号 | 说明 |
|---|---|
| 121～130 | `MPP_ERR_TIMEOUT` 时最多重试 30 次。**默认是非阻塞的**，拿不到图像时返回 `MPP_OK` + `frame == NULL`，不会走到这里（见第 5 节） |
| 137～166 | ⭐ **info change**，见 2.4 |
| 171～172 | `mpp_frame_get_errinfo` / `mpp_frame_get_discard`：这帧有没有错误、是不是该丢弃 |
| 197～198 | `if (fp_output && !err_info) dump_mpp_frame_to_file(...)`：**有错误的帧不写** |
| 207～208 | 记下 EOS，然后 **`mpp_frame_deinit`**：不管是 info change、错误帧还是正常帧，都要释放 |
| 220～223 | EOS 包已经送了、但还没拿到 EOS 帧：`msleep(1)` 继续取（解码器还在处理最后几帧） |
| 225～228 | 拿到 EOS 帧：结束 |

### 2.4 ⭐ info change（137～166 行）—— 今天最重要的一段

```c
if (mpp_frame_get_info_change(frame)) {
    RK_U32 width      = mpp_frame_get_width(frame);       // 1920
    RK_U32 height     = mpp_frame_get_height(frame);      // 1080
    RK_U32 hor_stride = mpp_frame_get_hor_stride(frame);  // 1920
    RK_U32 ver_stride = mpp_frame_get_ver_stride(frame);  // 1088
    RK_U32 buf_size   = mpp_frame_get_buf_size(frame);    // 每块内存要多大

    grp = dec_buf_mgr_setup(data->buf_mgr, buf_size, 24, cmd->buf_mode);   // 149：建内存池，24 块
    mpi->control(ctx, MPP_DEC_SET_EXT_BUF_GROUP, grp);                     // 151：把内存池交给解码器
    mpi->control(ctx, MPP_DEC_SET_INFO_CHANGE_READY, NULL);                // 162：告诉解码器"好了，继续"
}
```

**为什么第一次 `get_frame` 拿到的不是图像**：解码器一开始不知道图像多大，要先解析码流里的 SPS。解析完它就知道"1920×1080，stride 1920×1088，每块内存要 buf_size 字节"，但它**不自己申请内存**，而是吐出一个特殊的 MppFrame（`info_change = 1`，没有图像数据）来通知你：

```
你：put_packet（含 SPS/PPS/第一帧）
解码器：解析 SPS → 发现"我需要内存" → 暂停 → 输出一个 info change 帧
你：get_frame → 拿到 info change → 建内存池 → SET_EXT_BUF_GROUP → SET_INFO_CHANGE_READY
解码器：继续解码 → 输出真正的图像
```

不处理 info change（不调 `SET_INFO_CHANGE_READY`）→ 解码器一直暂停 → 永远拿不到图像，程序卡住。

**"change"** 的意思：码流中途分辨率变了（比如直播切换清晰度），也会再来一次 info change，要重新配置内存池。第一次是"从无到有"的 change。

## 3. 内存池：`dec_buf_mgr_setup()`（mpi_dec_utils.c 817～932 行）

`cmd->buf_mode` 默认是 0 = `MPP_DEC_BUF_HALF_INT`（`mpi_dec_utils.h` 87 行），对应官方文档的 3 种模式：

| 模式 | 代码 | 做法 | 官方文档 |
|---|---|---|---|
| **半内部分配**（默认，我们用这个） | 852～866 | `mpp_buffer_group_get_internal(&grp, ION)` + `mpp_buffer_group_limit_config(grp, size, count)`：建一个内部池，**限制**最多 count 块、每块 size 字节，具体由解码器自己从池里申请 | 模式二 |
| 纯内部分配 | 867～871 | 什么都不建，grp 为 NULL，解码器自己随便申请 | 模式一：简单，但内存用量不受控 |
| 纯外部分配 | 872～ | 自己申请 count 块内存，`mpp_buffer_commit` 一块块提交进外部池 | 模式三：零拷贝显示用，难 |

**要分配多少块**：demo 传的是 **24**（149 行）。官方文档 3.3.2 节："H.264/H.265 这类参考帧较多的协议需要 20+ 内存块能保证一定能解码"。原因：H.264 最多可以有 16 个参考帧，加上正在解码的、已经输出给你还没 deinit 的，就要二十多块。

**`buf_size` 从哪来**：info change 帧的 `mpp_frame_get_buf_size`，解码器按芯片和格式算好的。比 `hor_stride × ver_stride × 3/2` 大，因为还要放额外的信息（官方文档："额外附加信息：hor_stride × ver_stride / 2"）。

> 💡 demo 用的是 `MPP_BUFFER_TYPE_ION`。在我们 5.10 内核的板子上，ION 和 DRM 一样都会被 MPP 换成 DMA-HEAP（见 [DRM缓冲区.md](../../day1_yuv2h264/doc/DRM缓冲区.md) 第 5 节），写哪个都行。

## 4. 读文件：`read_normal_file()`（mpi_dec_utils.c 174～198 行）

```c
read_size = fread(slot->data, 1, buf_size, fp);        // 按固定大小读，不管帧边界
if (read_size != buf_size || feof(fp) || ...) eos = 1; // 读不满 = 到文件尾了
```

- `buf_size` 默认 `DEFAULT_PACKET_SIZE` = **4KB**（37 行），可以用环境变量 `reader_buf_size` 改（`check_file_type` 229 行）。
- 按固定大小读，一块里可能有半帧、也可能有好几帧 —— 所以必须打开 `split_parse`，让 MPP 内部重新切帧。
- 我们自己写的时候读 **64KB** 一块：块越大，`put_packet` 调用次数越少（`aaa.264` 55.7MB，4KB 要送 1.4 万次，64KB 不到 900 次）。

### 内部分帧和外部分帧

| | 外部分帧（默认） | 内部分帧（`split_parse = 1`） |
|---|---|---|
| 每包是什么 | 正好一完整帧，不多不少 | 任意长度，可能半帧、可能多帧 |
| 谁来切帧 | 你自己（比如从 MP4 / RTSP 里取出来的数据本来就是一帧一包） | MPP 内部 |
| 效率 | 高 | 略低（MPP 要扫一遍找起始码） |
| 适合 | 解封装后的数据、RTSP 收到的 RTP 包 | **裸码流文件**（`.h264` / `.h265`）按长度读 |

`aaa.264` 是 Annex-B 裸码流文件，我们按 64KB 读 → **用内部分帧**。两种混用会解码出错。

## 5. 写文件：`dump_mpp_frame_to_file()`（utils/utils.c 62 行起）

`MPP_FMT_YUV420SP`（NV12）分支：

```c
RK_U8 *base_y = base;
RK_U8 *base_c = base + h_stride * v_stride;          // UV 从第 1088 行开始

for (i = 0; i < height; i++, base_y += h_stride)     // Y：1080 行
    fwrite(base_y, 1, width, fp);                     //     每行只写 width 个字节
for (i = 0; i < height / 2; i++, base_c += h_stride) // UV：540 行
    fwrite(base_c, 1, width, fp);
```

和 Day 1 的 `read_nv12_rows` **正好反过来**：Day 1 是从紧密排列的文件读进有 stride 的缓冲区，今天是从有 stride 的缓冲区写成紧密排列的文件。

| | 读的位置 | 写的位置 |
|---|---|---|
| Day 1 读 NV12 | 文件：连续 | 缓冲区：`row * hor_stride` |
| Day 2 写 NV12 | 缓冲区：`row * hor_stride` | 文件：连续 |

写成按 `hor_stride × ver_stride` 整块写 → 每帧多出 8 行，ffplay 按 1920×1080 播放会越播越错位。

## 6. MPP 内部：两个和 Day 1 不一样的默认行为

（`mpp/mpp.cpp`，行号对着当前源码核对过）

### 6.1 默认非阻塞（169～173 行）

```cpp
case MPP_CTX_DEC :
    if (mInputTimeout == MPP_POLL_BUTT)  mInputTimeout  = MPP_POLL_NON_BLOCK;
    if (mOutputTimeout == MPP_POLL_BUTT) mOutputTimeout = MPP_POLL_NON_BLOCK;
```

| 调用 | 非阻塞时的表现 |
|---|---|
| `decode_put_packet` | 输入队列满（默认 4 包）→ 立刻返回 **`MPP_ERR_BUFFER_FULL`**（420 行），packet 不动 |
| `decode_get_frame` | 没有解码好的帧 → 立刻返回 **`MPP_OK`，`*frame == NULL`** |

Day 1 编码时我们设了 `MPP_SET_OUTPUT_TIMEOUT = BLOCK`。解码**不要**这么设：送了一包后不一定立刻有帧输出（比如 info change 之前、或者一包里只有半帧），阻塞取就会卡死。

### 6.2 送进去的数据会被拷贝（433～440 行）

```cpp
if (NULL == mpp_packet_get_buffer(packet)) {
    /* packet copy path */
    mpp_packet_copy_init(&pkt_in, packet);   // 拷一份
    mpp_packet_set_length(packet, 0);        // 原 packet 的 length 清 0
    ...
}
```

我们用 `mpp_packet_init(&pkt, 数据, 长度)` 包出来的 packet 没有 MppBuffer，走拷贝路径。所以 **`put_packet` 成功后，我们的读缓冲区马上就能复用**（读下一块）。这也是官方文档说的"送入成功后 length 被清为 0"。

### 6.3 取帧时自动同步缓存（`Mpp::get_frame` 519 行）

```cpp
buffer = mpp_frame_get_buffer(frm);
if (buffer)
    mpp_buffer_sync_ro_begin(buffer);   // 硬件写完、CPU 要读：先让 CPU 缓存失效
```

Day 1 是 CPU 写、硬件读，要我们自己 `sync_end`；今天是硬件写、CPU 读，MPP 在 `get_frame` 里已经替我们做了，**不用自己调 sync**。

## 7. 带着问题读：自测

先自己回答，再展开看参考答案。

<details>
<summary>1. 为什么第一次 <code>decode_get_frame</code> 拿到的不是图像？</summary>

解码器要先解析 SPS 才知道图像多大、要多少内存。解析完它会暂停，输出一个 `info_change = 1` 的 MppFrame（没有图像数据）通知我们配置内存。我们建好内存池、`SET_EXT_BUF_GROUP`、`SET_INFO_CHANGE_READY` 之后，它才继续解码、输出真正的图像。见第 2.4 节。
</details>

<details>
<summary>2. <code>buf_size</code> 是从哪里来的？要分配多少块缓存？</summary>

`buf_size` 来自 info change 帧的 `mpp_frame_get_buf_size()`，解码器按芯片和格式算好的，比 `hor_stride × ver_stride × 3/2` 大。块数 demo 给的是 24（149 行），官方文档说 H.264/H.265 要 20+ 块，因为参考帧多。见第 3 节。
</details>

<details>
<summary>3. <code>errinfo</code> 和 <code>discard</code> 的帧应该怎么处理？</summary>

`errinfo != 0` 表示解码出错，图像内容有问题；`discard != 0` 表示这帧应该丢弃。demo 的做法是**不写文件，但照样计数、照样 `mpp_frame_deinit`**（197～198、208 行）。不 deinit 的话这块内存一直被占着，池子很快就空了。
</details>

<details>
<summary>4. 内部分帧和外部分帧有什么区别？<code>aaa.264</code> 应该用哪种？</summary>

外部分帧：每包正好一帧，需要自己切；内部分帧（`split_parse = 1`）：任意长度，MPP 自己切。`aaa.264` 是裸码流文件，按固定长度读 → 用内部分帧。见第 4 节。
</details>

<details>
<summary>5. <code>decode_put_packet</code> 返回失败，这包数据怎么办？</summary>

非阻塞模式下输入队列满会返回 `MPP_ERR_BUFFER_FULL`，packet 原样没动。**等 1ms 再送同一包**，不能丢掉、也不能读下一块覆盖它，否则漏帧、画面花。见第 2.2、6.1 节。
</details>

<details>
<summary>6. 文件读完了，怎么知道解码器把最后几帧也吐完了？</summary>

最后一包 `mpp_packet_set_eos()`。送完之后继续 `get_frame`，直到拿到一个 `mpp_frame_get_eos() == 1` 的帧才算结束（220～228 行）。和 Day 1 编码的 inputEos / outputEos 是同一个道理。
</details>

<details>
<summary>7. 解码出来的图像写文件前，要不要像 Day 1 那样调 <code>sync</code>？</summary>

不用。`get_frame` 内部已经调了 `mpp_buffer_sync_ro_begin`（硬件写、CPU 读的方向）。见第 6.3 节。
</details>

## 8. 了解一下：`mpi_dec_mt_test.c`

多线程版本：一个线程只管 `put_packet`，另一个线程只管 `get_frame`。好处是送和取互不等待，吞吐更高；代价是要处理线程同步和退出。今天先用单线程，Day 5 转码器会用到多线程。
