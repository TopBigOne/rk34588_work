## 1. `struct MppVideoDecoder` 为什么只在 .h 里声明一个名字，成员写在 .c 里？

> 11-25 问。起因是上面那条 CLion 警告。

```c
// mpp_video_decoder.h:22 —— 只有名字，没有成员
typedef struct MppVideoDecoder MppVideoDecoder;

// mpp_video_decoder.c:20 —— 完整的成员列表，只有这个 .c 能看到
struct MppVideoDecoder {
    MppCtx decoderCtx;
    MppApi *decoderApi;
    ...
    AVBufferRef *selfRef;
};
```

### 答：这是 C 里常见的“不透明指针”（opaque pointer）写法

“不透明”的意思是：外面的人拿到的只是一个指针，**看不透**它指向的东西里面有什么。

### 前提：编译器处理指针时，不需要知道结构体有哪些成员

```c
struct Secret;          // 只告诉编译器“有个结构体叫 Secret”，没写成员。这叫“不完整类型”
struct Secret *pointer; // ✓ 能编译：64 位系统上任何指针都是 8 字节，存的只是一个地址
pointer->value = 1;     // ✗ 编译报错：编译器不知道 Secret 里有没有 value，也不知道它在第几个字节
sizeof(struct Secret);  // ✗ 编译报错：不知道有哪些成员，就算不出它占多大
```

只知道名字、不知道成员时，**能做的只有拿着指针传来传去**。不透明指针就是靠这一点实现的。

### 最小例子（3 个文件）

```c
// ===== counter.h：给别人 include 的 =====
typedef struct Counter Counter;      // 只有名字，没有成员
Counter *counterCreate(void);        // 创建，返回指针
void counterAdd(Counter *counter);   // 通过函数操作
void counterRelease(Counter *counter);

// ===== counter.c：只有这个文件知道成员 =====
#include "counter.h"
#include <stdlib.h>
struct Counter {                     // 完整定义，只写在 .c 里
    int value;
};
Counter *counterCreate(void) {
    // calloc：分配并清零。只有这里能算出 sizeof(Counter)，所以“分配内存”只能由 .c 来做
    return calloc(1, sizeof(Counter));
}
void counterAdd(Counter *counter) { counter->value++; }  // 只有 .c 能访问成员
void counterRelease(Counter *counter) { free(counter); }

// ===== main.c：使用者 =====
#include "counter.h"
int main(void) {
    Counter *counter = counterCreate();
    counterAdd(counter);       // ✓ 只能通过函数操作
    // counter->value = 100;   // ✗ 编译报错，main.c 看不到成员
    counterRelease(counter);
}
```

### 为什么不把 `struct MppVideoDecoder` 写进头文件？

可以写，C 语言不禁止，编译也能过。但在这个模块里写进 .h 有 3 个具体的坏处，按重要程度排：

**1. 外面可以绕过 Create 自己造一个解码器，一释放就出问题**

定义在 .h 里，外面就能算出 `sizeof`，于是可以这样写：

```c
MppVideoDecoder decoder;  // 在栈上直接声明一个，没经过 mppVideoDecoderCreate
```

但这个解码器的生命周期靠引用计数管理：[mpp_video_decoder.c:183](../src/video/mpp_video_decoder.c#L183) 在 Create 里用 `av_buffer_create` 把它包起来，引用计数降到 0 时，FFmpeg 调 `destroyMppVideoDecoder` 释放它的内存。上面这种写法得到的解码器，`selfRef` 是空的，引用计数根本没建起来，后面的流程都走不通。

定义藏在 .c 里，外面算不出 `sizeof`，上面那行会**编译报错**。外面只能调用 `mppVideoDecoderCreate`，引用计数就一定会建好。

**2. MPP 的头文件会传染到十几个文件**

成员用到了 `MppCtx`、`MppApi`、`MppDecCfg`、`MppBufferGroup`（定义在 `rockchip/rk_mpi.h`），还有 `AVBSFContext`（定义在 `libavcodec/bsf.h`）。现在这两个头文件**只有** `mpp_video_decoder.c` 自己 include。

结构体搬进 .h 的话，.h 就得 include `rk_mpi.h`，依赖会一层层传出去：

```
mpp_video_decoder.h  →  pipeline/decoder.h  →  player/video_state.h  →  另外 14 个 .c/.h 文件
```

这些文件都会依赖 MPP 的头文件，哪怕它们只处理音频或字幕。（14 个是 11-25 在 `src/` 下 grep `player/video_state.h` 数出来的）

**3. 外面可以随手改内部状态**

`hasPendingEndOfStream`、`hasSentEndOfStream`、`selfRef` 这几个成员是互相牵连的。`decoder.c` 里如果有人写了 `mppDecoder->hasSentEndOfStream = 1;`，编译器不会拦，解码器的状态就乱了。藏在 .c 里，这种写法会直接编译报错，出了问题也只用查这一个文件。

（还有一个小好处：改结构体的成员时，只有 `mpp_video_decoder.c` 需要重新编译。）

### 什么时候应该写在头文件里

判断方法：**调用方需不需要碰它的成员？**

- 需要 → 写在 .h 里。例：配置参数 `EncoderConfig`；FFmpeg 的 `AVPacket`、`AVFrame`（调用方要读 `frame->width`、`frame->pts`）
- 不需要，并且内部有要维护的状态（引用计数、状态标志），或者依赖不想暴露的库 → 写在 .c 里（不透明指针）

`MppVideoDecoder` 属于第二种：调用方只需要“送包、取帧、清空、释放”这 4 个动作，内部状态不该让外面碰。

## 2. 项目里为什么会用到 `AVBSFContext`？

> 11-25 问。

```c
// mpp_video_decoder.c:24
AVBSFContext *annexbFilterCtx; ///< mp4toannexb 码流过滤器：avcC 格式（4 字节长度开头）→ Annex B（起始码开头）
```

### 答：它是 FFmpeg 的码流过滤器，这里用来把 mp4 里的包转成 MPP 认识的格式

**字面意思**：`AVBSFContext` 是 FFmpeg 的**码流过滤器（bitstream filter，BSF）实例**。码流过滤器只改压缩数据的**封装格式**，不解码，也不碰画面内容。

**在这里的作用**：把从 mp4 里读出来的 H.264/H.265 包，从 **avcC 格式**转成 **Annex B 格式**，再交给 MPP。

### 为什么要转：同样的 H.264，有两种装法

| | avcC（mp4、mkv 里的样子） | Annex B（裸 .h264、.ts 里的样子） |
|---|---|---|
| 每个 NAL 前面放什么 | 4 字节的**长度** | 起始码 **`00 00 00 01`** |
| SPS/PPS 放在哪 | 不在包里，单独存在流参数的 `extradata` 里 | 直接放在码流里，每个关键帧前面都有 |

用字节示意一个关键帧包（数值是示意，不是实测）：

```
avcC:    [00 00 12 34][IDR 切片数据 ...]                ← 长度 0x1234，没有 SPS/PPS
Annex B: [00 00 00 01][SPS][00 00 00 01][PPS][00 00 00 01][IDR 切片数据 ...]
```

MPP 解码器的标准输入是 Annex B，`mpi_dec_test` 喂进去的就是裸 .h264 文件。如果把 mp4 里的包原样送进去，MPP 找不到起始码，也拿不到 SPS/PPS，就解不出画面。

FFmpeg 自带的软解码器（原版 ffplay 用的就是它）认识 avcC，会自己去 `extradata` 里读 SPS/PPS，所以原版 ffplay 不需要这一步。换成 MPP 硬解以后，格式转换就得我们自己做，这就是这个项目里多出 `AVBSFContext` 的原因。

### 数据流

```
mp4 文件 → av_read_frame（avcC 包）→ AVBSFContext: h264_mp4toannexb（Annex B 包）→ MPP decode_put_packet → 解出 NV12 帧
```
