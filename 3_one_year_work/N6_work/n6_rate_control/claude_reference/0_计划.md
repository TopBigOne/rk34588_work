## 1. 做什么、为什么做

**一句话**：同一段画面，用 MPP 的 4 种码控（CBR / VBR / AVBR / FIXQP）、不同码率、不同 GOP、不同 QP、普通 GOP 和 smart GOP 分别编码，再用 x264 软编在相同码率下对比，最后写成一份**码控实验报告**，给 4 路 1080p 的 NVR 推荐一组编码参数，并算出每路每天占多少硬盘。

**为什么做**

| 依据 | 内容 |
|---|---|
| JD 1 第 2 条 | “视频编码及码控策略优化，平衡画质、码率、带宽与存储空间”（README 第 5 节） |
| J03 / J04 / J16 | “码控、GOP、编码参数”3 份；J03 原文“帧类型、量化参数、码率控制、参考帧管理”，加分项 x264/x265（JD分析.md 第 2 节表格、README N6 小节） |
| 一深多浅 | 编码能力：MPP 硬编是“深”（Day 1～6 手写过），x264（FFmpeg libavcodec）是“浅”，比同码率画质和 CPU（README 第 2 节原则 6） |
| 给谁用 | 报告的推荐参数回填到 N5 `n5_mini_nvr` 的录像码流配置、N11/N12 推流的编码参数；作品整理时放进 GitHub README（README“作品整理”一节） |

> 这是 JD 直接要求的对比实验，是“不主动做 A/B 对比”的例外（README N6 小节、`memory/feedback_multi_tech_per_capability.md`）。

### 4.2 线程模型和所有权

- **单线程**。一个进程只跑一组参数：读一帧 → 编一帧 → 写一帧。编码器用 Day 6 的同步用法（`encode` 送一帧马上取包），所以“每帧耗时”就是 `encode` 调用前后的时间差。批量由脚本循环调用进程，不在程序里开多线程（减少变量，数据好解释）。
- `run_mpp_encode` 拥有：`YuvFileReader`、`MppEncoder`、一块输入 `MppBufferPtr`（从 `MppBufferGroupPtr` 里拿，大小 `horStride × verStride × 3 / 2`）、`StreamFileWriter`、`FrameStatsWriter`。析构顺序：先 writer，再 encoder，再 buffer，最后 group（`mpp_utils.h` 删除器注释里写的顺序）。
- x264 的输入不需要 MppBuffer，`run_x264_encode` 用 `std::vector<uint8_t>` 装一帧 NV12；`AVCodecContext`、`AVFrame`、`AVPacket` 用 `unique_ptr` + 删除器包起来（`avcodec_free_context`、`av_frame_free`、`av_packet_free`）。

### M1 4 种码控模式（第 25 周任务 1、4）

- **干了什么**：4 种码控 × 2 段素材 = 8 次编码，统计设定码率、实际平均码率、每秒最大和最小码率。
- **输入**：M0 两段素材；目标码率统一 4 Mbps，GOP 60，FIXQP 用 QP 28。
- **输出**：8 个 `.h264` + 8 个 CSV；`mac_report.py` 出一张 8 行的码率表和每秒码率曲线。
- **修改文件**：`encoder/mpp_encoder.h/.cpp`。
- **关键接口**（扩展 Day 6 的 `EncoderConfig`；字段名按规范带单位）：
  ```cpp
  struct EncoderConfig {
      int width = 1920; int height = 1080; int horStride = 0; int verStride = 0;
      MppCodingType codingType = MPP_VIDEO_CodingAVC;
      MppEncRcMode rcMode = MPP_ENC_RC_MODE_CBR;
      int targetBps = 4 * 1000 * 1000; // rc:bps_target
      int maxBps = 0;                  // rc:bps_max，0 = 按 mpi_enc_test.c 第 349～360 行的默认比例算
      int minBps = 0;                  // rc:bps_min，同上
      int fps = 30;
      int gopFrameCount = 60;          // rc:gop
      int fixedQp = 28;                // 只在 FIXQP 时用：qp_init/min/max/min_i/max_i 都设成它
      bool isSmartGopEnabled = false;  // M4
      int virtualIntraIntervalFrameCount = 0; // M4，对应 mpi_enc_test 的 vi_len
  };
  struct EncodedPacket { std::vector<uint8_t> data; bool isKeyFrame = false; bool isEos = false; int averageQp = -1; };
  bool MppEncoder::init(const EncoderConfig &requestedConfig);
  bool MppEncoder::encode(MppBuffer frameBuffer, EncodedPacket &encodedPacket, bool isInputEos);
  ```
  rc 部分照 `mpi_enc_test.c` 第 326～400 行的分支写（CBR 窄区间 17/16～15/16，VBR/AVBR 宽区间 17/16～1/16，FIXQP 把 10 个 qp 键都设成同一个值）。每帧平均 QP 从包的 meta 里读 `KEY_ENC_AVERAGE_QP`（`inc/mpp_meta.h` 第 81 行；用法见 `test/mpi_enc_test.c` 第 828 行）。
- **验收**（命令：`scripts/board_run_matrix.sh m1` → `scripts/pull_results.sh m1` → `python3 scripts/mac_report.py m1`）：

  | 预期现象（**推断**，Claude 先上板 probe 确认差距明显，再交给用户） | 说明 |
  |---|---|
  | CBR 两段素材的实际平均码率都在 4 Mbps ±10% 以内，每秒码率波动小 | 静态场景 CBR 会“浪费”码率：QP 被压得很低 |
  | VBR、AVBR 在静态素材上实际码率明显低于 4 Mbps | 能看出“画面简单就省码率” |
  | FIXQP 运动素材的码率是静态素材的好几倍（预期 > 3 倍） | 码率完全跟着画面复杂度走 |
  | CSV 里平均 QP：CBR 静态 QP 低、运动 QP 高 | 用 QP 解释码率为什么稳 |

  如果 probe 时某两组几乎没差别，先换素材（运动更剧烈）或降目标码率到 2 Mbps，不硬做。

- **用户敲 / 复制**：`mpp_encoder.cpp` 的 rc 配置段用户敲；`board_run_matrix.sh`、`mac_report.py` 复制。

### M2 画质：PSNR / SSIM 和拐点（第 25 周任务 5、6）


### M3 GOP 和存储（第 26 周任务 1～3）

- **干了什么**：同一码控（CBR 4 Mbps）下 GOP 30 / 60 / 120 各编一次，比码率和 seek 代价；按实测码率换算存储量。
- **输入**：静态、运动素材各**循环 3 遍**（`YuvFileReader` 的 `requestedLoopCount = 3`，900 帧 = 30 秒）。10 秒素材里 GOP 120 只有 3 个 I 帧，太少，看不出规律。循环点会有一次画面跳变，静态素材几乎看不出，运动素材在报告里注明。
- **输出**：码率表、seek 表、存储量表。
- **新增文件**：`scripts/mac_seek_test.sh`：裸流先 `ffmpeg -r 30 -i x.h264 -c copy x.mp4` 套成 MP4，再 `ffmpeg -ss 15 -i x.mp4 -frames:v 1 -f null -` 计时（跑 5 次取平均）；同时用 `ffprobe -show_frames -select_streams v -show_entries frame=key_frame` 算出“从前一个 I 帧到目标帧要解几帧”。
- **验收**：

  | 表 | 内容 |
  |---|---|
  | 码率表 | GOP 30/60/120 的实际码率；**推断**：GOP 越长码率越低，静态素材差得更明显（I 帧占比大） |
  | seek 表 | 要解的帧数（确定的数字，最多 29 / 59 / 119）+ Mac 上实测耗时。帧数是主要指标，耗时只作参考（Mac 解 1080p 很快，耗时差可能只有几十 ms） |
  | 存储量表 | 每路每天 = 平均码率 × 86400 ÷ 8。例：4 Mbps → 43.2 GB/天；4 路 30 天 → 5184 GB ≈ 5.2 TB |

- **学完能回答**：第 26 周问题 1、2（GOP 从 30 到 120 码率怎么变、拖动快慢；4 路 30 天要多大硬盘）。

### M5 x264 软编 vs MPP 硬编 + 报告（第 27 周）

- **干了什么**：同一份 NV12，用 libavcodec 的 libx264 编码；和 MPP 在相同码率下比画质、CPU、每帧耗时；x264 试 `ultrafast`、`veryfast`、`medium` 3 个 preset。最后写报告。

- **输出**：对比表；`3_one_year_work/N6_work/n6_rate_control/doc/码控实验报告.md`（报告放用户工程的 `doc/`，周计划第 27 周任务 4 写的路径）。
- **新增文件**：`encoder/x264_encoder.h/.cpp`、`app/run_x264_encode.h/.cpp`、`common/process_cpu_meter.h/.cpp`。
- **关键接口**：
  ```cpp
  struct X264EncoderConfig { int width = 1920; int height = 1080; int fps = 30; int targetBps = 4 * 1000 * 1000;
                             int gopFrameCount = 60; const char *presetName = "veryfast"; };
  class X264Encoder {
      bool init(const X264EncoderConfig &requestedConfig);              // avcodec_find_encoder_by_name("libx264") → 设参数 → avcodec_open2
  ```

  | 编码器 | 码率 | 实际码率 | PSNR / SSIM | 进程 CPU 占用（CPU 秒 ÷ 墙钟秒，8 核满载 = 800%） | 每帧耗时 | 能否实时 30fps |
  |---|---|---|---|---|---|---|
  | MPP | 2、4 Mbps | | | | | |

  **推断**的差距（probe 后改成实测）：MPP 的 CPU 占用很低（几乎只花在读文件和拷贝上），x264 要占几个核；medium 在 1080p 上可能达不到 30fps，这正是“NVR 为什么用硬编”的答案。同码率 PSNR 谁高不预设，以实测为准。
