## 1. 做什么、为什么

**一句话**：输入“通道 + 时间点”，从 N3 的 SQLite 索引里找到录像文件，seek 到目标时间之前最近的 IDR 开始解码，显示目标时间的画面；一个文件播完自动接下一个；支持 2×/4×（加快送显）和 8× 以上（只解 I 帧）；Qt 界面上有时间轴、播放/暂停、拖动。

**为什么做**

| 对应 JD | 说明 |
|---|---|
| J01：“录像存储、回放、预览……” | `2_nvr_work/JD分析.md` 第 3 节 J01 摘要，已核对 |
| JD 1 “延迟、卡顿、音画不同步” | README 第 5 节表格把 N4 列在这一行，已核对 |
| FFmpeg（9 份）、编解码（14 份） | 拆封装 + seek 用 libavformat，解码用 MPP |

**给后面谁用**：N4 在全年顺序里排第 3 段（README 第 3 节“做的顺序”，已核对），后面没有阶段依赖它；它是 mini NVR 作品“录像 → 回放”闭环的最后一块（作品整理 v2，第 44 周）。

### 4.2 线程模型和所有权

| 线程 | 干什么 | 在哪里等 |
|---|---|---|
| UI 线程（Qt 主线程） | 按钮、时间轴、`VideoWidget::paintEvent` | 事件循环 |
| 回放线程 | `SegmentReader` 读包 → `AnnexbConverter` → `MppVideoDecoder` → RGA 转 RGBX → 按 `PlaybackClock` 决定送显 / 丢弃 → 回调 | 画面早了睡到该显示的时刻；暂停时等条件变量 |

- 只有视频，没有音频（N3 不录音频，第 39 周“本周不学”，已核对），所以 Day 8 的解封装线程和视频线程合并成一个，不要包队列。节奏由 `PlaybackClock`（系统单调时钟 × 倍速）定，不是声卡。
- **控制命令**（seek、暂停、改倍速）由 UI 线程写进 `PlaybackEngine` 的一个加锁的“请求”结构，回放线程每处理一帧前检查一次（照 Day 8 `pipeline/playback_state.h` 的 seek 请求 + serial）。
- **所有权**：`PlaybackWindow` 拥有 `PlaybackController`；`PlaybackController` 拥有 `RecordIndex`、`PlaybackEngine`、`std::thread`；`PlaybackEngine` 拥有 `SegmentReader`（里面是当前段的 `Mp4Demuxer`、`AnnexbConverter`）、`MppVideoDecoder`、`PlaybackClock`。窗口关闭时先 `engine.stop()` + `join`，再析构。

## 5. 各里程碑

### M1 按时间定位（第 39 周前半）

- **干了什么**：`n4_playback m1 <通道> <目标时间，本地时间 "2027-08-16 14:05:30">` → 查索引 → 打开文件 → seek 到目标之前最近的 IDR → 解码到目标时间，之前的帧解但不显示 → 把目标帧存成 NV12 → 打印“请求时间、实际帧的墙上时间、差值、seek 耗时”。
- **输入**：N3 的录像和 `record_index.db`。**输出**：日志 + `/userdata/n4_out/seek_<时间>.nv12`。
- **文件**：`timeline/recording_timeline.*`、`playback/segment_reader.*`（只用打开 + seek 的部分）、`app/m1_seek_to_time.*`；复制 `index/`、`demux/`、`video/`、`common/`。
- **关键接口**

```cpp
struct RecordingSegment {          // 时间轴上的一段（来自 RecordingEntry）
    int64_t startTimeMs;           // 段首帧的墙上时间（Unix 毫秒）
    int64_t endTimeMs;
    std::string filePath;
};
struct LocateResult {
    enum class Kind { InSegment, InGap, AfterLastSegment, NoRecording } kind;
    int segmentIndex;              // InSegment / InGap 时：所在段，或空档后面那一段
    int64_t offsetInFileUs;        // InSegment 时：目标时间 − 段的 startTimeMs，换成微秒
};

class RecordingTimeline {
public:
    bool load(const RecordIndex &recordIndex, int channelIndex, int64_t rangeStartMs, int64_t rangeEndMs);
    LocateResult locate(int64_t targetTimeMs) const;
    const std::vector<RecordingSegment> &getSegments() const;
    std::vector<std::pair<int64_t, int64_t>> listGaps() const;    // 空档 [开始, 结束)，毫秒
};

class SegmentReader {
public:
    bool openAt(const RecordingTimeline &timeline, int64_t targetTimeMs);  // 打开段并 seekTo(offset)
    ReadPacketResult readVideoPacket(AvPacketPtr &packetPtr, int64_t &frameTimeMs); // frameTimeMs：墙上时间
};
```

  换算规则（依赖 N3 的约定“文件内 PTS 从 0 开始”）：`frameTimeMs = segment.startTimeMs + pts × time_base × 1000`。
- **验收**
  - 边界单测（`m1 selftest`，在板子上跑，用假的段列表）：目标刚好等于某段 `startTimeMs`、刚好等于 `endTimeMs`（左闭右开，应落到下一段或空档）、在空档里、在第一段之前、在最后一段之后。
  - 随机 10 个时间点：表格“请求时间 / 实际帧时间 / 差值”，**差值都 < 1 帧（33 ms）**，因为是解到目标帧才停；“seek 后第一个 IDR 离目标多远”都 ≤ 2 秒（最长 IDR 间隔）。
  - 画面核对（推断可行：H.264 解码按标准逐位确定，MPP 和 FFmpeg 软解的结果应该一样）：
    ```bash
    adb pull /userdata/n4_out/seek_xxx.nv12 .
    ffmpeg -v error -i <对应文件>.mp4 -ss <offsetInFile 秒> -frames:v 1 -pix_fmt nv12 -f rawvideo ref.nv12
    md5 seek_xxx.nv12 ref.nv12     # 期望一致；不一致先看是不是 stride / 1088 行没裁掉
    ```
  - seek 耗时：同一个时间点，正常关闭的 fMP4 和 `kill -9` 留下的 fMP4 各测 3 次，记表。
- **学完能回答**：第 39 周 1～3 题，外加：为什么 `offsetInFile` 能直接用“目标时间 − 段开始时间”（因为 N3 让每个文件 PTS 从 0 开始）。
- **用户手敲**（如果按 C 方案）：`recording_timeline.cpp`、`segment_reader.cpp` 的 seek 部分。**直接复制**：`index/`、`demux/`、`video/`、`common/`、`m1` 的打印和存文件。

### M2 跨文件连续播放（第 39 周后半）

- **干了什么**：从某个时间点开始一直播（命令行版：不显示，只按 1× 时钟节拍“送显”并计数），读到文件尾就打开下一段；遇到空档按定好的方式处理。
- **空档处理（Claude 草案，用户定）**：跳到下一段的开头，播放时钟也跳过去，日志打印“跳过空档 X 秒”；界面（M4）在时间轴上把空档画成灰色，并显示 2 秒提示。
- **输入 / 输出**：同 M1；日志里每段一行“段文件、帧数、首帧时间、末帧时间”，每次切段一行“上一段末帧 → 下一段首帧，间隔 X ms”。
- **文件**：`segment_reader.*` 补“读完打开下一段”；新建 `playback/playback_clock.*`、`playback/playback_engine.*`（先只有 1×）、`app/m2_play_across_segments.*`。
- **关键接口**

```cpp
class PlaybackClock {
public:
    void start(int64_t startPositionMs);        // 位置用墙上时间轴（Unix 毫秒）
    int64_t getPositionMs() const;              // = 起点 + (单调时钟走过的时间 × 倍速)
    void setRate(double requestedRate);         // 改倍速时先把当前位置记成新起点，位置不跳
    void setPaused(bool shouldPause);
    void jumpTo(int64_t newPositionMs);         // seek、跳空档
};

class PlaybackEngine {
public:
    using PictureCallback = std::function<void(const RgbxPicture &picture, int64_t frameTimeMs)>;
    bool open(const RecordIndex &recordIndex, int channelIndex, PictureCallback requestedPictureCallback);
    void requestSeek(int64_t targetTimeMs);     // 任何线程调用
    void requestRate(double requestedRate);
    void requestPause(bool shouldPause);
    void runPlaybackLoop();                     // 回放线程的函数体
    void stop();
};
```

- **验收**
  - 跨 3 个**连续**的段：切段时“上一段末帧 → 下一段首帧”间隔 = 1 帧（33 ms ± 1 ms），总送显帧数 = 3 个文件 `nb_read_frames` 之和减去起点之前的帧。
  - 跨一个空档：日志打印跳过的秒数，和索引里两段的 `end_time_ms` / `start_time_ms` 之差一致。
- **学完能回答**：第 39 周 4～5 题。
- **用户手敲**：`playback_clock.cpp`、`segment_reader.cpp` 切段那段。**直接复制**：`m2` 的统计打印。

### M3 倍速（第 40 周前半）

- **干了什么**：
  - 2×、4×：时钟走得快，每帧照常解码；屏幕刷新有上限，所以**送显上限**设成 30 fps（`app_config.h`，可调），超出的帧解码但不送显（推断：瓶颈在 RGA 转换 + Qt 画图，不在 MPP 解码；用实测验证）。
  - 8×、16×：只把 IDR 包送进解码器，其他包读出来就扔（N3 只给 IDR 打了 `AV_PKT_FLAG_KEY`）。进出 I 帧模式时 `MppVideoDecoder::reset()`。
- **输入 / 输出**：`m3 <通道> <起点> <倍速>`，跑 60 秒录像，打印“解码帧数、送显帧数、丢弃帧数、每帧解码耗时 平均/最大、读包字节数”。
- **文件**：`playback_engine.*` 加倍速和 I 帧模式；新建 `app/m3_trick_play.*`。
- **关键接口**：沿用 M2；`PlaybackEngine` 内部加 `bool shouldDecodeKeyFramesOnly(double rate) const;`（阈值 8.0 写在 `app_config.h`）。
- **验收**：表格“倍速 / 每帧解码耗时 / 送显帧率 / 丢弃数”，2×、4× 送显帧率稳定在上限附近、不卡；8×、16× 画面一跳一跳，每秒送显的 IDR 数 ≈ 倍速 × 每秒 IDR 数（`aaa.264`：36 个 IDR / 60 秒）；16× 时读包速度 ≈ 16 × 0.97 MB/s ≈ 15.6 MB/s（计算），看 eMMC 跟不跟得上。
- **学完能回答**：第 40 周 1～2 题，外加：只送 IDR 时 MPP 会不会攒着帧不出（试 `MPP_DEC_SET_IMMEDIATE_OUT` 前后的差别，只记现象）。
- **用户手敲**：I 帧模式的取舍逻辑、送显 / 丢弃判断。**直接复制**：耗时统计。

## 6. 风险和还没验证的推断

| # | 风险 / 推断 | 怎么处理 |

| 1 | `kill -9` 留下的 fMP4 没有 `mfra`，libavformat 4.4 seek 可能要从头扫 `moof`，可能很慢（推断） | M1 实测；慢的话打开文件时先顺序扫一遍建关键帧表（记“以后再挖”），或者让 N3 启动修复时重写这个文件（要和用户商量，改动 N3） |
