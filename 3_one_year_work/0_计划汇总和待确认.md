# N1～N14 计划汇总：Claude 代做的决定和待用户确认的问题

> 2026-11-20 用户说“直接做，不用问我”。下面是写计划和参考代码时 Claude 替用户做的决定，每条写了理由和做错的代价，用户回来后逐条过一遍。

## Claude 代做的决定

| 阶段 | 问题 | 决定 | 理由 | 做错的代价 |
|---|---|---|---|---|
| N6 | PSNR/SSIM 在哪算 | 在板子上用板子的 ffmpeg 算，只把 CSV 拉回 Mac | 两段原始 YUV 约 1.9 GB，Mac 剩余空间只有几 GB | 板子 ffmpeg 没有 libvmaf/ssim 滤镜时要改回 Mac |
| N6 | 素材 | 只用摄像头自录（静态、运动各 10 秒）；H.265 不单独跑一组 | 对比要能拉开差距，自录的静态/运动已够；H.265 加倍工作量 | 报告缺标准序列，面试时可比性弱一点 |
| N10 | 模型转换机器 | 先在 OrbStack rk-dev（x86_64 Ubuntu 22.04、Python 3.10）上试 | 已有、版本对得上 cp310 | Rosetta 下 toolkit2 跑不通就换编 SDK 的 Ubuntu |
| N10 | 测试视频 | M1 用网上的行人视频文件；M2 起用摄像头实时 | M1 只验证检测流水线，文件可重复 | 无 |
| N10 | N3 没做完时的事件录像 | 参考代码直接依赖 N3 参考代码的 `Mp4FileWriter` | 参考代码按阶段顺序一起写 | N3 接口变了要同步改 |
| N9 | 代码谁写（概览写“到时再定”） | 参考代码 Claude 全写；用户手敲 SIP 报文、Digest、注册状态机、PS 封装、RTP 拆包，socket / XML 模板 / 配置 / 脚本直接复制 | 和主干一样：协议核心自己写过才讲得清 | 用户想全交给 Claude 时，只是少敲几个文件 |
| N8、N14 | 代码谁写（C 方案未确认） | 参考代码 Claude 全写；N14 用户有 Android 经验，核心（Camera2 → MediaCodec、推流）用户自己敲；N8 按浅的部分处理，用户读懂、跑通 | 按 C 方案的默认划分 | 无 |
| N2 / N8 | 真 IPC 要 RTSP Digest 鉴权，主码流多是 H.265 | N2 参考代码直接支持 H.265 FU 解包（N1 M3 已经发 H.265）和 RTSP Digest（Digest 代码和 N9 共用一份 `md5_digest`） | 不然 N8 接真 IPC 只能拉 H.264 子码流 | N2 多 1～2 天工作量 |
| N8 | Mac 上的 ONVIF 工具 | Python onvif-zeep（还没装，M0 第一步 `pip install onvif-zeep`） | 最轻 | 无 |
| N9 | 标准版本 | 以 GB28181-2016 为主对抓包（WVP 开源版是 2016），2022 版只读差异 | 和平台实际行为一致 | 无 |
