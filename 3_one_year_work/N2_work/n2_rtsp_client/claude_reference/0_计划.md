## 1. 做什么、为什么

**一句话**：自己写 RTSP 客户端：连上 N1 的服务端（板子上 `127.0.0.1:8554`）→ OPTIONS…PLAY → 从 interleaved 字节流里拆出 RTP 包 → 还原成完整的 NAL 和一帧帧码流 → 存文件 / 送进 MPP 解码；断线自动重连，丢包时丢到下一个 IDR。这是 NVR 接入 IPC 时做的事。

**为什么做**

| 对应 JD（`2_nvr_work/README.md` 第 5 节、`JD分析.md`） | N2 怎么对应 |
|---|---|
| RTSP/RTP；接入、拉流 | 手写客户端状态机、SDP 解析、interleaved 拆包、FU-A / H.265 FU 重组 |
| 瑞芯微平台硬件编解码 | 收到的帧直接送 MPP 解码 |
| 稳定性（7×24） | 断线检测、退避重连、seq 回绕和丢包判断、丢包后等 IDR |

**给后面谁用**：N3 用“收包不解码”那一半（`RtspReceiver` 吐出的一帧帧码流直接封装 MP4）；N5 每一路通道 = `ReconnectingReceiver` + `StreamDecodeStage`；N8 拿到的 RTSP 地址交给 N2 拉流。

### 4.3 线程模型和对象所有权

**全程单线程**（M1～M4）：主线程里 `RtspReceiver` 收 → 拼帧 → 存文件或 `StreamDecodeStage` 送解码、取帧，一帧一帧顺序做。理由：走 TCP 不乱序，一路 30 fps 的解码远比收包快，没必要加队列；对象全在 `runMx()` 的栈上，生命周期一眼看清。

| 对象 | 谁拥有 | 什么时候释放 |
|---|---|---|
| socket fd | `RtspClient`（RAII，析构 `close`） | 断线、重连前、程序结束 |
| `RtspClient`、`InterleavedReader`、`RtpDepacketizer`、`FrameAssembler` | `RtspReceiver` 的成员 | 每次重连时整个 `RtspReceiver` 重建（`std::unique_ptr<RtspReceiver> receiverPtr`），重组缓存一起清掉 |
| `MppDecoder` | `StreamDecodeStage` 用 `std::unique_ptr<MppDecoder> decoderPtr` 持有 | 重连后码流重新开始（可能换了分辨率、换了编码格式）：销毁重建 |
| 停止 | Ctrl+C → `sigaction`（不带 `SA_RESTART`）的处理函数只设 `std::atomic<bool>` + `shutdown(socketFd, SHUT_RDWR)`，阻塞中的 `recv` 立刻返回 | `shutdown` 是异步信号安全函数：**推断**，写代码前查 `man 7 signal-safety` |

N5 要多路时，每一路一个线程跑同样的循环，再在“拿到一帧”之后分给录像队列和预览队列（见第 7 节）。

### 4.4 和 N1 的约定（客户端怎么用）

| 项目 | 客户端的做法 |
|---|---|
| URL | 默认 `rtsp://127.0.0.1:8554/aaa.264`；H.265 测试 `rtsp://127.0.0.1:8554/out_720p.h265` |
| 请求 | `OPTIONS`；`DESCRIBE`（`Accept: application/sdp`）；`SETUP <control URL>`（`Transport: RTP/AVP/TCP;unicast;interleaved=0-1`）；`PLAY <Content-Base>`（`Session`、`Range: npt=0.000-`）；结束时 `TEARDOWN`。每个请求带递增的 `CSeq`，`User-Agent: n2_rtsp_client` |
| 回复检查 | 状态码 200；`CSeq` 和请求一致，不一致就报错断开 |
| control URL | `a=control` 是完整 `rtsp://` 地址就直接用；否则 = `Content-Base`（没有就用请求 URL）+（末尾没有 `/` 时补 `/`）+ control。N1 给的是 `track0`，得到 `rtsp://127.0.0.1:8554/aaa.264/track0`（RFC 2326 附录 C.1.1） |
| Session | 取 `Session:` 头里 `;` 前面的部分，之后的请求都带上；`timeout=60` 记下，本阶段不发保活（N1 不会因为没收到保活断开） |
| 编码格式 | `a=rtpmap:96 H264/90000` → H.264；`H265/90000` → H.265；时钟频率必须是 90000 |
| 参数集 | H.264：`sprop-parameter-sets` 按逗号分成 SPS、PPS，base64 解码；H.265：`sprop-vps`、`sprop-sps`、`sprop-pps` |
| 通道 | 通道 0 = 视频 RTP；通道 1 = RTCP（N1 不发；连 live555 时会收到 SR，读完丢掉）；其他通道号打日志丢掉 |
| RTP | 不假设 seq、时间戳、SSRC 的初始值（N1 每个会话随机）；第一个包定 SSRC，之后 SSRC 变了打日志 |
| 时间戳 | 文件源相邻帧固定差 3000；摄像头源约 3000 不精确；客户端把 32 位时间戳展开成 64 位（`extendedRtpTimestamp`），以防回绕（90 kHz 下约 13.25 小时绕一圈，随机初值可能更早绕） |
| 打包 | 只处理单 NAL 包（H.264 type 1～23、H.265 type 0～47）和 FU（H.264 type 28、H.265 type 49）；STAP-A（24）/ AP（48）打日志、丢掉（N1 不发） |
| 帧结束 | M=1 的包是一帧最后一个包；时间戳变了但没见到 M=1 时，把已攒的当成一帧交出去（兜底） |
| 流结束 | 文件源不循环时，N1 发完最后一帧会关连接 → `recv` 返回 0：M1～M3 当作“正常结束”打印统计；M4 当作断线去重连 |

### M1 信令 + 收包（第 07 周）

- **干了什么**：TCP 连 N1，发 OPTIONS → DESCRIBE → SETUP → PLAY，按 `Content-Length` 读完回复正文，解析 SDP；PLAY 之后从字节流里切出一个个 `$` 帧，解析 RTP 头并打印。
- **输入**：N1 服务端（`m4 file /userdata/av/aaa.264`，也测 `out_720p.h265`）。
- **输出**：日志：四个请求的状态码、编码格式、SPS/PPS 长度和前 4 个字节、每个 RTP 包的 seq / timestamp / M / 负载第一个字节；收满 300 帧（按 M 位数）后发 TEARDOWN 退出。
- **新增文件**：`rtsp/*`、`rtp/interleaved_reader.*`、`rtp/rtp_packet.*`、`common/base64.*`、`app/m1_receive_packets.*`；E 线 `media/bit_reader.*`。

### M2 解包重组（第 08 周）

- **干了什么**：RTP 负载 → 完整 NAL（单 NAL 包补起始码；FU-A 按 S/E 位拼回并还原 NAL 头）→ 按 M 位分帧 → 文件开头写 SDP 里的 SPS/PPS，之后逐帧写成 Annex-B。
- **输入**：N1 `m4 file /userdata/av/aaa.264`。
- **输出**：板子 `/userdata/av/n2_received.h264`；日志：收到帧数、FU 重组次数、丢弃的残缺 NAL 数。
- **新增文件**：`rtp/rtp_depacketizer.*`、`rtp/frame_assembler.*`、`media/encoded_frame.h`、`pipeline/rtsp_receiver.*`、`app/m2_save_stream.*`；E 线 `media/h264_sps_parser.*`（profile、level、sps_id、宏块宽高）。
- **关键接口**：

```cpp
struct StreamInfo {                    // 一次连接的码流信息（重连后可能变）

    int clockRateHz = 90000;

};
struct EncodedFrame {                  // 一帧码流（给存文件、解码、N3 录像）
    std::vector<uint8_t> annexBData;   // 每个 NAL 前面都有 00 00 00 01
    uint32_t rtpTimestamp = 0;
    int64_t extendedRtpTimestamp = 0;  // 展开成 64 位，单调递增
    bool isKeyFrame = false;           // 含 IDR（H.264 type 5；H.265 type 16～21）
    int64_t frameIndex = 0;            // 这次连接里的第几帧
};
enum class DepacketizeResult { NalReady, NeedMorePackets, Dropped };
class RtpDepacketizer {
public:
    explicit RtpDepacketizer(VideoCodec requestedCodec);
    DepacketizeResult pushPacket(const RtpPacketView &packet, std::vector<uint8_t> &outputNal); // outputNal 不带起始码
    void resetPartialNal();            // 丢包时调用：丢掉拼了一半的 FU
    int getDroppedNalCount() const;
};
class FrameAssembler {
public:
    // 输入一个完整 NAL；isMarker / rtpTimestamp 来自携带它最后一片的 RTP 包；凑满一帧返回 true
    bool pushNal(const std::vector<uint8_t> &nal, uint32_t rtpTimestamp, bool isMarker, EncodedFrame &outputFrame);
    void waitForNextKeyFrame();        // （M4）丢包后：清空，直到下一个关键帧才再交出帧
};
enum class ReceiveResult { FrameReady, StreamEnded, Timeout, Error };
class RtspReceiver {
public:
    bool connectAndPlay(const std::string &requestedUrl);   // OPTIONS…PLAY，成功后 getStreamInfo 有效
    ReceiveResult receiveNextFrame(EncodedFrame &outputFrame);
    const StreamInfo &getStreamInfo() const;
    void teardownAndClose();
    int getLostPacketCount() const;    // M4 起有意义
};
```

伪代码（FU-A 重组，RFC 6184 第 5.8 节）：S=1 → 新 NAL 头 = `(indicator & 0xE0) | (fuHeader & 0x1F)`，开始缓存 `payload + 2`；中间片追加；E=1 → 输出。没有 S 就来了中间片或 E 片、或 seq 不连续 → 丢掉这个 NAL，`droppedNalCount + 1`。H.265（RFC 7798 第 4.4.3 节）：NAL 头 = `{(payloadHdr[0] & 0x81) | (fuType << 1), payloadHdr[1]}`，负载从 `payload + 3` 开始。

- **验收**：
  1. `./run_on_board_with_mac.sh m2` 跑完（约 60 秒），日志收到 1803 帧、丢弃 NAL 0 个。
  2. `adb pull /userdata/av/n2_received.h264`，Mac 上 `ffplay n2_received.h264` 能播、不花屏。
  3. 逐帧比对：
     ```bash

     diff <(grep -v '^#' source_md5.txt | awk -F, '{print $6}') <(grep -v '^#' received_md5.txt | awk -F, '{print $6}')
     ```

### M3 接上解码（第 08 周）

- **干了什么**：每拼好一帧就送 `MppDecoder::feed`，循环 `getFrame` 取 NV12；流结束时送 EOS，取到 EOS 帧为止；数正常帧和错误帧。
- **输入**：同 M2。
- **输出**：日志：解码帧数、错误帧数、info change 次数、首帧宽高和 stride。
- **新增文件**：`pipeline/stream_decode_stage.*`、`app/m3_decode_stream.*`；复制 `decoder/mpp_decoder.*`。
- **关键接口**：

### M4 断线重连 + 丢包恢复（第 09 周）

- **干了什么**：`RtpSequenceChecker` 用 16 位无符号减法判断丢包 / 重复；丢包时 `RtpDepacketizer::resetPartialNal()` + `FrameAssembler::waitForNextKeyFrame()`；`SO_RCVTIMEO` 5 秒收不到数据算断线；`ReconnectingReceiver` 关旧连接、重建接收器和解码器，按 1、2、4、8、10、10… 秒退避重连，连上并收到第一帧后退避清零。
- **输入**：N1 打开故障注入：`--drop-every 100`、`--initial-seq 65500`、`--close-after-half-response`；服务端被 `kill -9`、`kill -STOP`、重启。
- **输出**：日志：丢包次数和个数、等 IDR 次数和每次等了几帧、重连次数和每次用时。
- **新增文件**：`rtp/rtp_sequence_checker.*`、`pipeline/reconnecting_receiver.*`、`app/m4_reconnect_decode.*`、`run_reconnect_test_on_board.sh`；E 线 SPS 裁剪。
- **关键接口**：

```cpp
enum class SequenceCheckResult { InOrder, PacketsLost, DuplicateOrOld, FirstPacket };
class RtpSequenceChecker {
public:
    // diff = (uint16_t)(sequenceNumber - expectedSequenceNumber)：0 = 正常；1～0x7FFF = 丢了 diff 个；其余 = 旧包或重复（RFC 3550 附录 A.1 的思路，简化）
    SequenceCheckResult check(uint16_t sequenceNumber, int &outputLostPacketCount);
    int64_t getTotalLostPacketCount() const;
};
enum class ReconnectingReceiveResult { FrameReady, StreamRestarted, Stopped };
class ReconnectingReceiver {
public:
    ReconnectingReceiver(std::string requestedUrl, int requestedReceiveTimeoutMs, int requestedMaxBackoffMs);
    // StreamRestarted：重新连上了，getStreamInfo 可能变了，调用方要重建解码器
    ReconnectingReceiveResult receiveNextFrame(EncodedFrame &outputFrame);
    const StreamInfo &getStreamInfo() const;
    void requestStop();                // 信号处理函数里调：设标志 + shutdown 当前 socket
    int getReconnectCount() const;
};
struct H264SpsInfo { int profileIdc = 0, levelIdc = 0, spsId = 0, widthPixels = 0, heightPixels = 0; };  // E 线
bool parseH264Sps(const uint8_t *sps, size_t spsSizeBytes, H264SpsInfo &outputInfo);  // 宽高已减去裁剪
```

- **验收**：
  1. 服务端 `--drop-every 100`：客户端报的丢包个数 = 服务端打印的“已丢 N 个包”；`n2_received.h264` 或解码过程不花屏（丢包后停住，下一个 IDR 恢复），等 IDR 每次 ≤ 60 帧。
  2. 服务端 `--initial-seq 65500`：seq 回绕到 0 时不报丢包。
  3. `./run_reconnect_test_on_board.sh`：服务端重启 10 次（每次间隔 5～15 秒），客户端 10 次都恢复出帧，日志 `reconnectCount=10`。
  4. 服务端 `kill -9`：客户端 10 秒内发现（`recv` 返回 0 或出错）并开始重连；`kill -STOP`：5 秒超时后发现；`kill -CONT` 前客户端一直在退避重试，不崩溃。
  5. H.265（`out_720p.h265`）+ `--drop-every 100`：重组和等 IDR 正常，解码错误帧 0（丢包期间的帧不送解码器）。
  6. 故障注入至少 3 个（例如重连后换成分辨率不同的文件、回复只发一半就断开、seq 回绕），每个写“现象 → 定位 → 根因”。
  7. E 线：aaa.264 的 SPS 解出 1920×1080（不是 1920×1088）。
- **学完能回答的问题**：周计划第 09 周 5 题（seq 回绕、为什么丢 P 帧会一直花、等 IDR 停多久和 GOP 的关系、为什么退避、服务端死了怎么尽快发现）。
- **用户敲**：`rtp_sequence_checker`、等 IDR 的逻辑（`FrameAssembler::waitForNextKeyFrame` 和调用处）、`reconnecting_receiver` 的重连状态机。**复制**：信号处理、`run_reconnect_test_on_board.sh`、N1 的故障注入开关（已在 N1 第 06 周快照）。

## 6. 风险和还没验证的推断

| # | 风险 / 推断 | 怎么处理 |
|---|---|---|
| 1 | adb 只转发 TCP；N2 在板子上走 127.0.0.1，本来就不经过 adb，所以 RTP 也一律 interleaved（N1 只支持 TCP） | 已核对（README 第 3 节） |
| 2 | 走 TCP 不会真丢包、不会乱序，丢包只能靠 N1 的开关模拟；所以 jitter buffer、NACK 都不做 | 周计划第 07、09 周“本周不学” |
| 3 | 板子上的回环流量没法用 Mac 的 Wireshark 抓 | 客户端日志打印足够的字段；需要看包时让 Mac 上的 ffplay 连 N1 对照 |
| 4 | `adb shell` 里后台起的服务端，在 `adb shell` 退出后会不会被杀掉：**推断**可能被杀 | 脚本里用 `nohup` + `setsid`（板子 busybox 有没有 `setsid`：**推断有**），第 07 周写脚本时实测 |
| 5 | Ctrl+C 时 `shutdown` 打断阻塞的 `recv`；`shutdown` 是异步信号安全函数：**推断** | `man 7 signal-safety` 核对；不是的话改成 `SO_RCVTIMEO` 1 秒醒一次查标志 |
| 6 | 32 位 RTP 时间戳回绕：90 kHz 下约 13.25 小时一圈（2^32 / 90000 = 47722 秒），随机初值可能更早 | `extendedRtpTimestamp` 展开；N3 的 PTS、N5 的 24 小时测试都用展开后的值 |
| 7 | 每个 IDR 前都有 SPS/PPS（aaa.264 已核对、摄像头源 EACH_IDR），所以重连 / 丢包后从关键帧开始送解码器就够；如果遇到只在开头有 SPS/PPS 的 IPC，要在关键帧前补 SDP 里的参数集 | 本阶段只记在 m4 文档“以后再挖”，N8 接真 IPC 时再处理 |
| 8 | 重连后分辨率变了，MPP 能不能靠 info change 自己处理：本计划直接销毁重建解码器，不依赖它 | 第 09 周故障注入验证 |
| 9 | `sub_720p.h264` 在板子上：**推断** | 第 09 周前 `adb shell ls -l /userdata/av/` |
| 10 | FrameAssembler 的“时间戳变化兜底”和 M 位同时存在，如果 N1 漏设 M 位，帧会晚一帧交出（要等到下一帧的第一个包） | 正常情况只靠 M 位；兜底触发时打日志计数（N1 故障注入可以出这道题） |

## 7. 给后面阶段提供的接口

| 谁用 | 用什么 | 怎么用 |
|---|---|---|
| N3 录像 | `RtspReceiver` / `ReconnectingReceiver` + `EncodedFrame` + `StreamInfo`（**收包不解码**） | 拿到 `EncodedFrame` 直接交给 libavformat：`StreamInfo` 的 SPS/PPS 做 extradata（N3 自己转 AVCC），`extendedRtpTimestamp` 换算 PTS（time_base 1/90000），`isKeyFrame` 决定在哪切分段；`StreamRestarted` 时关掉当前文件开新文件 |
| N5 整合 | 每路一个线程：`ReconnectingReceiver` → 一帧分两份（`std::shared_ptr<const EncodedFrame>`）→ 录像队列（N3）+ 解码队列（`StreamDecodeStage` → Day 6 的 RGA 拼图） | N2 本身是单线程，N5 在外面加线程和队列；N2 的类不加锁 |
| N4 回放 | `StreamDecodeStage` | 输入从“网络来的帧”换成“MP4 读出来的帧”，接口不变 |
| N8 ONVIF | `RtspClient` | 拿到真 IPC 的 RTSP 地址后直接拉；真 IPC 多半要 Digest 鉴权（401），那时再加 |
| N12 WebRTC | `RtpSequenceChecker`、`RtpDepacketizer` | 对照 libdatachannel 收包的做法 |
