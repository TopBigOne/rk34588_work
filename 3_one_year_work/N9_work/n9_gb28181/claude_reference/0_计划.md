## 1. 做什么、为什么做

**一句话**：板子扮演一台 GB28181 **设备**（IPC），用 SIP over UDP 注册到 Mac 上 docker 跑的 WVP-PRO + ZLMediaKit，定时发心跳、回目录查询；平台点播时收到 INVITE，把 H.264 封装成 **PS 流**，用 RTP over UDP 推给 ZLMediaKit，平台网页上看到板子的画面。

**为什么做**：ONVIF/GB28181 有 6 份 JD（J03、J04、J08、J09、J10、J13），J03 加分项原文"RTSP/SIP/RTCP/ONVIF/GB28181"，J13 是"SIP/GB28181/RTP/RTCP"（`JD分析.md` 第 2、3 节，已核对）。国内安防设备要接公安、园区平台，基本都走国标。

**一深多浅**：
- **深（手写）**：SIP 报文拼装和解析、Digest 鉴权、REGISTER/心跳状态机、PS 封装（pack header / system header / PSM / PES）、PS 的 RTP 拆包。
- **浅（用现成的）**：平台用 WVP-PRO + ZLMediaKit（开源，docker）；PS 封装用 FFmpeg 的 `-f mpeg` 生成一份对照文件，和自己写的逐字节比包头（ffmpeg 4.4 有 `mpeg`、`vob`、`dvd` 三个 PS 封装器，2026-11-20 `ffmpeg -muxers` 已核对）。
- SIP 库（libosip2 / libeXosip2 / sofia-sip / pjsip）只记一句：Buildroot 里都有包（`buildroot/package/` 已核对），但工具链 sysroot 里没有头文件（2026-11-20 已核对），本阶段不用。

**代码由谁写**：概览里 N9 是"到时再定"（`一年学习计划.md` 第 34 行，已核对），第 36 周任务"开始前要准备好"第 1 条要求先定。本计划给出建议的分工（第 5 节每个里程碑的"核心 / 样板"），**需要用户决定**。

### 4.2 线程和所有权

| 线程 | 做什么 | 谁拥有 |
|---|---|---|
| 主线程 = SIP 线程 | `receive(timeoutMs=200)` 循环；每轮检查"该续约了 / 该发心跳了 / 注册超时"；收到报文就分发 | `GbDeviceSession` 拥有 `SipUdpTransport`（值成员） |
| 推流线程（每个点播会话一个；本阶段同时最多 1 个） | 从源取帧 → `PsMuxer` → `RtpPsSender` | `GbDeviceSession` 持有 `std::unique_ptr<MediaPushSession> pushSessionPtr`；收到 ACK 时创建并 `start()`，收到 BYE 或注销时 `stop()`（置 `std::atomic<bool> isStopRequested`，`join`）再 reset |

不用 epoll、不用定时器线程：心跳 60 s 一次，200 ms 的轮询精度够用。

### M2：注册和心跳（第 36 周）

- **干了什么**：
  1. 拼 REGISTER（`Via` 带 `rport` 和 branch、`From`/`To` 都是 `sip:设备ID@域`、`Call-ID`、`CSeq`、`Contact`、`Expires: 3600`），UDP 发到平台 SIP 端口。
  2. 收 401，解析 `WWW-Authenticate: Digest realm=..., nonce=..., algorithm=MD5`；`HA1 = MD5(用户名:realm:密码)`，`HA2 = MD5(REGISTER:uri)`，`response = MD5(HA1:nonce:HA2)`（不带 qop 时；带 qop 时公式多 nc、cnonce，RFC 2617）；CSeq 加 1 重发。
  3. 200 OK 后进入 Registered；每 `kKeepaliveIntervalSeconds`（60）发 `MESSAGE`，正文 `Content-Type: Application/MANSCDP+xml`，`<CmdType>Keepalive</CmdType>`；`Expires` 到 2/3 时续约。
  4. 心跳连续 3 次没收到 200，或平台回 4xx → 回到 Unregistered，重新走注册（平台重启后自动恢复）。
- **20 位编码**（周计划问题 3）：前 8 位中心编码（省 2 + 市 2 + 区县 2 + 基层单位 2）、2 位行业、3 位类型（例如 132 = 网络摄像机）、1 位网络标识、6 位序号。具体取值对照标准附录（**推断**，开始前核对章节）。设备 ID 例：`34020000001320000001`，通道 ID 例：`34020000001310000001`（131 = 摄像机，**推断**）。
- **新增文件**：`common/md5_hex.*`、`sip/*`、`gb28181/gb_device_config.h`、`manscdp_xml.*`（Keepalive）、`gb_device_session.*`（注册 + 心跳部分）、`app/m2_register_keepalive.*`。
- **关键接口**：

### M3a：目录查询 + INVITE 信令（第 37 周）

- **干了什么**：收到平台的 `MESSAGE`（`CmdType=Catalog`）先回 200，再发一条 `MESSAGE` 带 Catalog 响应（`SumNum=1`，一个通道：通道 ID、名字、`Status=ON`）。平台可能还会查 DeviceInfo，同样回（**推断**，抓包看）。收到 INVITE：回 `100 Trying`；解析 SDP 里 `c=`（平台收流 IP）、`m=video 端口 RTP/AVP 96`、`y=`（10 位 SSRC，第 1 位 0 = 实时、1 = 历史，**推断**对照标准）、`a=setup`（有就说明要 TCP，本阶段只支持 UDP，回 488）；回 `200 OK` + 应答 SDP（`a=sendonly`、`a=rtpmap:96 PS/90000`、`y=` 原样带回）；收 ACK 后才开始推（M3c）；收 BYE 回 200 并停。
- **关键接口**：

- **验收**：平台网页设备下能看到 1 个通道；网页点播后 Wireshark 里有 INVITE → 100 → 200 OK → ACK，关掉播放窗口后有 BYE → 200（这时还没有画面，平台会提示收流超时，正常）。

### M3b：PS 封装，先写文件（第 37 周）

- **干了什么**：每帧前加 pack header（`00 00 01 BA`，14 字节，SCR 用 90 kHz 时间戳、mux_rate）；**I 帧前**再加 system header（`00 00 01 BB`）和 PSM（`00 00 01 BC`，视频 `stream_type = 0x1B` = H.264）；帧数据放进视频 PES（`00 00 01 E0`，带 PTS；一帧超过 PES 长度字段上限 65535 时拆成几个 PES）。解码器从 I 帧开始解，所以 I 帧前必须带"有哪些流、各是什么编码"的说明（周计划问题 2）。
- **输入**：N1 的文件源（Day 4 摄像头录的 `.h264`，30 fps）。**输出**：`/userdata/av/n9_out.ps`。
- **关键接口**：
  ```cpp
  class PsMuxer {
  public:
      // 一帧 Annex-B（含 SPS/PPS 的 I 帧整体作为一帧传入）→ 追加到 psBytes；ptsUs 单位微秒
      void muxVideoFrame(const uint8_t *annexBData, size_t sizeBytes, int64_t ptsUs, bool isKeyFrame, std::vector<uint8_t> &psBytes);
  };
  int runM3WritePsFile();
  ```
- **验收**：
  ```bash

  ffprobe -v error -show_entries format=format_name:stream=codec_name,width,height -count_frames -show_entries stream=nb_read_frames n9_out.ps
  # 期望：format_name=mpeg，codec_name=h264，宽高 = 源文件，nb_read_frames = 源文件帧数
  ```

### M3c：RTP 推流 + 平台点播（第 37 周）

- **干了什么**：一段 PS 按每包负载 ≤ 1400 字节拆成多个 RTP 包；同一帧的包时间戳相同（90 kHz），**最后一个包 M 位 = 1**；PT 96；SSRC = `y=` 的十进制数；UDP 发到 SDP 里的 IP:端口。源换成 N1 的摄像头编码源（实时）。
- **关键接口**：
  ```cpp
  class RtpPsSender {
  public:
      bool open(const std::string &remoteIp, int remotePort, uint32_t ssrc, int requestedLocalPort);
      bool sendPsFrame(const std::vector<uint8_t> &psBytes, uint32_t rtpTimestamp90k); // 拆包、发送、seq 递增
  };
  class MediaPushSession {
  public:
      MediaPushSession(std::unique_ptr<EncodedFrameSource> requestedSourcePtr, const SdpOffer &requestedOffer);
      bool start();   // 起推流线程
      void stop();    // 置停止标志、join；可重复调
  };
  ```

- **验收**（周计划验收）：
  - 网页点播出画面，连续 10 分钟不花屏、不断流（ZLM 日志里没有 PS 解析错误）。
  - 点停止后 Wireshark 过滤 `udp.dstport == <SDP 端口>` 不再有包。
  - 故障注入：① 推流线程里每 50 个 RTP 包丢 1 个 → 看网页花屏多久恢复（到下一个 I 帧）；② 平台不回 ACK → 不推流，INVITE 事务超时后清理；③ 重复收到同一个 INVITE（同 Call-ID）→ 重发上次的 200，不另起推流线程。
- **学完能回答**：第 37 周问题 1～5。

## 6. 风险和还没验证的推断

1. **docker 里的 SIP 走 UDP 端口映射**：设备看到的回包源地址可能是 docker 网关地址，Via/Contact 对不上导致平台找不到设备。对策：`.env` 的 SIP_ShowIP 填 Mac 局域网 IP；不行就把 WVP 容器改成 host 网络（OrbStack 支持程度 **推断**）。
2. **平台端口不是 5060**：WVP docker 版 README 写的 SIP 是 8116（已核对 README），以 M1 实际记录为准，代码里全部从 `app_config.h` 读。
3. **WVP 是否先查 Catalog 才能点播**：周计划标了推断，M3a 抓包确认。
4. **XML 字符集**：国标规定 GB2312，WVP 对 UTF-8 是否宽容 **推断**；通道名只用 ASCII 就绕开了。
5. **MPP 编码输出的 I 帧是否自带 SPS/PPS**：Day 4 的编码器怎么配的要看 N1 的源；PS 的 I 帧前要能拿到 SPS/PPS（N1 M4 写了"每个 IDR 前带上 SPS/PPS"，**假设**沿用）。
6. **RTP over TCP**：新版 WVP 可能默认让设备 TCP 推流（`a=setup:active/passive`），本阶段只做 UDP；网页"国标设置"或点播参数里选 UDP（**推断**有这个选项）。

## 7. 接口

### 依赖前面阶段（假设，等 N1 的计划定了再对）

| 阶段 | 假设的接口 | 本阶段怎么用 |
|---|---|---|
| N1 `n1_rtsp_server` | `struct EncodedFrame { std::vector<uint8_t> annexBData; int64_t ptsUs; bool isKeyFrame; };` | PS 封装的输入 |
| N1 | `class EncodedFrameSource { public: virtual bool readFrame(EncodedFrame &frame) = 0; ... };`，两个实现：`H264FileSource`（读 Day 5 的文件、按帧切、按 30 fps 打时间戳）和 `CameraEncodeSource`（Day 4 的 `CameraCapture` + `MppEncoder`） | M3b 用文件源，M3c 用摄像头源 |
| N1 | `size_t writeRtpHeader(uint8_t *outBuf, uint8_t payloadType, bool isMarker, uint16_t sequenceNumber, uint32_t timestamp, uint32_t ssrc);`（返回 12） | `RtpPsSender` 用；N1 的 FU-A 打包不用（这里负载是 PS，不是 NAL） |

### 给后面阶段提供

- `computeDigestResponse` / `parseDigestChallenge`：**N8**（第 38 周）给 N2 的 RTSP 客户端加 Digest 鉴权时直接复用（RTSP 的 Digest 和 SIP 是同一套 RFC 2617）。
- `PsMuxer`：以后做 GB28181 录像回放、或 NVR 作为平台收 PS 时的对照。
- `SipMessage` + `SipUdpTransport`：以后做平台级联 / 语音对讲的起点（本年不做）。
