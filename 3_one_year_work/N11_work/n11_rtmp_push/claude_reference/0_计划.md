### 4.2 线程模型和所有权

- **时间戳**：N1 的 `AccessUnit` 只有 `captureTimeUs`（摄像头源）、文件源为 0（`0_跨阶段接口.md` 第 2 节），推流要的是从 0 开始的 PTS。所以每个输出各自持有一个 `PtsAssigner`：直播源用 `captureTimeUs − 本输出收到的第一帧的 captureTimeUs`；文件源用 `本输出收到的第几帧 × 1000000 / 30`。每个输出从自己的第一帧归零，所以中途重连、中途加入都不用特殊处理。
- **M1、M2**：单线程。`CameraAccessUnitSource::readNextAccessUnit` 阻塞拿一帧 → `PtsAssigner` → 推流对象发出去。对象都由 `runM1…` / `runM2…` 栈上持有，函数返回时析构（先关推流、再关编码器、再关摄像头）。
- **M3**：
  - 直接用 N1 M4 的分发机制，不另写：`StreamHub` 的源线程读摄像头 → 每帧做成 `std::shared_ptr<const AccessUnit>` → 推进每个订阅者的 `ClientFrameQueue`（满了丢到下一个关键帧，不阻塞源线程）。
  - RTSP：N1 的 `RtspServer`（主线程 accept；每个客户端一个会话线程 + 一个发送线程），客户端 PLAY 时向 hub `subscribe()`。
  - RTMP 发送线程：启动时向同一个 hub `subscribe()` → `popWait` → `PtsAssigner` → `RtmpPublisher::sendAccessUnit`；发送失败 → 关连接 → 每 1 秒重连一次 → 重连成功后先发 AVC sequence header，再丢帧直到下一个关键帧。
  - 所有权：N1 里 `StreamHub` 归 `RtspServer` 所有；M3 要两个输出共用一路摄像头，所以改成 `runM3…` 持有 `std::unique_ptr<StreamHub> streamHubPtr`，`RtspServer` 只拿引用（对 N1 代码唯一的改动）。`runM3…` 还持有 `RtmpPublisher`、RTMP 发送线程。退出顺序：RTMP 线程 `queue->abort()` + join → `unsubscribe` → 停 `RtspServer` → 析构 hub（停源线程、关摄像头）。
- 进程开头 `signal(SIGPIPE, SIG_IGN)`（或 `send` 带 `MSG_NOSIGNAL`）：mediaMTX 被关掉时，往断开的 socket 写数据，内核默认发 SIGPIPE 直接杀掉进程。

## 5. 各里程碑

### M1 先用 FFmpeg 推通（第 28 周）

**干了什么**：摄像头画面 → MPP 编成 H.264 → libavformat 的 flv 封装 + `rtmp://127.0.0.1:1935/live/cam` → 经 `adb reverse` 到 Mac 的 mediaMTX → Mac 上 ffplay 拉流。

**输入**：`/dev/video22` 的 NV12（1920×1080，30 fps）；没有摄像头时用 `/userdata/av/main_1080p.h264`（`FileAccessUnitSource`，按 30 fps 节流）。
**输出**：mediaMTX 上的流 `live/cam`；Mac 上 ffplay 出画面；Wireshark 抓包截图。

**新增文件**：`pipeline/pts_assigner.h/.cpp`、`mux/annexb_joiner.h/.cpp`、`sink/ffmpeg_rtmp_publisher.h/.cpp`、`app/m1_push_with_ffmpeg.h/.cpp`、`app/app_config.h`、`main.cpp`、`CMakeLists.txt`、`run_on_board_with_mac.sh`、`tools/mediamtx_n11.yml`；其余从 Day 4/6、N1、N6 复制。

**关键接口**：

```cpp
// pipeline/pts_assigner.h
class PtsAssigner {
public:
    PtsAssigner(bool requestedIsLiveSource, int requestedFps);
    int64_t assignPtsUs(const AccessUnit &accessUnit); // 返回微秒、第一帧 = 0。直播源：captureTimeUs − 第一帧；文件源：第几帧 × 1000000 / fps
};
// mux/annexb_joiner.h
void appendNalUnitsAsAnnexB(const std::vector<std::vector<uint8_t>> &nalUnits,
                            std::vector<uint8_t> &annexBBytes);       // 每个 NAL 前加 00 00 00 01，追加到 annexBBytes 末尾
// sink/ffmpeg_rtmp_publisher.h
class FfmpegRtmpPublisher {
public:
    bool open(const char *rtmpUrl, int width, int height, int fps,
              const ParameterSets &parameterSets);                   // SPS、PPS 来自 AccessUnitSource::getParameterSets()
    bool writeAccessUnit(const AccessUnit &accessUnit, int64_t ptsUs); // pts = dts = ptsUs / 1000（time_base 1/1000，没有 B 帧）
    void close();                                                    // av_write_trailer + avio_closep
private:
    AVFormatContext *outputContext = nullptr;
    AVStream *videoStream = nullptr;
};
int runM1PushWithFfmpeg();
```

伪代码：`avformat_network_init` → `avformat_alloc_output_context2(&ctx, nullptr, "flv", url)` → `avformat_new_stream` → 填 `codecpar`（`AVMEDIA_TYPE_VIDEO`、`AV_CODEC_ID_H264`、宽高、`extradata` = 加了起始码的 SPS+PPS，用 `av_mallocz` 分配并多留 `AV_INPUT_BUFFER_PADDING_SIZE`）→ `avio_open2(&ctx->pb, url, AVIO_FLAG_WRITE, …)` → `avformat_write_header` → 循环：`appendNalUnitsAsAnnexB` 拼成一个 `AVPacket` → `av_interleaved_write_frame`。

- extradata 和每帧都给 Annex-B 就行：flv 封装发现 extradata 第一个字节不是 1，会自己转成 avcC、把每帧转成 4 字节长度前缀（已核对 `FFmpeg-6.0/libavformat/flvenc.c` 第 550 行 `ff_isom_write_avcc`、第 917～918 行 `ff_avc_parse_nal_units_buf`）。M2 手写时这一步要自己做，这正是 M2 要学的。
- SPS/PPS 直接用 `getParameterSets()`（N1 的源已经切好、不带起始码）；Day 6 的编码器每个 IDR 前也带 SPS/PPS（`MPP_ENC_HEADER_MODE_EACH_IDR`，已核对 `day6_nvr_mosaic/claude_reference/src/encoder/mpp_encoder.cpp` 第 68 行），所以中途连上的播放器也能解。

### M2 手写最小推流端（第 29 周，可选）

**干了什么**：不用 libavformat，自己完成：TCP 连接 → 握手 → `connect` → `releaseStream`/`FCPublish`/`createStream` → `publish` → 先发 AVC sequence header，再按帧发 video 消息。

**输入**：同 M1。**输出**：mediaMTX 上的同一个流；Wireshark 抓包能和 M1 的逐步对照。

**协议要点**（写代码前对照规范核对一遍）：

| 内容 | 要点 | 依据 |
|---|---|---|
| 握手 | C0 = 1 字节版本号 3；C1 = 1536 字节（4 字节时间、4 字节 0、1528 字节随机数）；客户端发 C0+C1，收 S0+S1+S2，回 C2（= S1 原样） | 1536 已核对（`FFmpeg-6.0/libavformat/rtmp.h` 第 30 行 `RTMP_HANDSHAKE_PACKET_SIZE`）；其余按 Adobe RTMP 规范，**推断**（未打开原文）。FFmpeg 用的是带 HMAC 的“复杂握手”，mediaMTX 接受简单握手：**推断** |
| chunk 头 | basic header（fmt 2 位 + csid）+ message header：fmt 0 = 11 字节、1 = 7、2 = 3、3 = 0；算上 1 字节 basic header 就是 12/8/4/1 | 已核对（`rtmppkt.h` 第 68～71 行 `RTMP_PS_TWELVEBYTES` … `RTMP_PS_ONEBYTE`）。message stream id 是**小端**：**推断**（规范原文） |
| chunk 大小 | 默认 128 字节；先发 Set Chunk Size（消息类型 1）改成 4096 | 类型号已核对（`rtmppkt.h` 第 48 行）；128 是规范默认值，**推断** |
| 消息类型 | 1 Set Chunk Size、5 Window Ack Size、6 Set Peer BW、9 视频、18 数据（`@setDataFrame`）、20 AMF0 命令 | 已核对（`rtmppkt.h` 第 48～61 行） |
| chunk stream id | FFmpeg 用 2 = 协议控制、3 = 命令、6 = 视频、8 = publish 等流命令 | 已核对（`rtmppkt.h` 第 37～41 行） |

### M3 同一路画面同时出 RTSP 和 RTMP，比延迟和断线恢复（第 29 周）

**干了什么**：一个进程里，摄像头编码一次，N1 的 `StreamHub` 同时分给 N1 的 `RtspServer` 和 RTMP 推流（M2 做了就用手写的，否则用 M1 的）。Mac 上同时开两个 ffplay，加上计时器页面，**一张截图同时读出两种协议的延迟**。

**输入**：摄像头。**输出**：延迟表（5 次）、断线恢复记录。

**新增文件**：`pipeline/rtmp_push_worker.*`、`app/m3_rtsp_rtmp_latency.*`、`tools/latency_timer.html`；复制 N1 的 `rtp/`、`rtsp/`、`pipeline/`（`rtsp_server` 改成接收外部的 `StreamHub&`）。

**关键接口**：

**端口安排**：N1 的 RTSP 在板子 8554，照 N1 的脚本 `adb forward tcp:8554 tcp:8554`；mediaMTX 默认也监听 8554（**推断**），所以 `mediamtx_n11.yml` 里把 mediaMTX 的 RTSP 关掉（不关的话 Mac 侧改用 8556；8555 N1 已经给 live555 用了）；RTMP 仍是 `adb reverse tcp:1935 tcp:1935`。两种协议都走同一根 USB，条件一致。

**延迟测法**（第 29 周计划写好的方法，本计划补细节）：
1. Mac 上浏览器全屏开 `tools/latency_timer.html`（显示毫秒，`requestAnimationFrame` 刷新），摄像头对着屏幕拍。
2. 两个播放窗口和计时器排在同一屏：`ffplay -fflags nobuffer -flags low_delay -framedrop -rtsp_transport tcp rtsp://127.0.0.1:8554/camera` 和 `ffplay -fflags nobuffer -flags low_delay -framedrop rtmp://127.0.0.1:1935/live/cam`。
3. `Cmd+Shift+3` 截图；延迟 = 计时器当前值 − 窗口里拍到的计时器值。每种协议 5 张截图取平均，记下分辨率、码率、GOP、播放器参数。
4. 误差：摄像头一帧 33 ms + 屏幕刷新 16.7 ms + 计时器数字本身的刷新，**单次误差约 ±50 ms**（推断），所以只比较平均值，差距小于 50 ms 的算“测不出差别”。

**期望**（全部是**推断**，第 29 周开始前 Claude 先上板 probe 一次，确认差距看得出来再交给用户测）：
- RTSP（直连板子）约 150～350 ms；RTMP（多经过 mediaMTX 转发一次）约 200～500 ms。**两者可能只差几十毫秒，落在误差里**。这本身是结论：协议差别不大，延迟主要来自编码、播放器缓冲。
- 看得出明显差别的对照：同一个 RTMP 流，VLC 默认参数（网络缓存默认约 1000 ms，**推断**）和 ffplay `nobuffer` 能差约 1 秒。这一组放进表格，说明“播放器缓冲”这一环。
- 断线恢复：推流中途 `Ctrl+C` 关掉 mediaMTX，5 秒后再启动。推流端日志应显示：发送失败 → 每秒重连 → 重连成功 → 发 sequence header → 等到下一个关键帧才发数据。记两个时间：服务器启动到 `publish` 成功（期望 ≤ 1～2 秒），到 ffplay 重新打开后出画面（期望 ≤ 1 个 GOP，GOP 60 时 ≤ 2 秒）。RTSP 这边：关掉 ffplay 再打开，记出画面用时（同样受 GOP 限制）。

## 6. 风险和还没验证的推断

| 风险 | 影响 | 怎么确认 / 退路 |
|---|---|---|
| 板子 adbd 不支持 `adb reverse` | M1 推不到 Mac | 第 28 周任务 2 先试；不行就用方案 B（板子上的 mediaMTX + `adb forward`），或者接网线 |
| mediaMTX 不接受简单握手 | M2 握手失败 | 抓包看服务器有没有回 S0/S1/S2；不行就照 FFmpeg `rtmpproto.c` 的 `rtmp_handshake` 补 HMAC 部分，或者换 nginx-rtmp 试 |
| RTSP 和 RTMP 延迟差距落在误差里 | 用户觉得“没测出东西”（见项目记忆 feedback_experiment_design） | 先 probe；表格里加“播放器缓冲”那一组，保证有一个明显的对比 |
| 一个进程同时跑 RTSP 服务端和 RTMP 推流，RTMP 卡住拖慢 RTSP | 延迟数据不准 | N1 的 `ClientFrameQueue` 满了丢到关键帧、不阻塞源线程，RTMP 在自己的线程发 |
| N6 的实际接口和第 7 节假设不同；N1 计划之后再改 | 复制过来要改 | N6 计划定了、N1 计划有变动时，Claude 先对一遍第 7 节 |
| FFmpeg 6.0 的 libavformat 在 `avio_open2` 里阻塞很久（服务器没开时） | 重连时卡住 | 设置 `rw_timeout` 选项（**推断**选项名，以 FFmpeg 6.0 文档为准） |

## 8. 和周计划、README 不一致的地方
