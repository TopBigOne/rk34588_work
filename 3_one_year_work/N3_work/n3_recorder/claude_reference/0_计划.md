## 1. 做什么、为什么

**一句话**：N2 拉到的 H.264/H.265 帧**不解码**，直接用 libavformat 封装成 MP4；每 N 分钟在下一个 IDR 处切一个新文件；每段写一条 SQLite 索引；空间不够时删最早的录像；改用 fragmented MP4，`kill -9` 后已写的部分仍能播。

| J02 加分项“多路采集与存储架构” | JD分析.md 第 3 节 J02 摘要，已核对 |

**给后面谁用**

- **N10**（第 15～18 周）：事件录像复用 `Mp4FileWriter`，事件表加在同一个 SQLite 数据库里（第 17 周计划任务 5，已核对）。

### 4.2 线程模型和所有权

- **N3 单独运行时只有一个线程**：主线程循环 `receiver.receiveNextFrame() → recorder.writeFrame()`（N2 没好时 receiver 换成 `raw_stream_frame_source`）。录像写盘每秒约 1 MB（上面的估算），不需要单独的写盘线程；N5 才把“收”和“写”拆成两个线程，中间加队列（N5 M1 决定）。
- **退出**：`SIGINT` 处理函数只把一个 `std::atomic<bool>` 置位；主循环看到后 `recorder.close()`（写 trailer、补索引）再退出。`kill -9` 不走这条路，靠 M4 的 fMP4 + 启动修复兜底。
- **所有权**：`app` 里的函数在栈上按顺序声明 `RecordIndex` → `StorageReclaimer`（引用 index）→ `SegmentRecorder`（拿两者的裸指针，不拥有）→ source；析构顺序反过来，保证 recorder 关文件时 index 还活着。`Mp4FileWriter` 归 `SegmentRecorder` 所有（成员对象，每段 `close` 后 `open` 复用同一个）。`AVFormatContext` 用 `common/ffmpeg_utils.h` 的删除器包成 `AvFormatContextPtr`。

- **关键接口**

```cpp
// 输入类型 StreamInfo / EncodedFrame 来自 N2，定义见 3_one_year_work/0_跨阶段接口.md 第 3 节
struct VideoTrackParams {                     // 写 MP4 视频轨要的参数（N3 自己定义）
    VideoCodec codec;                         // H264 / H265
    int width;                                // 像素。StreamInfo 里没有宽高：用 N2 并行线的 SPS 解析器算，
    int height;                               // 没有就先写死在 app_config.h（1920×1080）
    std::vector<uint8_t> extradataAnnexb;     // StreamInfo 的 vps/sps/pps 各自前面补 00 00 00 01 拼起来
};
VideoTrackParams buildVideoTrackParams(const StreamInfo &streamInfo, int width, int height);

class Mp4FileWriter {
public:
    bool open(const std::string &requestedFilePath, const VideoTrackParams &trackParams, bool shouldFragment);
    bool writeFrame(const EncodedFrame &frame, int64_t ptsIn90kHz);    // ptsIn90kHz：这个文件里从 0 开始
    bool close();                                                        // av_write_trailer + 关文件
    bool isOpen() const;
    int64_t getWrittenBytes() const;
    int getWrittenFrameCount() const;
};
```

  内部顺序（伪代码，照 Mac 本机 `remuxing.c` 第 134 / 165 / 173 行的 `avformat_write_header` / `av_interleaved_write_frame` / `av_write_trailer`，已核对）：
  `avformat_alloc_output_context2(mp4) → avformat_new_stream → 填 codecpar（codec_id、宽高、extradata = extradataAnnexb）→ avio_open → avformat_write_header（这里传 movflags）→ 每帧：AVPacket 指向帧数据、pts = dts = ptsIn90kHz、IDR 打 AV_PKT_FLAG_KEY、av_packet_rescale_ts(1/90000 → stream->time_base) → av_interleaved_write_frame → close 时 av_write_trailer`。

- **两个要先确认的事实**（第 10 周任务 4、5）
  1. **Annex-B 转 AVCC 由谁做**：FFmpeg **6.0.2** 源码 `~/rk-toolchain/ffmpeg6-src/libavformat/movenc.c` 第 6087 行：H.264 的 extradata 第一个字节不是 1（也就是 Annex-B）时，封装器自己把每个包转成长度前缀；H.265 在第 6106 行，同样处理；avcC/hvcC 由第 1360 / 1384 行 `ff_isom_write_avcc` / `ff_isom_write_hvcc` 从 Annex-B 的 extradata 生成（已核对）。**板子用的 4.4.1 源码没核对**，推断一样；第 10 周用 box 遍历器看 `avcC` 和 `mdat` 里每帧开头是不是 4 字节长度来确认。
  2. **time_base 会被改**：4.4 头文件 `avformat.h` 第 899 行写明“`avformat_write_header()` 里封装器会覆盖 `time_base`”（已核对）；movenc 用 `time_base.den` 当 timescale，小于 10000 才翻倍（6.0.2 `movenc.c` 第 7108～7109 行，已核对），所以设 1/90000 大概率保持不变（推断）。代码里一律在写头之后按 `stream->time_base` 换算，不假设。

- **关键接口**

```cpp
struct SegmentRecorderConfig {
    std::string recordRootPath;   // 例 /userdata/n3_rec
    int channelIndex;             // 0～3
    int segmentDurationSeconds;   // 测试 60，产品 600
    bool shouldFragment;          // M4 起为 true
};

class SegmentRecorder {
public:
    bool open(const SegmentRecorderConfig &requestedConfig, const VideoTrackParams &trackParams);
    bool writeFrame(const EncodedFrame &frame);        // 到时间且是 IDR → 切段；第一帧不是 IDR 就丢，直到 IDR
    void markDiscontinuity();                          // 上游 StreamRestarted / 时间戳倒退：下一个 IDR 强制开新段
    void updateTrackParams(const VideoTrackParams &trackParams); // 重连后 SPS/PPS 可能变，下一段用新的
    bool close();
    int getClosedSegmentCount() const;
};

std::string buildSegmentFilePath(const std::string &recordRootPath, int channelIndex,
                                 int64_t segmentStartTimeMs); // 本地时间；目录不存在就 mkdir -p
```

  **PTS 约定**：每个文件第一帧 PTS = 0，之后 = 本帧 `extendedRtpTimestamp` − 段首帧的 `extendedRtpTimestamp`（N2 已展开成 64 位）。段首帧的墙上时间由 N3 在写这一帧时自己取（`EncodedFrame` 里没有墙上时间）。这条是给 N4 的约定（第 7 节）。

### M3 索引（第 13 周）

- **干了什么**：开新段时插一条（结束时间 NULL），关段时补结束时间和大小；按“通道 + 时间段”查出**有重叠**的段。
- **输入**：M2 的录像流程。**输出**：`/userdata/n3_rec/record_index.db`。
- **文件**：新建 `storage/record_index.*`、`app/m3_record_with_index.*`；`SegmentRecorder::open` 多一个 `RecordIndex *recordIndex` 参数（可以是 `nullptr`，M2 的路径不受影响）。
- **表结构**（第 13 周任务 2 给的字段，已核对；这里只是 Claude 的草稿，用户定稿）

```sql
CREATE TABLE IF NOT EXISTS recordings (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    channel_index INTEGER NOT NULL,
    start_time_ms INTEGER NOT NULL,   -- 段首帧的墙上时间（Unix 毫秒）
    end_time_ms   INTEGER,            -- NULL = 正在录，或者异常中断还没修
    file_path     TEXT    NOT NULL UNIQUE,
    size_bytes    INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_recordings_channel_start ON recordings(channel_index, start_time_ms);
-- 查重叠：[a1,a2) 和 [b1,b2) 重叠 ⇔ a1 < b2 AND b1 < a2（第 13 周“资料”，已核对）
SELECT ... WHERE channel_index = ?1 AND start_time_ms < ?3 AND (end_time_ms IS NULL OR end_time_ms > ?2)
ORDER BY start_time_ms;
```

  `end_time_ms` = `start_time_ms` + (段内最后一帧 PTS + 一帧时长) / 90。墙上时间只在段首取一次，段内按 RTP 时间戳算，避免两种时钟混用。

## 6. 风险和还没验证的推断

| # | 风险 / 推断 | 怎么处理 |
|---|---|---|
| 1 | **RTP 时间戳 32 位会回绕**：90 kHz 下 2³² / 90000 ≈ 47722 秒 ≈ **13.3 小时**（计算）。N3 单测碰不到，**N5 的 24 小时测试一定会碰到** | N2 的 `EncodedFrame::extendedRtpTimestamp` 已展开成 64 位（0_跨阶段接口.md 第 3 节）；N3 只用它，不用 32 位的 `rtpTimestamp`。N3 M2 用 `raw_stream_frame_source` 造一段跨回绕的时间戳做单测 |
| 2 | N1 循环发文件时，RTP 时间戳可能从头开始（倒退）→ `av_interleaved_write_frame` 报 “non monotonically increasing dts” | `Mp4FileWriter` 写之前检查单调；倒退就 `markDiscontinuity()`，下一个 IDR 开新段 |
| 3 | 4.4.1 的 movenc 是否和 6.0.2 一样自动转 Annex-B（推断） | 第 10 周任务 4 用 box 遍历器确认；不一样就自己转（Day 8 `annexb_converter` 反方向可对照） |
| 4 | fMP4 没正常关闭时没有 `mfra`，Mac 播放器拖进度条可能要从头扫 `moof`、`ffprobe` 的 `duration` 可能不准（推断） | 验收用 `-count_frames` 数帧，不用 duration；seek 速度留给 N4 M1 实测 |
| 5 | `kill -9` ≠ 断电：`kill -9` 时已经 `write` 进内核的数据还在页缓存里，会落盘；真断电会丢页缓存里的 | 只按周计划测 `kill -9`；“写完要 `fsync` 才真正落盘”只到够用线（第 14 周“本周不学”） |
| 6 | 1 分钟一段 ≈ 58 MB，1 小时测试写 eMMC 约 3.5 GB；N5 4 路 24 小时会写约 336 GB（计算），对板载 eMMC 有磨损 | N3 不受影响；N5 计划里提给用户决定（降低测试源码率或接 U 盘） |
| 7 | 板子上有没有 `libsqlite3.so`、`/userdata` 剩多少、系统时间准不准，**都未实测**（板子 2026-11-20 没连上） | 第 10、13 周开工第一步查 |
| 8 | N2 的接口按 0_跨阶段接口.md 写，N2 实现时可能还会小改 | 只有 `app/` 里调接收端的几行受影响，`storage/` 不动 |
| 10 | `StreamInfo` 没有宽高；宽高写 0 时 MP4 能不能播（推断：tkhd 宽高为 0，有的播放器会出问题） | M1 先写死 1920×1080；N2 的 SPS 解析器（第 09 周并行线）好了以后换成算出来的 |
| 9 | `start_time_ms` 用墙上时间，系统时间被往回调会让新段的开始时间比旧段早（第 14 周故障注入之一） | 只做到“能发现并打日志”；用单调时钟纠正记进“以后再挖” |

## 7. 接口

### 7.1 依赖前面阶段的接口

**N2**：按 `3_one_year_work/0_跨阶段接口.md` 第 1、3 节（2026-11-20 Claude 定，来源是 N2 的计划；起草本计划时 N2 计划还没给我看，**等 N2 实现定了再对**）。N3 用到的部分：

```cpp
struct StreamInfo   { VideoCodec codec; int clockRateHz; std::vector<uint8_t> vps, sps, pps; };   // 参数集不带起始码
struct EncodedFrame { std::vector<uint8_t> annexBData; uint32_t rtpTimestamp;
                      int64_t extendedRtpTimestamp; bool isKeyFrame; int64_t frameIndex; };
enum class ReconnectingReceiveResult { FrameReady, StreamRestarted, Stopped };
class ReconnectingReceiver {
public:
    ReconnectingReceiver(std::string requestedUrl, int requestedReceiveTimeoutMs, int requestedMaxBackoffMs);
    ReconnectingReceiveResult receiveNextFrame(EncodedFrame &outputFrame); // StreamRestarted：开新录像文件
    const StreamInfo &getStreamInfo() const;
    void requestStop();
};
```

- N3 主循环：`FrameReady` → `recorder.writeFrame`；`StreamRestarted` → `recorder.markDiscontinuity()` + `updateTrackParams(新的 StreamInfo)`；`Stopped` → `close()`。
- **还要和 N2 对的两点（假设）**：① `isKeyFrame` 为 true 的帧里是否一定带 SPS/PPS（`aaa.264` 本身每个 IDR 前都有，N1 M4 也要求“每个 IDR 前带 SPS/PPS”，README N1，已核对）；② `StreamRestarted` 之后第一帧是否保证是 IDR（N3 不依赖它：`SegmentRecorder` 自己丢到 IDR）。
- 0_跨阶段接口.md 写 H.265 关键帧是 NAL 16～21（IRAP），N3 按它；N2 周计划写的是 19/20（IDR），两者对 `out_720p.h265` 是否有区别**未核对**。
- **N1（假设）**：服务端能指定端口和输入文件、能循环发送、循环时 RTP 时间戳继续增长（N5 起 4 个实例也要靠这个）。
