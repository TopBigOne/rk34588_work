## 1. 做什么、为什么做

**一句话**：板子接上网线后，用 WS-Discovery 组播搜到局域网里的 IPC，再用 SOAP 调 ONVIF 的 GetProfiles → GetStreamUri（带 WS-Security 鉴权）拿到每个码流的 RTSP 地址，交给 N2 的 RTSP 客户端拉流，N5 的 mini NVR 多一路真摄像头。

**为什么做**：ONVIF/GB28181 在 18 份 JD 里出现 6 次（J03、J04、J08、J09、J10、J13，见 `JD分析.md` 第 2 节）。NVR"插上网线自动搜到摄像头"就是这个功能。按"一深多浅"：
- **深（手写）**：WS-Discovery 的 Probe/ProbeMatch、SOAP 报文、PasswordDigest 计算。报文就几段固定 XML，手写比 gSOAP 生成的几万行代码更容易讲清。
- **浅（用现成工具）**：Mac 上用 Python 的 `onvif-zeep` 跑同样的流程，抓包和手写版逐字段对照。

**代码由谁写**：周计划写"按概览的 C 方案，N8 由 Claude 写，你负责读懂、跑通、抓包"。C 方案用户**还没确认**（`一年学习计划.md` 第 26～34 行，已核对）。本计划按"Claude 写参考实现，用户读懂 + 跑通 + 抓包"排；第 5 节每个里程碑仍列出"如果自己敲，敲哪几个文件"。

### 4.2 线程和所有权

- 单线程、同步调用：发现阶段阻塞等 `kProbeWaitMs`（例如 3000 ms），SOAP 每次请求 curl 超时 5 s。N8 只是 NVR 启动时跑一次的工具，不需要并发。
- `WsDiscoveryClient` 拥有一个 UDP socket（RAII，析构 `close`）。`SoapHttpClient` 拥有一个 `CURL*`（`unique_ptr` + 删除器 `curl_easy_cleanup`，变量名 `curlHandlePtr`）。libxml2 的 `xmlDoc*` 同样用 `unique_ptr` 包起来（`xmlDocPtr` 和 libxml2 自己的类型名撞了，变量叫 `responseDocPtr`，类型别名叫 `XmlDocumentPtr`）。
- `curl_global_init` / `xmlInitParser` 在 `main` 里调一次。

## 5. 里程碑

### M0：IPC 上手 + 看现成工具发的包

- **干了什么**：网页登录 IPC → 打开 ONVIF、建 ONVIF 用户（很多 IPC 的 ONVIF 用户和网页用户分开，**推断**）→ VLC 按说明书地址拉 RTSP；Mac 上用 onvif-zeep 写 10 行脚本调 GetProfiles/GetStreamUri，Wireshark 抓全过程。
- **输入**：IPC 说明书、IPC 的 IP（从路由器后台看）。
- **输出**：VLC 出画面；一份标注过的抓包（过滤条件 `udp.port == 3702 || http`）：Probe、ProbeMatch、GetProfiles、GetStreamUri 各一条，标出 `XAddrs`、`ProfileToken`、`Uri`、`UsernameToken` 四处。
- **验收**：`ffprobe -rtsp_transport tcp "rtsp://用户:密码@IPC_IP:554/..."` 打出 `codec_name=hevc`（或 h264）和分辨率。
- **学完能回答**：周计划问题 1、2。

### M1：WS-Discovery 设备发现

- **干了什么**：往 `239.255.255.250:3702` 发一份 Probe（SOAP over UDP，`Types` 写 `dn:NetworkVideoTransmitter`，`MessageID` 用随机 UUID），在同一个 socket 上收若干个 ProbeMatch（单播回到发 Probe 的源端口），解析 `XAddrs`（设备服务地址，例如 `http://192.168.1.64/onvif/device_service`）和 `EndpointReference/Address`（设备 UUID，用来去重）。
- **输入**：`app_config.h` 里的 `kProbeWaitMs`；可选的网卡地址（多网卡时用 `IP_MULTICAST_IF` 指定从 eth0 发）。
- **输出**：终端打印每台设备的 IP、UUID、XAddrs、Scopes 里的型号名。
- **新增文件**：`ws_discovery_client.*`、`onvif_xml.*`（Probe 模板 + ProbeMatch 解析部分）、`m1_discover_devices.*`、`main.cpp`、`CMakeLists.txt`、`run_on_board_with_mac.sh`。
- **关键接口**：
  ```cpp
  struct DiscoveredDevice { std::string endpointUuid; std::string deviceServiceUrl; std::string ipAddress; std::string scopes; };
  class WsDiscoveryClient {
  public:
      bool openMulticastSocket(const char *requestedInterfaceAddress); // nullptr = 系统默认网卡
      bool sendProbe();
      std::vector<DiscoveredDevice> receiveProbeMatches(int waitMs);   // 收满 waitMs 才返回，按 endpointUuid 去重
  };
  std::string buildProbeEnvelope(const std::string &messageUuid);
  bool parseProbeMatch(const std::string &responseXml, DiscoveredDevice &parsedDevice);

  ```
- **验收**：

### M2：拿 RTSP 地址，交给 N2 拉流

- **干了什么**（四步，都是 HTTP POST，`Content-Type: application/soap+xml`）：
  1. `GetSystemDateAndTime`（不需要鉴权）→ 算出"IPC 时间 − 板子时间"的偏差。板子 RTC 不一定准，Created 用"板子时间 + 偏差"，否则鉴权可能失败（周计划问题 3）。
  2. `GetCapabilities`（Category=Media）→ 拿 Media 服务地址。
  3. `GetProfiles`（带 UsernameToken）→ 每个 profile 的 token、名字、编码、分辨率。
  4. 每个 profile 调 `GetStreamUri`（`Stream=RTP-Unicast`，`Transport/Protocol=RTSP`）→ RTSP 地址。
- **WS-Security**：`PasswordDigest = Base64(SHA1(nonce原始字节 + Created + 密码))`；报文里的 `Nonce` 是 nonce 原始字节的 Base64。（周计划写的 `nonce + created + password` 里的 nonce 指**解码后的原始字节**，不是 Base64 字符串，这一点 M2 文档要讲清。定义见 WS-Security UsernameToken Profile 1.0，**推断**，开始前对原文。）
- **输入**：M1 的 `deviceServiceUrl`；`app_config.h` 的 `kOnvifUserName`、`kOnvifPassword`。
- **输出**：每个 profile 一行：`token 编码 宽x高 rtsp://...`；同时写 `/userdata/av/n8_discovered_channels.conf`（格式见第 7 节"给后面阶段"），N5 直接读。
- **新增文件**：`soap_http_client.*`、`ws_security_token.*`、`onvif_media_client.*`、`onvif_xml.*`（补后四个模板和解析）、`m2_get_stream_uris.*`。
- **关键接口**：
  ```cpp
  class SoapHttpClient {
  public:
      bool open();
      int postEnvelope(const std::string &serviceUrl, const std::string &soapEnvelope, std::string &responseText); // 返回 HTTP 状态码，网络失败返回 -1
  };
  struct UsernameToken { std::string userName; std::string nonceBase64; std::string createdUtc; std::string passwordDigestBase64; };
  UsernameToken makeUsernameToken(const std::string &userName, const std::string &password, int64_t deviceClockOffsetSeconds);
  struct MediaProfile { std::string profileToken; std::string profileName; std::string encodingName; int width; int height; std::string rtspUrl; };
  class OnvifMediaClient {
  public:
      OnvifMediaClient(SoapHttpClient &requestedHttpClient, std::string requestedDeviceServiceUrl);
      bool fetchDeviceClockOffset(int64_t &clockOffsetSeconds);
      bool fetchMediaServiceUrl(std::string &mediaServiceUrl);
      bool fetchProfiles(const UsernameToken &token, std::vector<MediaProfile> &profiles);
      bool fetchStreamUri(const UsernameToken &token, MediaProfile &profile); // 填 profile.rtspUrl
  };
  std::string makeRtspUrlWithCredentials(const std::string &rtspUrl, const std::string &userName, const std::string &password);
  int runM2GetStreamUris();
  ```
- **验收**：
  ```bash
  ./run_on_board_with_mac.sh m2
  # 期望：至少 2 个 profile（主码流、子码流），每个都有 rtsp:// 地址；主码流编码 H265，分辨率和 IPC 网页设置一致
  adb shell cat /userdata/av/n8_discovered_channels.conf   # 期望：每行 "通道名 rtsp://用户:密码@IP:554/..."
  ```
  - 交给 N2：用主码流地址跑 N2 客户端，解码 0 错误帧（周计划验收第 2 条）。
  - N5：配置里换上这一路，2×2 预览里出现真摄像头画面。
  - 故障注入（周计划任务 7）：① 密码错 → 打印 "鉴权失败（HTTP 401 / SOAP Fault NotAuthorized）"，返回 1，不崩溃；② 把 `deviceClockOffsetSeconds` 强行加 3600 → 观察 IPC 是否拒绝（不同 IPC 容忍的偏差不同，**推断**），记进问题案例库；③ IPC 断电 → curl 超时 5 s 后提示，返回 1。

## 6. 风险和还没验证的推断

1. **N2 的客户端不一定支持 RTSP Digest 鉴权和 H.265**：README 把 N1 的 Digest 鉴权放到"N5 以后"，N2 里只写了 FU-A（H.264）。真 IPC 的 RTSP 基本都要 Digest、主码流是 H.265。**对策**：N9（第 36 周，在 N8 前面）会写 MD5 Digest 计算，N8 的 M2 顺手把它接进 N2 的 DESCRIBE；H.265 的 FU 解包看 N2 计划有没有（假设见第 7 节）。实在来不及，就先拉 IPC 的 H.264 子码流。
2. **IPC 默认 RTP 走 UDP**：N2 发的是 `Transport: RTP/AVP/TCP`，主流 IPC 都支持 interleaved（**推断**）。
3. **ONVIF 版本差异**：有的新设备只实现 Media2（`ver20`），GetStreamUri 的报文不一样。先用 Media（`ver10`），M0 抓包时看 IPC 的 GetCapabilities 返回里有没有 Media（**推断**大多数都有）。
4. **组播被路由器或 Wi-Fi 过滤**：板子和 IPC 都走有线就没问题；Mac 走 Wi-Fi 时可能收不到 ProbeMatch，只影响 Mac 上的抓包实验（**推断**）。
5. **板子上缺 libcurl / libxml2 的 .so**：sysroot 里有不等于根文件系统里装了，开始前 `adb shell ls` 确认；缺的话 libcurl 可以换成手写 HTTP POST（SOAP 就是一次短连接 POST）。
6. **IPC 不在手**：周计划已定"没买到的话本周当缓冲周"。

## 8. 和周计划不一致的地方

1. 周计划任务 2 写"Mac 上的 ONVIF 客户端工具未核对"。本计划定为 Python `onvif-zeep`（**推断**能用，Mac 上还没装）；Windows 上常用的 ONVIF Device Manager 在 Mac 上没有（**推断**）。
2. 周计划 M2 的调用顺序是 GetCapabilities → GetProfiles → GetStreamUri；本计划在最前面加了 **GetSystemDateAndTime**（不鉴权，算时间偏差），用来回答周计划问题 3 并避免鉴权失败。
3. 周计划没提"N2 要支持 RTSP Digest 鉴权 / H.265"这一前提（风险 1），任务 6 的 1.5 h 可能不够。
4. 周计划的 PasswordDigest 公式没写清 nonce 是原始字节（第 5 节 M2 已说明）。
