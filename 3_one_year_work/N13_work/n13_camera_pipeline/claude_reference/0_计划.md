## 1. 做什么、为什么做

**一句话**：不写驱动，讲清 IPC 的画面从哪来——IMX415 sensor 经 I2C 被配置、经 MIPI CSI-2 送出 RAW10，CIF 收下来交给 ISP 变成 YUV，再由 ISP 的 mainpath 作为 `/dev/video22` 交给我们 Day 3/Day 4 的 V4L2 + MPP 编码程序；能用工具看到每一环，读出 sensor 的一个寄存器，说清 3A 是谁在算。

**为什么做**：Sensor/ISP/V4L2/驱动/总线 9 份 JD（J01 J02 J03 J04 J05 J10 J11 J14 J15），其中 J03、J04 要 Sensor/ISP 集成，J01、J05、J10 要 I2C/SPI 总线（`JD分析.md` 第 2 节，已核对）。够用线是"能讲清这条链"，写驱动在线外。

**服务于哪个编解码问题**（按项目记忆"别学偏"）：编码器的输入就是这条链的输出。画面发绿、发暗、帧率不对、`/dev/videoX` 号变了——这些是做 IPC 编码时一定会碰到的问题，要知道往链路的哪一环查。

**够用线**（N13 专用，比 CLAUDE.md 里 V4L2 那条高一档）：知道 entity / pad / link，会用 `media-ctl` 和 `v4l2-ctl` 查；读得懂设备树里 sensor 节点和 endpoint 连线；会用 `i2ctransfer` 读寄存器；知道 3A 在用户态的 `rkaiq_3A_server` 里算、结果写回 sensor（曝光、增益）和 ISP（白平衡等）。**线外**：用 `MEDIA_IOC_*` ioctl 自己枚举拓扑、驱动怎么写、IQ tuning、rkaiq 内部算法。

**代码由谁写**：周计划写"本阶段基本不写代码"。本计划按此执行：用户读、敲命令、做实验；Claude 只写一个很小的参考工程（见第 4 节），用来把"按名字找节点"和"读 chip ID"落到代码里，用户读懂即可，不要求手敲。

## 5. 里程碑

### M1：链路结构

- **干了什么**：
  1. 读 `SDK/kernel/arch/arm64/boot/dts/rockchip/rk3588-alientek-cameras.dtsi`。第 7～10 行把 `ATK_CAMERA_1`～`ATK_CAMERA_4` **都定义了**，4 个口各有一个 `imx415@1a`：第 19 行（`&i2c3`，CSI3）、第 167 行（`&i2c4`，CSI4）、第 309 行（`&i2c7`，CSI1）、第 447 行（`&i2c2`，CSI2）（已核对）。Day 3 实测 sensor 实体名是 `m00_b_imx415 3-001a`（I2C 总线 3、地址 0x1a），所以用的是**第 19 行那个**（CSI3）。
  2. 给第 19～40 行逐个属性写注释：`reg = <0x1a>`（I2C 从地址）、`clocks`（给 sensor 的 27 MHz 主时钟 xvclk，驱动第 78 行 `IMX415_XVCLK_FREQ_27M`）、`reset-gpios` / `power-gpios`（上电时序用的 GPIO）、`rockchip,camera-module-name` / `lens-name`（rkaiq 用它找 IQ 文件）、`remote-endpoint = <&mipidphy0_in_ucam0>` + `data-lanes = <1 2 3 4>`（数据走 4 lane MIPI 进 csi2_dphy0）。
  3. 顺着 `remote-endpoint` 走完整条：`imx415 → csi2_dphy0（第 43 行）→ mipi2_csi2（第 77 行）→ rkcif_mipi_lvds2（第 117 行）→ rkcif_mipi_lvds2_sditf（第 127 行）→ rkisp0_vir0（第 149 行）`（已核对）。
  4. 板子上 `dmesg | grep -i imx415` 看探测日志（应有 `Detected imx415 id 0000e0`，驱动第 3031 行的打印，**推断**格式）；跑 `scripts/print_camera_chain.sh`，和设备树逐站对上。
- **输入**：设备树、驱动源码、板子。**输出**：一张 SVG 链路图（设备树节点名 / media 实体名 / 设备文件 / 每站的格式 四行对齐）、`doc/m1流程.md`。
- **验收**：
  ```bash
  adb shell 'for m in /dev/media*; do media-ctl -d $m -p 2>/dev/null | grep -q imx415 && echo $m; done'
  # 期望：/dev/media1（Day 3 实测值；以实际为准）
  adb push scripts/find_video_node.sh /tmp/ && adb shell sh /tmp/find_video_node.sh
  # 期望：/dev/video22
  ```
  每站格式和 Day 3 实测一致：sensor `SGBRG10 3864x2192` → ISP 输入 `SGBRG10 3840x2160` → ISP 输出 `YUYV8 3840x2160` → mainpath `NV12 1920x1080`（`v4l2-ctl和media-ctl用法.md` 2.4 节）。
- **学完能回答**：周计划问题 1、2、3（配置走 I2C，画面走 MIPI CSI-2）、5。

### M2：sensor 和 ISP

- **干了什么**：
  1. 读驱动 `SDK/kernel/drivers/media/i2c/imx415.c` 第 81～82 行（`CHIP_ID 0xE0`、`IMX415_REG_CHIP_ID 0x311A`）和第 3012～3031 行 `imx415_check_sensor_id`（已核对）。
  2. 板子上读一次：`i2ctransfer -f -y 3 w2@0x1a 0x31 0x1a r1`（写 2 字节寄存器地址、读 1 字节；`-f` 因为地址已被驱动占用）。sensor 不出流时可能处于掉电状态读不出（**推断**，驱动用了 runtime PM），这时先在另一个 adb shell 里跑 `capture` 让它出流，再读。
  3. 跑参考程序的 `chipid` 子命令（`I2C_RDWR` 一次发"写地址 + 读 1 字节"两条消息），结果应和 `i2ctransfer` 一致。
  4. `v4l2-ctl -d /dev/v4l-subdev2 --list-ctrls`：sensor 的 `exposure`、`analogue_gain`、`vertical_blanking`、`horizontal_flip`（驱动第 2975～2991 行注册了这几个控件，已核对）。
  5. 3A 对照（README 要求"改一两个参数看效果"）：`/etc/init.d/S40rkaiq_3A stop` → 用 `capture` 采一段 → `v4l2-ctl -c exposure=...,analogue_gain=...` 手动改两次各采一段 → `S40rkaiq_3A start` 再采一段。拉回 Mac 用 ffplay 看：3A 停掉后画面发暗、偏色、手动曝光生效；3A 起来后自动恢复。（3A 跑着时手动改会被马上改回去，Day 3 文档 1.6 节已记录。）
  6. 读 `SDK/external/camera_engine_rkaiq/` 目录结构（`rkaiq/`、`rkaiq_3A_server/`、`rkisp_demo/`、`media_enquiry/`、`iqfiles/isp3x/`），翻 `Rockchip_Development_Guide_3A_ISP30` 的总述部分，写一页笔记：3A 每帧从 ISP 拿统计 → 算曝光、增益、白平衡 → 曝光/增益经 sensor 子设备写进 sensor 寄存器、白平衡等写进 ISP 参数；IQ 文件是"这颗 sensor + 这个镜头"的标定参数。
  7. 故障注入（周计划任务 6）：① 停 3A 再采 → 画面暗、偏色；② `capture` 传错节点（`/dev/video11` 这类 CIF 出口）→ 拿到的是 RAW 或报格式错误；③ 要 4K 以上分辨率 → `S_FMT` 被驱动改回去。每条记现象和定位路径。
- **关键接口**：
  ```cpp
  class SensorRegisterReader {
  public:
      bool openBus(int requestedBusIndex);                                   // 打开 /dev/i2c-N
      bool readRegister8(uint16_t deviceAddress, uint16_t registerAddress, uint8_t &registerValue); // 16 位寄存器地址，读 1 字节
  };
  int runM2ReadChipId();                                 // 打印 0x311A 的值，和 kExpectedChipId 比
  int runM2CaptureEncode(const char *requestedVideoPath, int frameCount, const char *outputPath);
  ```
- **验收**：
  ```bash
  ./run_on_board_with_mac.sh chipid
  # 期望：chip id = 0xE0，和驱动 CHIP_ID 一致；读不出时打印 errno 和原因（周计划允许"清楚的失败记录"）
  ./run_on_board_with_mac.sh capture /dev/video22 150 /userdata/av/n13_3a_on.h264
  adb pull /userdata/av/n13_3a_on.h264 . && ffprobe -v error -count_frames -show_entries stream=codec_name,width,height,nb_read_frames n13_3a_on.h264
  # 期望：h264 1920x1080，nb_read_frames=150
  ```
  3A 对照：4 段码流各抽一帧 JPG 放 `doc/img/m2/`，肉眼能看出差别。
- **学完能回答**：周计划问题 3、4；另加"画面发绿 / 很暗，你先查哪两件事"（`pidof rkaiq_3A_server`、IQ 文件是否匹配模组名）。
- **核心 vs 样板**：本阶段用户不必手敲代码；用户自己敲的是命令和实验。参考工程里 `sensor_register_reader.cpp` 有逐行注释（`struct i2c_msg`、`I2C_RDWR`、`I2C_M_RD`）；`camera_capture`、`mpp_encoder` 是 Day 4 复制来的样板。

## 6. 风险和还没验证的推断

1. **读 chip ID 时 sensor 没上电**（第 5 节 M2 第 2 步）：推断，上板确认；不影响"链路讲得清"这个主验收。
2. **media 设备编号、video 编号随系统版本变**：所以 M1 专门做"按名字查"；Day 3 的 `media1` / `video22` 只当参考。
3. **板子上没有 i2c-tools**：那就只用参考程序的 `chipid`（它只依赖内核的 `/dev/i2c-N`，`linux/i2c-dev.h` 在 sysroot 里，已核对）。
4. **停掉 3A 后能不能再起来**：用 init 脚本重启 **推断**可以；不行就重启板子。
5. **README 写的 3A 含"对焦"**：设备树里 IMX415 节点没有 `lens-focus` / 马达（VCM）（2026-11-20 grep dtsi 无结果），这个模组是定焦，AF 在这块板子上不起作用（推断）。笔记里写"3A = AE、AWB、AF，本板只有前两个在工作"。
