## 1. 干了什么

M3 的流水线一行不改，只把输出路径从 `/userdata/av/mosaic.h265` 换成一个 FIFO `/tmp/n0_mosaic.fifo`。板子上另起一个 `gst-launch-1.0` 进程，从 FIFO 的另一头读码流、用 MPP 硬解、画到屏幕上。

```
本程序（n0_nvr_mosaic m4）                                         gst-launch-1.0（另一个进程）
4 路解码 → RGA 拼图 → MPP 编码 H.265 → fwrite ──→ [ FIFO /tmp/n0_mosaic.fifo ] ──→ filesrc → h265parse → mppvideodec → waylandsink → 屏幕
                                                  （内核里的管道，数据不落盘）
```

整个 M4 的代码只有一行：

```cpp
// app/m4_show_mosaic.cpp:14-16
int runM4ShowMosaic() {
    return runMosaicEncodePipeline(kM4FifoPath, "M4");
}
```

`runMosaicEncodePipeline`（`app/m3_encode_mosaic.cpp:49`）就是 M3 用的那个函数，M3 传的是 `kM3OutputPath`（:115）。M4 的工作量都在脚本 `run_m4_on_board_with_mac.sh` 里：建 FIFO、起 gst、起程序、看着两个进程、收尾。

## 4. 技术点

### 4.1 Linux：FIFO（命名管道）（问题 1）

**字面意思**：FIFO = First In First Out，先进先出。`mkfifo 路径` 在文件系统里建一个**特殊文件**（`ls -l` 第一个字符是 `p`），它不存数据，只是一个“名字”：一个进程以写方式打开它，另一个进程以读方式打开它，内核在中间搭一根管道，写进去的字节按顺序从另一头读出来。

**作用**：两个**不相干**的进程（本程序和 gst）之间传数据，不落盘。普通管道 `a | b` 只能在 shell 里把两个命令接起来；FIFO 有名字，谁知道路径谁就能打开。

和 M4 有关的三条规矩（`man 7 fifo`、`man 7 pipe`）：

| 规矩 | 在 M4 里的表现 |
|---|---|
| 以写方式打开时，**没有读的一方就一直阻塞**，直到有人以读方式打开 | 本程序停在 `StreamFileWriter::open` 的 `fopen(filePath, "wb")`（`sink/stream_file_writer.cpp:17`），也就是 `EncodeStage::open` 第 1 步（`pipeline/encode_stage.cpp:17-20`，注释写了“是 FIFO 的话，这里会等到播放器打开它”）。所以脚本**先起 gst，再起程序**；gst 起不来，程序就会一直停在这里 |
| 管道里的缓冲区满了，`write` 就阻塞，直到读的一方读走一些 | Linux 默认管道容量 65536 字节（`man 7 pipe`）。gst 读得慢，`fwrite` 就停住 → 编码段停住 → 拼图停住 → 各路队列满了 → 解码线程停在 `push` 里。背压一路传回去，不会越积越多 |
| 读的一方关掉以后还往里写，内核给写的进程发 `SIGPIPE` 信号，默认动作是**直接结束进程** | gst 中途崩了，本程序会在下一次 `fwrite` 时被 SIGPIPE 杀掉，不会打印“fwrite 没写完”（推断：程序没有处理 SIGPIPE）。脚本最后打印的返回码会是 141（128 + SIGPIPE 的编号 13，推断） |

写的一方 `fclose` 以后，读的一方读到 EOF（文件结束）。对 gst 来说就是 `filesrc` 发出 EOS，整条管道收尾退出。本程序的 `FilePtr` 在 `EncodeStage` 析构时 `fclose`，所以 M4 正常结束时 gst 也会跟着结束。

放在 `/tmp` 的原因：FIFO 不占磁盘空间，只是一个“通道”（`app/app_config.h:47-48` 的注释）。

### 4.2 gst-launch-1.0 管道（问题 2）

```sh
# run_m4_on_board_with_mac.sh:55（$FIFO_PATH、$GST_SINK 在脚本前面定义）
XDG_RUNTIME_DIR=/var/run WAYLAND_DISPLAY=wayland-0 gst-launch-1.0 filesrc location=$FIFO_PATH ! h265parse ! mppvideodec ! $GST_SINK > $GST_LOG 2>&1 &
```

`gst-launch-1.0` 是 GStreamer 的命令行工具：把一串元素（element）用 `!` 连成一条管道，数据从左往右流。每个元素：

| 元素 | 字面意思 → 在这里的作用 |
|---|---|
| `filesrc location=…` | 从文件读字节，按块往下游送 → 以读方式打开 FIFO（这一刻本程序的 `fopen` 才返回），读到 EOF 时发出 EOS |
| `h265parse` | H.265 码流解析器：在字节流里找 NAL 单元的起始码，切成一帧一帧（access unit），并从 VPS/SPS/PPS 里读出宽高等信息告诉下游 → 本程序写进 FIFO 的是连续字节，`fwrite` 的边界和帧的边界没关系，必须有人重新切帧 |
| `mppvideodec` | Rockchip 写的 GStreamer 插件，内部调用 MPP 解码 → 和我们 M1 里自己调的是同一个硬件解码器，输出 NV12 的 dma-buf |
| `waylandsink`（`$GST_SINK`，默认值在 `run_m4_on_board_with_mac.sh:19`） | Wayland 客户端：把每一帧交给 Wayland 合成器（板子上是 weston）显示 → 屏幕上出现一个窗口 |

`> $GST_LOG 2>&1 &`：gst 的输出写进 `/tmp/n0_gst.log`，`&` 让它在后台跑，脚本接着往下走。

### 4.3 Linux：`XDG_RUNTIME_DIR` 和 `WAYLAND_DISPLAY`（问题 3）

**字面意思**：两个环境变量。`XDG_RUNTIME_DIR` 是“当前用户放运行时文件（socket、锁文件）的目录”；`WAYLAND_DISPLAY` 是“Wayland 合成器的 socket 文件名”。Wayland 客户端（`waylandsink`、Qt 程序都是）连合成器时，去 `$XDG_RUNTIME_DIR/$WAYLAND_DISPLAY` 这个 socket 连。

**为什么要手动设**：weston 启动时环境里有这两个变量，所以它把 socket 建在 `/var/run/wayland-0`（在 weston 进程的环境变量里实测是 `/var/run`）。`adb shell` 开出来的 shell 是另一个环境，**没有** `XDG_RUNTIME_DIR`，客户端就不知道去哪找 socket。

**不设会怎样**：推断 `waylandsink` 连不上合成器，gst 报错退出（日志里大概是 `XDG_RUNTIME_DIR not set` 或 “could not connect to display”）。gst 一退出，FIFO 就没有读的一方，本程序永远停在 `fopen` —— 这正是 4.4 里脚本要处理的情况。

### 4.4 Linux：脚本怎么同时管两个进程

板子上的部分写在一个字符串 `BOARD_SCRIPT` 里（`run_m4_on_board_with_mac.sh:53-71`），用**一次** `adb shell` 跑完，两个进程在同一个 shell 里，结束时一起收拾：

| 步骤 | 行 | 做什么、为什么 |
|---|---|---|
| 第 1 步 | :54 | `rm -f` 再 `mkfifo`：上次异常退出可能留下 FIFO 或同名普通文件，先删再建，保证是一个新的 FIFO |
| 第 2 步 | :55-56 | 后台起 gst，`$!`（刚放到后台的进程号）记进 `GST_PID` |
| 第 3 步 | :57-58 | 后台起本程序，进程号记进 `APP_PID`。`LD_LIBRARY_PATH` 指向新版 MPP 库（项目约定） |
| 第 4 步 | :59-65 | 每秒看一次：`kill -0 PID` 不发信号，只检查进程还在不在。程序还在、gst 已经没了 → 打印 gst 日志、杀掉程序。没有这一步，gst 起不来时程序会永远停在 `fopen`，脚本也跟着卡死 |
| 第 5 步 | :66-70 | `wait` 等两个进程结束，`$?` 拿到程序的返回码；删掉 FIFO；用程序的返回码作为整个脚本的返回码 |

`$` 前面的 `\`：`BOARD_SCRIPT` 在 Mac 上用双引号定义，`\$!`、`\$APP_PID` 让这些 `$` 原样传到板子上，由板子上的 shell 展开；没有 `\` 的 `$FIFO_PATH` 等在 Mac 上就展开成具体值。

故意让 gst 起不来的验证方法：`GST_SINK=waylandsinkxxx ./run_m4_on_board_with_mac.sh`，预期 1～2 秒后打印 `[run_m4] gst 已经退出，程序还在，杀掉程序`，脚本正常结束（推断，待上板）。也可能看到另一种结果：gst 在报错退出前 `filesrc` 已经打开过 FIFO，程序的 `fopen` 返回了，接着写的时候被 SIGPIPE 结束，脚本打印 `程序返回 141`。两种都算“不卡死”，看到哪种记哪种。

### 4.5 为什么可能播得飞快（问题 4）

**时间戳是什么**：每一帧“应该在第几毫秒显示”的标记。mp4、RTSP 这些封装格式每帧都带时间戳；**裸码流（Annex B 的 .h265 文件）里没有**，只有一个接一个的 NAL 单元。

播放器按时间戳控制速度：帧早了就等，到点了才显示（一般的播放器都这么做，M5 也是）。M4 交给 gst 的是裸码流：

- 如果 gst 拿不到时间戳，`waylandsink` 收到一帧就显示一帧，**播放速度 = 本程序写进 FIFO 的速度**（再被硬解和显示的速度限制）。本程序是“能多快就多快”：M2 实测拼图 251.7 张/秒（[m2流程.md](m2流程.md) 第 75 行），加上编码后推断仍然明显高于 30 张/秒，所以 1803 帧可能十几秒就播完，看起来是快放。
- 如果 H.265 的 SPS 里带了帧率信息（VUI 里的 timing info），`h265parse` 可能按帧率自己补时间戳，那就会接近正常速度。MPP 编码器写不写这个信息，没查过（推断，上板看现象）。

两种情况都**允许**（设计 `0_设计.md` 第 22 行定的）：M4 只验证“画面能上屏”，正常速度留给 M5 用主时钟解决。上板看到的实际速度记进第 6 节，同时作为一条候选写进问题案例库（现象：上屏播得快；原因：裸码流没有时间戳；解决：M5 主时钟，或者封装成带时间戳的格式）。

注意 FIFO 的背压（4.1）：如果 gst 真的按时间戳慢慢播，本程序会被 FIFO 拖慢到同样的速度，日志里的“用时”就接近 60 秒；如果是快放，“用时”就接近 M3。**看日志里的用时就能反推 gst 有没有按时间戳播**（推断）。

### 4.6 MPP、RGA

M4 没有新的 MPP、RGA 知识点。和 M3 唯一的区别：M3 写进文件的字节，M4 原样写进 FIFO，码流头（VPS+SPS+PPS）照样写在最前面（`pipeline/encode_stage.cpp:25-31`）。gst 的 `h265parse` 必须先看到码流头才能告诉解码器宽高，这也是 M3 里“取了头就必须写”的另一个用处。

### 4.7 本篇重点（汇总四个问题）

1. **FIFO**：有名字的管道，一头写一头读，不落盘。写的一方 `fopen` 时如果没有读的一方，就阻塞到对方打开为止；所以先起 gst 再起程序，gst 起不来要由脚本把程序杀掉。
2. **gst 管道**：`filesrc` 读 FIFO → `h265parse` 把字节流切成帧 → `mppvideodec` 用 MPP 硬解 → `waylandsink` 交给 weston 显示。
3. **`XDG_RUNTIME_DIR`**：Wayland 客户端靠它和 `WAYLAND_DISPLAY` 找到合成器的 socket（`/var/run/wayland-0`）；`adb shell` 里没有，不设就连不上屏幕。
4. **播得快**：裸码流没有时间戳，gst 推断是拿到一帧显示一帧，速度由生产速度决定；正常速度要靠时间戳 + 时钟（M5）。

## 5. 业务场景：NVR 本地预览

NVR 接显示器时，最常见的界面就是“四分屏 / 九分屏预览”：多路摄像头的画面拼在一起实时显示。

- 真实产品一般**不会**像 M4 这样“拼好 → 编码 → 再解码 → 显示”，那样白白多了一次编码和一次解码。直接把拼好的大图（dma-buf）交给显示（DRM/KMS 或 Wayland）更省（推断，M4 这样做是为了复用 M3 的流水线，用现成的 gst 快速看到画面）。
- 但“编码后交给另一个进程”这条路本身很常见：把 FIFO 换成 RTSP 推流，就是 NVR 的“远程预览 / 转发”；把 gst 换成另一个程序，就是“录像进程和预览进程分开”。
- 进程之间用 FIFO 传码流，一个进程挂了另一个也会受影响（4.1 的阻塞和 SIGPIPE），所以真实系统里要处理“对方没起来 / 中途挂了”，M4 的脚本第 4 步就是最简单的版本。
