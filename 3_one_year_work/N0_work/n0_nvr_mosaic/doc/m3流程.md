## 0. 学完能回答的问题

1. 编码器最后为什么要排空（drain）？不排空会少什么？
2. 编码器的 stride 为什么要从大图上取（1920×1088），不自己按 1920×1080 算？
3. 大图只有一块 buffer，为什么能“拼一张、编一张”而不冲突？

答案在第 4 节对应的条目里，第 4.5 节再汇总一遍。

## 1. 干了什么

M2 拼出来的 1920×1080 大图不再抽两张存 YUV，而是**每一张都送进 MPP 编码器**，编成 H.265 码流，写进 `/userdata/av/mosaic.h265`。所有通道都解完后，给编码器送一个 EOS（结束标志），把编码器里剩下的包都取出来，再关文件。

```
解码线程 0：aaa.264         → 解码 → 队列 0 ┐
解码线程 1：out_720p.h265   → 解码 → 队列 1 ┤   主线程（循环）：
解码线程 2：main_1080p.h264 → 解码 → 队列 2 ┤ → ① RGA 拼一张大图（M2）
解码线程 3：out.h265        → 解码 → 队列 3 ┘   ② 大图送 MPP 编码器，取回一个包
                                                ③ 包写进 mosaic.h265
                                                ……所有通道都解完
                                              → ④ 送 EOS，排空编码器
```

主线程的循环在 `app/m3_encode_mosaic.cpp:25` 起，只有三种走向：

```cpp
// app/m3_encode_mosaic.cpp:27-28
if (composeResult == ComposeResult::AllChannelsEnded) {
    return encodeStage.drainEncoder(); // 所有通道都解完了：EOS 传到编码器
```

拼出一张 → `encodePicture`（:34）；所有通道都结束 → `drainEncoder`（:28）；出错 → `abortAllChannels`（:31、:35）叫停解码线程。

## 4. 技术点

### 4.1 MPP：创建编码器、读出默认配置再改

`MppEncoder::init`（`encoder/mpp_encoder.cpp:18`）分 6 步：

| 步骤 | 代码 | 字面意思 → 作用 |
|---|---|---|
| 创建 | `mpp_create(&encoderCtx, &encoderApi)`（:26） | 创建一个 MPP 实例，同时拿到函数表 `MppApi`（`encode_put_frame`、`encode_get_packet`、`control` 都在里面）→ 后面所有操作都通过这对 ctx + api |
| 输出阻塞 | `MPP_SET_OUTPUT_TIMEOUT` 设成 `MPP_POLL_BLOCK`（:27-28） | 取输出时的等待方式：一直等 → `encode_get_packet` 会等到这一帧编完才返回。注释说要在 `mpp_init` 之前设 |
| 初始化成编码器 | `mpp_init(encoderCtx, MPP_CTX_ENC, config.codingType)`（:31） | 把实例定成“编码”类型、编码格式（这里 `MPP_VIDEO_CodingHEVC` = H.265） |
| 读默认配置 | `mpp_enc_cfg_init` + `MPP_ENC_GET_CFG`（:32-33） | 分配一份配置对象，再从编码器读出当前（默认）配置 → 只改我们关心的项，其余保持默认 |
| 写回配置 | `MPP_ENC_SET_CFG`（:67） | 把改好的配置交给编码器，前面的 `mpp_enc_cfg_set_s32` 到这里才生效 |

每一项参数用 `SET_CFG_S32(key, value)` 设置，它就是 `mpp_enc_cfg_set_s32` 加上失败检查（`encoder/mpp_encoder.cpp:9`）。key 分三组：`prep:*`、`rc:*`、`codec:*`（`h264:*`）。

### 4.2 MPP：prep —— 输入画面的样子（问题 2）

```cpp
// encoder/mpp_encoder.cpp:40-42
SET_CFG_S32("prep:hor_stride", horStride);
SET_CFG_S32("prep:ver_stride", verStride);
SET_CFG_S32("prep:format", MPP_FMT_YUV420SP);
```

- `prep:width / height`（:38-39）：画面的**有效**宽高，1920×1080。
- `prep:hor_stride`：字面意思是输入 buffer **一行占多少字节**；`prep:ver_stride`：**Y 平面占多少行**（`encoder/mpp_encoder.h:11-12`）。编码器靠这两个数在 buffer 里找到每一行、找到 UV 平面从哪开始（UV 起点 = hor_stride × ver_stride）。
- `prep:format = MPP_FMT_YUV420SP`：就是 NV12（Y 平面后面跟 UV 交错平面）。

**为什么 stride 要从大图上取**：大图 buffer 是拼图段按 1920×1088 分配、排布的（高度 1080 对齐到 16 是 1088，见 `app/m3_encode_mosaic.cpp:62` 的注释）。如果编码器以为 ver_stride 是 1080，它会在第 1920×1080 字节处找 UV，而实际的 UV 在 1920×1088 处 —— 推断结果是色度错位、画面底部或颜色发花。所以 `app/m3_encode_mosaic.cpp:65-68` 直接把大图的 `width / height / horStride / verStride` 抄给 `EncoderConfig`，不自己算。

`init` 里也有兜底：config 里 stride 填 0 时才用 `ALIGN(width, 16)`、`ALIGN(height, 16)` 算（`encoder/mpp_encoder.cpp:36-37`）。本例 1080 对齐后正好也是 1088，但**以 buffer 的实际排布为准**才是原则：以后输入换成别的来源（比如别的对齐方式），自己算就会错。

### 4.3 MPP：rc —— 码率控制

```cpp
// encoder/mpp_encoder.cpp:52-56
const int bpsMin = config.rcMode == MPP_ENC_RC_MODE_CBR ? config.bps * 15 / 16 : config.bps / 16;
SET_CFG_S32("rc:bps_target", config.bps);
SET_CFG_S32("rc:bps_max", config.bps * 17 / 16);
```

| key | 字面意思 | 这里的值和作用 |
|---|---|---|
| `rc:mode` | 码率控制模式 | `MPP_ENC_RC_MODE_CBR`（`app/m3_encode_mosaic.cpp:70`）= 固定码率：每秒输出的比特数尽量贴着目标值，画面复杂时降画质保码率。适合录像、转推这种要预估带宽和磁盘的场景 |
| `rc:bps_target` | 目标码率，单位 bit/s | `kMosaicBps` = 4 000 000（`app/app_config.h:43`） |
| `rc:bps_max / bps_min` | 码率允许浮动的上下限 | CBR 下是目标的 17/16 和 15/16，即 ±6.25%（:52-55）；VBR 时下限放宽到 1/16 |
| `rc:fps_in_* / fps_out_*` | 输入、输出帧率，用分子/分母表示；`flex = 0` 表示固定帧率 | 都是 30/1（:46-51）。码率控制靠帧率把“每秒多少比特”换算成“每帧多少比特” |
| `rc:gop` | 每隔多少帧一个 I 帧 | 60（`app/app_config.h:45`），30 fps 下 2 秒一个 I 帧。播放器拖动、中途接入都只能从 I 帧开始解 |

### 4.4 MPP：codec 和码流头

- `codec:type`（`encoder/mpp_encoder.cpp:59`）：编码格式，和 `mpp_init` 时一致。`h264:profile / cabac_*` 只在 H.264 时设置（:60-64）；H.265 的 profile、level 用默认值。
- **HEADER_MODE_EACH_IDR**（:68-69）：

```cpp
MppEncHeaderMode headerMode = MPP_ENC_HEADER_MODE_EACH_IDR;
MPP_CHECK(encoderApi->control(encoderCtx, MPP_ENC_SET_HEADER_MODE, &headerMode), false);
```

  字面意思：码流头（VPS/SPS/PPS）的输出方式 = 每个 IDR 帧（I 帧）前面都带一份。作用：播放器从中间任何一个 I 帧开始看都能解，转推直播、截取片段都需要。默认模式是只在开头给一次（推断，依据是这里特意改了它）。

- **取码流头 `getHeader`**（`encoder/mpp_encoder.cpp:79-89`）：

```cpp
// encoder/mpp_encoder.cpp:82, 85
MPP_CHECK(mpp_packet_init(&rawPacket, headerBuffer.data(), headerBuffer.size()), false);
MPP_CHECK(encoderApi->control(encoderCtx, MPP_ENC_GET_HDR_SYNC, packetPtr.get()), false);
```

  `MPP_ENC_GET_HDR_SYNC` 的字面意思是“同步取码流头”：我们准备一块 64 KB 内存（:80），用 `mpp_packet_init` 包成 MppPacket 交给它，它把头写进来；`mpp_packet_set_length(…, 0)`（:84）先把有效长度清零，让 MPP 从头写。取出来的头 H.264 是 SPS+PPS，H.265 是 VPS+SPS+PPS（`encoder/mpp_encoder.h:53`）。
  `EncodeStage::open` 把它写在文件最前面（`pipeline/encode_stage.cpp:26-31`）。头文件注释说：取了就必须写，MPP 认为头已经交给我们了，第一个 I 帧前面不会再带（`encoder/mpp_encoder.h:56`）。

### 4.5 MPP：送帧取包（问题 3）

`MppEncoder::encode`（`encoder/mpp_encoder.cpp:99`）是**同步的一送一取**：

| 步骤 | 代码 | 字面意思 → 作用 |
|---|---|---|
| 包成 MppFrame | `mpp_frame_init` + `mpp_frame_set_width/height/hor_stride/ver_stride/fmt`（:106-112） | MppFrame 是一个“画面描述”：只记 buffer 和宽高、stride、格式，**不复制像素** |
| 挂 buffer | `mpp_frame_set_buffer(framePtr.get(), isInputEos ? nullptr : frameBuffer)`（:114） | 把大图的 MppBuffer（dma-buf）挂上去，编码硬件直接读这块内存 |
| 送帧 | `encode_put_frame`（:117） | 把帧交给编码器；送完 MppFrame 就可以释放（:118 `framePtr.reset()`），注释说编码器内部对 buffer 加了引用 |
| 取包 | `encode_get_packet`（:122） | 取一个编好的包。因为 4.1 设了 `MPP_POLL_BLOCK`，这里会等到这一帧编完 |
| 读 I 帧标志 | `mpp_packet_get_meta` + `mpp_meta_get_s32(…, KEY_OUTPUT_INTRA, …)`（:134-135） | 包的附加信息里 `KEY_OUTPUT_INTRA` 非 0 = 这是 I 帧 |
| 复制数据 | `mpp_packet_get_pos` + `mpp_packet_get_length`（:130、:138-139） | 包数据的起点和长度，复制进 `std::vector`；函数返回时 `packetPtr` 析构，包还给编码器（:141） |

**大图只有一块 buffer，为什么不冲突**：`encode` 返回时，`encode_get_packet` 已经拿到了这一帧的包，说明编码硬件**已经读完**这块 buffer（`encoder/mpp_encoder.h:66` 的 `@note`）。主线程是单线程顺序执行“拼 → 编 → 拼 → 编”（`app/m3_encode_mosaic.cpp:21` 的 `@note`），下一张大图一定是在上一张编完之后才往同一块 buffer 上拼，所以不会出现“编码器还在读、RGA 已经在写”的情况。
代价是拼图和编码不能并行。要并行就得给大图准备 2 块以上 buffer 轮流用（推断，本里程碑不做）。

### 4.6 MPP：EOS 排空（问题 1）

```cpp
// pipeline/encode_stage.cpp:57-58, 64
for (int tryIndex = 0; tryIndex < kDrainTryCount; ++tryIndex) {
    if (!encoder.encode(nullptr, encodedPacket, true)) {
    ...
    if (encodedPacket.isEos) {
```

- **字面意思**：EOS = End Of Stream，流结束。送一个**不带画面**的帧（buffer 为 nullptr，`encoder/mpp_encoder.cpp:114`），只打上 `mpp_frame_set_eos(…, 1)`（:113）；然后一直取包，直到取到 `mpp_packet_get_eos` 为真的包（:127）。最多试 `kDrainTryCount` = 30 次（`pipeline/encode_stage.h:54`），试满了只打警告（`pipeline/encode_stage.cpp:68`）。
- **作用**：告诉编码器“后面没有帧了”，让它把内部压着的包全部吐出来写进文件，然后才能安全销毁。
- **不排空会少什么**：一般情况下，编码器内部可能压着已经送进去、还没输出的帧（例如开了 B 帧要重排、或者硬件流水线里还有帧），不排空直接 `mpp_destroy`，这些帧就丢了，文件末尾少几帧。
  本代码是同步一送一取，每次 `encode` 都等到这一帧的包出来，也没有配置 B 帧，**推断**实际可能一帧也不少，排空时只拿到一个空的 EOS 包。但是排空是编码器的标准收尾流程，写上它，以后改成异步、开 B 帧也不会丢帧。少不少，上板后对比 ffprobe 帧数和日志里的“编码 N 帧”确认（待上板实测）。
- 空包怎么处理：`encode` 取不到包或包长度为 0 时 `data` 为空（`encoder/mpp_encoder.cpp:123-125、131`），`writeBytes` 遇到空数据直接返回 true（`sink/stream_file_writer.cpp:32-34`）。

### 4.7 MPP：销毁顺序

`~MppEncoder`（`encoder/mpp_encoder.cpp:149-156`）先 `mpp_enc_cfg_deinit` 释放配置，再 `mpp_destroy` 销毁实例，和 `init` 的创建顺序反过来。

### 4.8 RGA

M3 没有新的 RGA 知识点，拼图沿用 M2（见 [m2流程.md](m2流程.md) 4.1）。和 M3 相关的只有一点：RGA 写的和编码器读的是**同一块 dma-buf**（大图的 `mppBuf`，`pipeline/encode_stage.cpp:41`），中间没有 CPU 拷贝。

### 4.9 Linux：写文件

| 代码 | 字面意思 → 作用 |
|---|---|
| `fopen(filePath, "wb")`（`sink/stream_file_writer.cpp:17`） | 只写、二进制打开；文件存在就清空 → 每次运行都重新生成 mosaic.h265，跑两次才能比 md5 |
| `fwrite(data.data(), 1, data.size(), filePtr.get())`（:35） | 返回实际写入的**元素个数**；元素大小写的 1，所以就是字节数。比要写的少就是出错（比如磁盘满），`strerror(errno)` 打印原因（:36） |
| `filePtr` | `FilePtr`（`unique_ptr` + `fclose` 删除器），对象析构时自动关文件，缓冲区里的数据也在 fclose 时写进磁盘 |

写入顺序：码流头（`encode_stage.cpp:31`）→ 每帧的包（:44）→ 排空时的包（:61）。H.265 裸流就是这些 NAL 单元首尾相接，不需要额外封装。

### 4.10 本篇重点（汇总三个问题）

1. **排空**：送“空帧 + EOS”，取到带 EOS 标志的包为止，让编码器把内部剩的包都吐出来；不排空可能丢掉文件末尾的几帧。本代码同步一送一取，推断不会丢，但这是标准收尾。
2. **stride 从大图取**：编码器按 hor_stride × ver_stride 找 UV 平面，必须和 buffer 实际排布（1920×1088）一致，否则推断会色度错位。
3. **一块 buffer 不冲突**：同步编码，`encode` 返回时硬件已读完；主线程顺序执行拼 → 编，下一张一定在上一张编完后才拼。

## 5. 业务场景：NVR 多画面合成录像 / 转推

NVR（网络录像机）常见需求：4 个摄像头的画面拼成一个“四分屏”，**只编一路码流**：

- **合成录像**：一路 4 Mbps 的文件代替 4 路各自的录像，回看时一眼看到 4 个位置。CBR 让每小时的磁盘占用可预估（4 Mbps ≈ 1.8 GB/小时，推断按 4e6 × 3600 ÷ 8 算）。
- **合成转推**：把四分屏推到 RTSP / RTMP 服务器给手机或监控中心看，带宽只占一路。这时 `HEADER_MODE_EACH_IDR` 和 2 秒一个 I 帧就很重要：观众随时接入，最多等 2 秒就能拿到“码流头 + I 帧”开始解。
- 本里程碑的输出是文件；把 `StreamFileWriter` 换成推流的 sink，编码段（`EncodeStage`）不用改 —— `encode_stage.h:11` 的 `@note` 说它不管画面从哪来，也不管码流写到哪是下一步的事。

## 7. 自己要敲的文件

### 7.1 `encoder/mpp_encoder.cpp`

按 `init → getHeader → encode → 析构` 的顺序敲，每个 API 敲完能说出它的字面意思：
