## 1. 做什么、为什么

**一句话**：不用 live555，自己写一个 RTSP 服务端，把 H.264 / H.265 码流（先是文件，后是摄像头实时编码）用 RTP over TCP（interleaved）发出去，ffplay / VLC / N2 的客户端都能看。板子就成了一台 IPC。

**为什么做**

| 对应 JD（`2_nvr_work/README.md` 第 5 节、`JD分析.md`） | N1 怎么对应 |
|---|---|
| RTSP/RTP（JD 1 原文 “RTSP/RTP、HLS、HTTP-FLV”） | 手写信令状态机、SDP、RTP 打包、FU-A / H.265 FU 分片 |
| 音视频采集、编解码、传输 | 摄像头 → MPP 编码 → RTP 发送，端到端延迟实测 |
| 多种传输协议对比（N11、N12） | N1 是“一深多浅”里手写的那个“深”，后面 RTMP、WebRTC 的延迟都和它比 |

**给后面谁用**：N2（客户端默认连 N1，板子上 `127.0.0.1:8554`）、N3（录像的输入来自 N2 收 N1 的流）、N5（4 个 N1 实例当 4 台 IPC）、N9 / N12（RTP 打包代码直接复用）。

### 4.3 线程模型和对象所有权

| 阶段 | 线程 | 所有权 |
|---|---|---|
| M1 | 主线程 accept；一次只服务一个连接，`RtspSession::runRequestLoop()` 在主线程里跑，连接断开后回去 accept | `RtspServer` 栈上；`RtspSession` 由 accept 循环创建，连接结束时析构（关 socket） |
| M2、M3 | 主线程 accept + 跑会话；收到 PLAY 时会话起一个**发送线程**（`StreamSender`）；会话线程继续读 socket（TEARDOWN、ffplay 30 秒一次的保活 OPTIONS、VLC 发来的 `$` RTCP） | `RtspSession` 拥有 `std::unique_ptr<StreamSender>`；TEARDOWN 或断开时先 `stop()` 再 `join()`，然后关 socket |
| M4 | 主线程 accept；**每个客户端一个会话线程 + 一个发送线程**；**一个源线程**（`StreamHub`，第一个客户端 PLAY 时启动，最后一个离开或文件结束时停） | `RtspServer` 拥有 `std::vector<std::unique_ptr<RtspSession>>`（加锁），定期回收已结束的会话；`StreamHub` 由 `RtspServer` 拥有；一帧编码结果用 `std::shared_ptr<const AccessUnit>` 在各客户端队列之间共享（只读，最后一个用完的释放） |

**同一个 socket 两个线程写**：会话线程写 RTSP 回复，发送线程写 interleaved RTP。两边都通过 `RtspSession::sendBytesLocked()`，用 `socketWriteMutex` 串起来，否则一条 RTSP 回复可能插进一个 `$` 帧中间，客户端拆包错位。

### 4.4 和 N2 共用的约定（N2 计划第 4.4 节是同一张表）

| 项目 | 约定 | 依据 |
|---|---|---|
| URL | `rtsp://<host>:8554/<streamName>`；文件源 `streamName` = 文件名（`aaa.264`、`out_720p.h265`），摄像头源 = `camera`；名字对不上回 `404 Not Found` | Claude 定（和 live555 按文件名点播的习惯一致） |

| Session | 8 位十六进制随机数；`Session: 1A2B3C4D;timeout=60` | RFC 2326 第 12.37 节；FFmpeg 默认 `rt->timeout = 60`（`rtsp.c` 第 1471 行） |
| Content-Base | DESCRIBE 回复带 `Content-Base: rtsp://<请求里的 host:port>/<streamName>/`，**用请求 URL 里的 host**，不写板子 IP | Claude 定；RFC 2326 第 C.1.1 节 |
| SDP | 会话级 `a=control:*`，媒体级 `a=control:track0`；SETUP 的 URL = Content-Base + `track0` | RFC 2326 附录 C.1.1 |
| H.264 SDP | `m=video 0 RTP/AVP 96`，`a=rtpmap:96 H264/90000`，`a=fmtp:96 packetization-mode=1;profile-level-id=<SPS 字节 1～3 的十六进制>;sprop-parameter-sets=<SPS base64>,<PPS base64>`（aaa.264 是 `42C028`） | RFC 6184 第 8.1 节；`42C028` 已核对 |
| H.265 SDP | `a=rtpmap:96 H265/90000`，`a=fmtp:96 sprop-vps=..;sprop-sps=..;sprop-pps=..` | RFC 7798 第 7.1 节；Day 5 `m3_RTSP 播放.md` 第 99～100 行 live555 实测样本 |

| 通道号 | 视频 RTP 走通道 0，RTCP 预留通道 1（N1 不发 RTCP）；收到客户端发来的 `$` 帧（任何通道）读完丢掉 | RFC 2326 第 10.12 节；ffplay 走 TCP 时不发 RR：FFmpeg 6.0 `rtsp.c` 第 2170～2190 行（只在 UDP 和 CUSTOM 分支调 `ff_rtp_check_and_send_back_rr`）；VLC 会不会发：**推断会发**，所以必须能丢 |

| 时间戳 | 90 kHz。文件源：每帧固定 +3000（按 30 fps 发，aaa.264 实际 29.97 fps，差别不影响播放）；摄像头源：用采集时刻（单调时钟，微秒 × 90 / 1000），相邻帧约 3000 但不精确 | RFC 6184 第 5.1 节、RFC 7798 第 4.1 节 |
| 打包 | H.264：NAL ≤ 1400 字节单 NAL 包，否则 FU-A（type 28）；H.265：单 NAL 包或 FU（type 49）。**不用** STAP-A / AP | RFC 6184 第 5.6、5.8 节；RFC 7798 第 4.4.1、4.4.3 节 |
| M 位 | 一帧（访问单元）的最后一个 RTP 包置 1 | RFC 6184 第 5.1 节；RFC 7798 第 4.1 节 |
| 参数集 | 文件源：文件里每个 IDR 前已有 SPS/PPS（aaa.264 已核对），照原样发；摄像头源：编码器开了 `EACH_IDR`，每个 IDR 前带 | 见第 2 节；Day 6 `mpp_encoder.cpp` 第 68 行 |
| 文件结束 | 文件源不循环时，发完最后一帧，服务端关掉这个客户端的连接（N2 据此在 M2/M3 结束统计）；`--loop` 时从头再来，时间戳继续递增 | Claude 定 |

### M1 RTSP 信令（第 03 周）

- **干了什么**：TCP 监听 8554，读一个以 `\r\n\r\n` 结尾的请求，解析请求行和头，按状态机回复 5 个方法；DESCRIBE 的 SDP 用文件开头的 SPS/PPS 生成。PLAY 后不发数据。
- **输入**：ffplay 的请求；板子上 `/userdata/av/aaa.264`（只读开头的 SPS/PPS）。
- **输出**：服务端日志打印每个请求和回复；ffplay 停在等数据。
- **新增文件**：`app/m1_signaling_only.*`、`rtsp/*`、`common/socket_utils.*`、`common/base64.*`、`common/file_utils.*`、`media/annexb_nal_splitter.*`、`media/parameter_sets.*`、`media/video_codec.h`、`pipeline/rtsp_server.*`。
- **关键接口**：

```cpp
enum class RtspMethod { Options, Describe, Setup, Play, Teardown, Unknown };
struct RtspRequest {
    RtspMethod method = RtspMethod::Unknown;
    std::string methodText;   // 原文，Unknown 时回 501 用
    std::string url;
    std::string version;      // "RTSP/1.0"
    int cseq = -1;            // 没有 CSeq 头时是 -1
    std::map<std::string, std::string> headers; // 头名统一转小写
    std::string findHeader(const std::string &lowerCaseName) const; // 没有返回空串
};
enum class RequestParseResult { Complete, NeedMoreData, Malformed };
RequestParseResult parseRtspRequest(const std::string &receivedText, RtspRequest &outputRequest, size_t &consumedBytes);

std::string buildRtspResponse(int statusCode, const char *reasonPhrase, int cseq,
                              const std::vector<std::pair<std::string, std::string>> &extraHeaders,
                              const std::string &body);   // body 非空时自动加 Content-Length

struct NalView { const uint8_t *data = nullptr; size_t sizeBytes = 0; };  // 指向内存里的一个 NAL（不带起始码），不拥有内存
void splitAnnexBNals(const uint8_t *streamData, size_t streamSizeBytes, std::vector<NalView> &outputNals);
struct ParameterSets { std::vector<uint8_t> vps, sps, pps; };  // 都不带起始码；H.264 时 vps 为空
struct StreamDescription { std::string streamName; VideoCodec codec; ParameterSets parameterSets; }; // DESCRIBE 要的全部信息
bool findParameterSets(VideoCodec codec, const uint8_t *streamData, size_t streamSizeBytes, ParameterSets &outputSets);
std::string buildSdp(VideoCodec codec, const ParameterSets &parameterSets, uint8_t payloadType);
std::string encodeBase64(const uint8_t *data, size_t sizeBytes);

enum class SessionState { Init, Ready, Playing, Closed };   // RFC 2326 附录 A.2 的服务端状态
class RtspSession {
public:
    RtspSession(int requestedSocketFd, const StreamDescription &requestedStream); // 接管 socket，析构时 close
    void runRequestLoop();             // 一直读、解析、回复，直到 TEARDOWN 或 recv 返回 0
private:
    bool handleRequest(const RtspRequest &request);  // false = 该断开了
    bool sendBytesLocked(const uint8_t *data, size_t sizeBytes);
    int socketFd; SessionState state = SessionState::Init; std::string sessionId;
    std::string receivedText; std::mutex socketWriteMutex;
```

### M2 RTP 打包（第 04 周）

- **干了什么**：PLAY 后起发送线程：把 aaa.264 切成 NAL → 按帧分组 → 每个 NAL 打成一个或多个 RTP 包 → 加 interleaved 头 → 按 30 fps 节流发出。
- **输入**：`/userdata/av/aaa.264`（整个读进内存，58 MB）。
- **输出**：ffplay 出画面；日志每 300 帧打印一次已发帧数、包数、FU-A 包数。
- **新增 / 修改**：`media/nal_unit.*`、`media/access_unit.*`、`rtp/*`、`common/frame_pacer.*`、`pipeline/stream_sender.*`、`app/m2_h264_file_stream.*`；`rtsp_session` 在 PLAY 时启动发送线程、TEARDOWN 时停掉。
- **关键接口**：

```cpp
// 分组规则：非 VCL NAL（SEI/SPS/PPS）先攒着，遇到 VCL NAL 就连同攒着的一起凑成一帧。
```

### M4 多客户端 + 抓包对照（第 06 周）

- **干了什么**：`StreamHub` 一个源线程读帧，`std::shared_ptr<const AccessUnit>` 推给每个订阅者的 `ClientFrameQueue`；每个客户端自己的发送线程从队列取、用**自己的** `RtpPacketizer`（独立 seq/SSRC/时间戳）打包发送；新订阅者和溢出后的订阅者都从下一个关键帧开始收。加故障注入开关；和 live555 抓包对照。
- **输入**：摄像头或文件（`--loop`）。
- **输出**：2 个 ffplay 同时看；差异表、故障注入记录写进 m4 文档。
- **新增 / 修改**：`pipeline/stream_hub.*`、`pipeline/client_frame_queue.*`、`app/m4_multi_client_stream.*`、`app/command_line.*`；`rtsp_server` 改成每个连接一个线程并回收已结束的会话；`StreamSender` 改成从 `ClientFrameQueue` 取。
- **关键接口**：

```cpp
class ClientFrameQueue {
public:
    explicit ClientFrameQueue(size_t requestedCapacityFrameCount);          // 默认 30 帧（约 1 秒）
    void pushOrDropUntilKeyFrame(std::shared_ptr<const AccessUnit> accessUnitPtr); // 满了：清空，丢到下一个关键帧；不阻塞源线程
    bool popWait(std::shared_ptr<const AccessUnit> &accessUnitPtr);         // false = 已 abort
    void abort();
    int getDroppedFrameCount() const;
};
class StreamHub {
public:
    explicit StreamHub(std::unique_ptr<AccessUnitSource> requestedSourcePtr);
    std::shared_ptr<ClientFrameQueue> subscribe();      // 第一个订阅者到来时启动源线程
    void unsubscribe(const std::shared_ptr<ClientFrameQueue> &queuePtr);  // 最后一个离开时停源线程
    const AccessUnitSource &getSource() const;
};
// 命令行开关（N2 计划第 5 节 M4 用的就是这几个名字）：--loop  --port N  --drop-every N  --initial-seq N
//   --timestamp-jump-at N  --corrupt-sdp-sps  --omit-fu-end-bit  --close-after-half-response
struct FaultInjectionConfig {                // 【Claude 写】故障注入，默认全关
    int dropEveryNthPacket = 0;              // 每 N 个 RTP 包少发 1 个，seq 照样 +1（N2 第 09 周用）
    int initialSequenceNumber = -1;          // ≥0 时固定初始 seq，例如 65500 测回绕
    int timestampJumpAtFrameIndex = -1;      // 到这一帧时间戳突然 +90000
    bool shouldCorruptSdpSps = false;        // SDP 里放一个和码流不一致的 SPS
    bool shouldOmitFuEndBit = false;         // FU-A 最后一片不置 E
    bool shouldCloseAfterHalfResponse = false; // 回复只发一半就断开（N2 第 09 周用）
};
```

## 6. 风险和还没验证的推断

| # | 风险 / 推断 | 怎么处理 |
|---|---|---|
| 1 | adb 只转发 TCP，所以 RTP 必须 interleaved；UDP 要等接网线（可选） | 已核对（README 第 3 节）；SETUP 收到 UDP 回 461 |
| 2 | ffplay 30 秒发一次保活 OPTIONS（FFmpeg 6.0 源码核对，Mac 上 4.4 是**推断**） | M2 验收第 4 条实测；会话线程在 PLAY 后继续收请求，所以不管发不发都能处理 |
| 3 | VLC 走 TCP 时会在通道 1 上发 RTCP RR：**推断** | 会话线程读到 `$` 就按长度读完丢掉；M4 用 VLC 试一次 |
| 4 | 两个线程写同一个 socket，回复插进 `$` 帧中间 | `socketWriteMutex`；故障注入可以作为一道题 |
| 5 | 客户端断开后 `send` 触发 SIGPIPE，整个进程退出 | `send(..., MSG_NOSIGNAL)`；第 06 周并行任务 F |
| 6 | 分组规则只对“一帧一个 slice”成立；out_720p.h265 和摄像头码流是不是一帧一个 slice：**推断是**（MPP 默认不切 slice） | M3 第 1 步打印每帧 VCL NAL 个数确认 |
| 7 | 在 Mac 的 `lo0` 能抓到 ffplay ↔ adb 的流量：**推断** | 第 03 周并行任务 E 实测 |
| 8 | 摄像头源的时间戳用 dequeue 时刻近似采集时刻（V4L2 buffer 自带的 timestamp 没用） | 够用线内；m3 文档写明 |
| 9 | 整个文件读进内存（58 MB）；板子内存够：**推断**（RK3588 板子至少 4 GB） | M2 上板时 `free -m` 看一眼 |
| 10 | `/userdata/av/out_720p.h265` 还在板子上：**推断** | M3 前 `adb shell ls -l /userdata/av/` |
| 11 | 端到端延迟 < 500 ms 能不能达到：**推断能**（ffplay 加 nobuffer） | M3 实测；达不到就记数字、写进问题案例库，不在 N1 里调编码参数（周计划“本周不学”） |
