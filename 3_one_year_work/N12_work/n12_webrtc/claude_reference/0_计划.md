## 2. 前置条件和环境

### 2.1 网络连通：结论

WebRTC 的媒体默认走 UDP（ICE 连通检查、DTLS 握手、SRTP 都在 UDP 上），adb 只能转发 TCP（README 第 3 节“硬件限制”，已核对）。几种办法对比：

| 方案 | 怎么连 | 要什么硬件 | 能不能做 M3 的延迟和丢包实验 | 结论 |
|---|---|---|---|---|
| **A 板子网线接家里路由器** | 板子和 Mac 在同一个局域网，双方的 host candidate 直接互通，不需要 STUN/TURN | 一根网线；路由器空一个 LAN 口 | 能 | **选定** |
| B 板子网线直连 Mac | 手动配静态 IP（或 macOS“互联网共享”） | 网线；Mac 没有网口时还要一个 USB/雷电转千兆网口 | 能 | A 没条件时的备选 |
| C 只用 USB：ICE-TCP + `adb forward` | libdatachannel 换 libnice 后端，打开 ICE-TCP，固定端口；`adb forward tcp:P tcp:P`；把 offer 里 TCP candidate 的地址改成 `127.0.0.1`，Chrome 作为 TCP 主动方连过来 | 不要新硬件 | **不能**：媒体走 TCP，丢包变重传，NACK/PLI 实验没意义，延迟也不可比 | 只当 M1、M2 的应急方案 |
| D TURN over TCP | Mac 上跑 coturn，板子经 `adb reverse` 用 TCP 连 TURN，TURN 在 Mac 本机用 UDP 转给 Chrome | 不要新硬件 | 不能（同 C，还多一跳） | 不用 |
| E USB 虚拟网卡 | 板子 USB 口同时模拟 adb + 网卡 | 不要新硬件 | 能 | 不用：板子的 rkscript 只提供 RNDIS 这一种网卡功能，macOS 没有自带 RNDIS 驱动 |

依据和推断：
- A、B：第 30 周计划已经写明“板子必须用网线接入局域网”，README 第 6 节网线状态 ☐。板子有没有千兆网口、网口在哪：**推断**有（ATK-DLRK3588 底板，未核对）。
- C：libdatachannel 的 `rtc::Configuration::enableIceTcp` 只在 libnice 后端有效，默认的 libjuice 不支持 ICE-TCP：**推断**（以选定版本 `include/rtc/configuration.hpp` 为准）。sysroot 里有 `libnice.so.10.13.1` 和 `libglib-2.0.so.0.7600.1`：已核对（`/Users/dev/rk-toolchain/atk-dlrk3588-toolchain/aarch64-buildroot-linux-gnu/sysroot/usr/lib`）。Chrome 能主动连 `tcptype passive` 的远端 candidate、接受 `127.0.0.1` 的远端 candidate：**推断**。
- D：libjuice 的 TURN 只支持 UDP：**推断**。
- E：已核对 `SDK/buildroot/package/rockchip/rkscript/rkscript.mk` 第 25～45 行（网卡相关的只有 `BR2_PACKAGE_RKSCRIPT_USB_RNDIS`）；macOS 不带 RNDIS 驱动：**推断**。

**选 A 以后，控制面仍然走 adb**（遵守根目录 `CLAUDE.md`：编译、push、运行、调试、信令都走 USB，不写死板子 IP）。只有媒体走局域网：ICE 自动收集板子 `eth0` 的地址写进 offer，不需要人去填 IP。M3 里 RTSP/RTMP 也要走局域网才公平，这时脚本用 `adb shell ip -4 addr show eth0` 在运行时取板子 IP、用 `ipconfig getifaddr en0` 取 Mac IP，不写死（这一点需要用户同意，见第 8 节）。

### 4.2 线程模型和所有权

- **libdatachannel 自己有线程**，`onLocalDescription`、`onStateChange`、PLI 回调都在它的线程里调用（**推断**，以文档为准）。所以回调里**不直接调 MPP**，只改原子变量或入队。
- **M1、M2**：单线程循环：`CameraAccessUnitSource::readNextAccessUnit` → `PtsAssigner` → `H264TrackSender::sendAccessUnit`（`track->send` 内部只是打包、加密、交给 socket 缓冲，不阻塞：**推断**）。
- **M3**：照 N11 M3，`runM3…` 持有 `StreamHub`；RTSP 会话、`RtmpPushWorker`、`WebRtcPushWorker` 各自 `subscribe()`，各有自己的线程和 `ClientFrameQueue`。
- **PLI → IDR**：编码器在 N1 的 `CameraAccessUnitSource` 里面（M3 时在 `StreamHub` 的源线程里跑）。PLI 回调（libdatachannel 线程）只调 `CameraAccessUnitSource::requestKeyFrame()`，它只做 `isKeyFrameRequested.store(true)`；源线程每次 `encode` 前检查，为 true 就调 `MppEncoder::requestIdrFrame()`（`MPP_ENC_SET_IDR_FRAME`，已核对 `rk_code/external/mpp/inc/rk_mpi_cmd.h` 第 133 行：下一帧编成 I 帧）。MPP 的 control 和 encode 在同一个线程调，不用考虑并发。M3 里摄像头源的 `unique_ptr` 交给 `StreamHub` 之前，先留一个裸指针 `CameraAccessUnitSource *cameraSource`，hub 活着它就有效。
- **所有权**：`runM2…` 持有 `std::unique_ptr<CameraAccessUnitSource> sourcePtr`、`std::unique_ptr<PeerSession> sessionPtr`。`PeerSession` 持有 libdatachannel 返回的 `std::shared_ptr<rtc::PeerConnection> peerConnectionPtr`、`std::shared_ptr<rtc::Track> videoTrackPtr`（库的 API 用 `shared_ptr`；按命名规范同样以 `Ptr` 结尾）。回调 lambda 不捕获 `shared_ptr`（否则循环引用，永远不释放），捕获 `this` 时要保证 `PeerSession` 析构前先 `peerConnectionPtr->close()` 并把回调清掉。
- 一次只服务一个浏览器（第 31 周计划“本周不学：多个浏览器同时观看”）。

### M1 信令 + 连通（第 30 周）

**干了什么**：板子当 offer 方：建 PeerConnection → 加一个 DataChannel（M1 还没有视频，至少要有一个 m-line 才能建连：**推断**；也可以直接加 `sendonly` 视频 track 不发数据）→ 等 ICE 收集完成 → 把完整 offer 打印成一行 JSON。用户粘到网页 → 网页 `setRemoteDescription`、`createAnswer`、等收集完成 → 显示一行 answer JSON → 粘回板子的 stdin。之后 ICE connected、DTLS 握手完成。

### M2 发视频（第 31 周）

**干了什么**：PeerSession 里加 H.264 视频 track（`sendonly`、PT 96、90 kHz），挂上打包器链；摄像头编码出来的每一帧（Annex-B）交给 track，libdatachannel 负责切 NAL、FU-A 分片、加 RTP 头、SRTP 加密。浏览器发 PLI 时让 MPP 下一帧出 IDR。

**输入**：摄像头 1080p30。**输出**：Chrome `<video>` 里的实时画面；webrtc-internals 的帧率、码率、丢包、`pliCount`、`nackCount`。

**新增 / 修改文件**：新增 `webrtc/h264_track_sender.*`、`app/m2_send_camera.*`；修改 `webrtc/peer_session.*`（加视频 track）、`encoder/mpp_encoder.*`（加 `requestIdrFrame`，N6 已有就不加）、`source/camera_access_unit_source.*`（加 `requestKeyFrame`）。

**关键接口**：

```cpp
class H264TrackSender {
public:
    bool attachToTrack(std::shared_ptr<rtc::Track> requestedTrackPtr, uint32_t ssrc,
                       std::function<void()> onKeyFrameRequested);  // PLI 到了就调这个回调
    bool sendAccessUnit(const AccessUnit &accessUnit, int64_t ptsUs); // appendNalUnitsAsAnnexB 拼成一帧交给 track；RTP 时间戳 = ptsUs × 90 / 1000（90 kHz）
};
bool MppEncoder::requestIdrFrame();                                 // mpi->control(ctx, MPP_ENC_SET_IDR_FRAME, nullptr)；只在编码线程调
void CameraAccessUnitSource::requestKeyFrame();                     // 任何线程都能调：只置原子标志，下一次 readNextAccessUnit 编码前生效
int runM2SendCamera();
```

`attachToTrack` 里要做的（libdatachannel 类名**推断**，第 31 周计划也写了“未核对”，以选定版本的头文件和 `examples/streamer` 为准）：
`rtc::RtpPacketizationConfig`（ssrc、cname、PT 96、时钟 90000）→ `rtc::H264RtpPacketizer`（分隔方式选“起始码”，因为 MPP 输出 Annex-B）→ 链上 `rtc::RtcpSrReporter`（发 SR）、`rtc::PliHandler`（收 PLI）、`rtc::RtcpNackResponder`（保留最近的包，收到 NACK 就重发）→ `track->setMediaHandler(...)`。

**SDP 里的 H.264 参数**：`a=rtpmap:96 H264/90000`、`a=fmtp:96 packetization-mode=1;profile-level-id=…;level-asymmetry-allowed=1`。Day 6 的编码器用的是 High profile（已核对 `mpp_encoder.cpp` 第 61 行 `h264:profile` = 100），所以 `profile-level-id` 不能照抄常见示例里的 `42e01f`（Constrained Baseline 3.1），而要用 SPS 的第 1～3 字节（profile_idc、约束标志、level_idc）拼成 6 位十六进制，从 `getParameterSets().sps` 现算（High、Level 4.0 时是 `640028`；MPP 默认 level 是多少：**推断** 4.0，以实际 SPS 为准）。Chrome 对 High 的协商结果：**推断**能用；不行就把编码器改成 Constrained Baseline（`h264:profile` = 66，关 CABAC），这正好是第 31 周任务 5 的实验。

期望：交换完 2 秒内网页出画面；webrtc-internals 里 `framesPerSecond` ≈ 30、`frameWidth` = 1920；刷新网页重新连接，第一帧画面 ≤ 1 秒出现（不等 GOP，因为浏览器一开始就发 PLI，板子日志能看到 `PLI → 请求 IDR`）。把 `onKeyFrameRequested` 注释掉再试一次：首帧要等到下一个自然 IDR（GOP 60 时最多约 2 秒）——这一组对比用来回答第 31 周第 3 题。Wireshark：`en0` 上过滤板子 IP，看到的是 DTLS 和 SRTP（`Decode As → RTP` 后能看到 RTP 头：V、PT、seq、timestamp、SSRC 明文，载荷加密），对照 N1 的 RTP 抓包。

**学完能回答的问题**：第 31 周计划的 4 题。

**自己敲 vs 复制**：Claude 写 `h264_track_sender`、`peer_session` 的视频部分；**建议用户自己敲** PLI → `isIdrRequested` → `requestIdrFrame` 这一段（和 MPP 直接相关，面试会问）。

### M3 三种协议同屏测延迟 + 弱网（第 32 周）

**干了什么**：一个进程，摄像头编码一次，`StreamHub` 同时分给 RTSP 服务端（N1）、RTMP 推流（N11，推到 Mac 的 mediaMTX）、WebRTC（M2）。三个播放窗口（ffplay RTSP、ffplay RTMP、Chrome WebRTC）和计时器页面排在 Mac 同一屏，一张截图读出三个延迟。然后开丢包看 NACK/PLI。

**链路**：三种协议**都走局域网**（RTSP：ffplay 连板子 IP:8554；RTMP：板子推到 Mac IP:1935；WebRTC：本来就走局域网）。USB 版（`adb forward`/`reverse`）的数字作为附加一列，不和局域网的混在一起比。

**新增文件**：`pipeline/webrtc_push_worker.*`、`app/m3_three_protocol_latency.*`；`run_on_board_with_mac.sh` 加运行时取 IP。

**延迟测法**：沿用 N11 M3（计时器页面 + 截图，每种协议 5 次取平均，单次误差约 ±50 ms，推断）。测量条件写进报告：1080p30、N6 推荐的码率和 GOP、无 B 帧、ffplay 参数 `-fflags nobuffer -flags low_delay -framedrop`、Chrome 默认（WebRTC 的接收端抖动缓冲由浏览器自己调）。

**期望**（全部**推断**，第 32 周开始前 Claude 先 probe 一次）：

| 协议 | 预计 | 主要差在哪 |
|---|---|---|
| WebRTC | 100～250 ms | UDP、浏览器抖动缓冲很小 |
| RTSP over TCP（ffplay nobuffer） | 150～350 ms | 直连，没有服务器转发 |
| RTMP（经 mediaMTX，ffplay nobuffer） | 200～500 ms | 多一次服务器转发 |

三者可能只差几十到一两百毫秒。能明显拉开的是**弱网**：

**弱网**：Mac 上 Network Link Conditioner 设下行丢包 1%、5%（5% 看不出变化就加到 10%，先 probe）。观察：
- WebRTC：`nackCount`、`retransmittedPacketsReceived`（推断字段名）上涨，偶尔 `pliCount` +1，画面偶有花屏或短暂卡住后恢复，延迟基本不变。
- RTSP over TCP：丢包被 TCP 重传掩盖，不花屏，但延迟逐渐累积（每张截图比上一张大），停止丢包后也不一定回落。
- 这一组对比就是第 32 周第 2、3 题的答案。

**验收**：

```bash

BUILD_DIR=build ./run_on_board_with_mac.sh m3              # 板子；打印 板子 IP、三种输出的状态
ffplay -fflags nobuffer -flags low_delay -framedrop -rtsp_transport tcp rtsp://<脚本打印的板子IP>:8554/live
```

产出：`n12_webrtc/doc/传输协议延迟对比报告.md`（用户写）：三种协议各 5 次延迟 + 测量条件 + 丢包 0/1/5% 下的观察 + webrtc-internals 截图；能回答第 32 周 4 题。

## 6. 风险和还没验证的推断

| 风险 | 影响 | 怎么确认 / 退路 |
|---|---|---|
| 网线 / 路由器口没准备好 | M1 起全部卡住 | **第 29 周就要确认**（见第 8 节）；临时用方案 C 做 M1、M2，M3 必须等网线 |
| 路由器开了“AP 隔离”，有线和无线之间不通 | Mac（Wi-Fi）连不上板子 | 先 `ping` 板子 IP；不通就让 Mac 也插网线或换方案 B |
| libdatachannel 新版本要求 OpenSSL 3 | M0 编不过 | 退版本，或 `USE_MBEDTLS`（sysroot 里有没有 mbedtls：未核对） |
| libdatachannel 的 API 名字和本计划不一致 | 代码要改 | 以选定 tag 的 `include/rtc/*.hpp` 和 `examples/streamer` 为准，第 30 周前 Claude 对一遍 |
| Chrome 不接受 High profile 的 `profile-level-id` | 不出画面 | 改成 Constrained Baseline 编码（M2 的实验） |
| 板子 IP 会变（`CLAUDE.md` 记录过 .196 变 .197） | M3 的命令要改 | 脚本运行时取 IP，不写死；WebRTC 本身不受影响（ICE 每次重新收集） |
| 三种协议延迟差距落在误差里 | 报告结论模糊 | 先 probe；弱网对比保证有明显现象 |
| Network Link Conditioner 对 Mac 和板子之间的流量不生效 | 丢包实验做不了 | 先用 `ping` 看丢包率；不行就在 Chrome 端用 webrtc-internals 记录自然丢包，或在板子发送端代码里按比例丢 RTP 包（测试用开关） |

## 8. 和周计划、README 不一致的地方

1. **阶段顺序**：README 第 3 节“做的顺序”是 N11 → N7（可选）→ N12；周计划是 N11（第 28～29 周）→ **N12（第 30～32 周）→ N7（第 33～34 周）**，第 33 周计划也写了“第 30 周起板子已经接入局域网”。本计划按周计划：N12 不依赖 N7 的任何代码。README 第 3 节建议改成和周计划一致（本计划不改 README）。
2. **网线要提前到第 29 周确认**：第 30 周计划把“板子能拿到 IP，Mac 能 ping 通”放在本周开始前；网线、路由器空口要买或要挪的话，第 29 周就要定，否则第 30 周整周卡住。
3. **M0 不在周计划里**：libdatachannel 交叉编译在第 30 周计划里只写了“Claude 在本周之前先编好”。本计划把它列成 M0，产物放进第 30 周目录的 `tools/`。
4. **M3 三种协议都走局域网**：周计划没说 RTSP、RTMP 走 USB 还是局域网。为了公平，本计划要求都走局域网，这需要在 Mac 上的播放命令里用板子 IP（运行时取，不写死）。这和 `CLAUDE.md`“不要用板子 IP”的约定有张力（那条约定是针对运行和调试的）——**需要用户同意**。
5. **弱网工具**：第 32 周计划写“板子上 `tc netem`（要内核支持，未核对）”；本次 grep `alientek_rk3588_defconfig` 没有 `NET_SCH_NETEM`，推断板子不能用，主选 Mac 的 Network Link Conditioner。
6. **WebSocket 信令的实现**：第 30 周任务 6 说“极简 WebSocket 信令服务”；本计划用 libdatachannel 自带的 `rtc::WebSocketServer`（推断类名）放在板子上，不另起 Node/Python 服务，经 `adb forward tcp:8000` 访问。
