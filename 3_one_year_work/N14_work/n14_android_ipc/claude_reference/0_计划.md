## 1. 做什么、为什么做

**一句话**：一台 Android 手机当作 NVR 的一路摄像头：Camera2 把画面直接送进 MediaCodec 的输入 Surface 硬件编码成 H.264，码流一路存 `.h264` / MP4，一路用 RTMP 推到 Mac 上的 mediaMTX，NVR（板子上的 N2/N5）从 mediaMTX 拉 RTSP 接进来；最后用 MediaExtractor + MediaCodec 把录的 MP4 读回来解码、seek。

**为什么做**：Android 底层多媒体 2 份 JD（J11、J14，`JD分析.md` 第 2 节 + 结论 6，已核对）。用户是 Android 工程师出身，这一阶段把"Android 多媒体 API ↔ RK MPP / FFmpeg"对上号，面试能讲"两个平台的硬编"。

**一深多浅里的位置**：编码这条能力，"深"是 MPP 硬编（Day 1～6），MediaCodec 是"浅"（README 第 2 节原则 6 表，已核对）。所以重点是**对照**：接口设计、buffer 队列、码流格式、码控、封装。

**代码由谁写**：周计划写"按 C 方案 N14 由 Claude 写；你原来就做 Android 开发，想自己写也可以，开始前定"（C 方案用户还没确认）。本计划按 **Claude 写参考工程（Kotlin）、用户读懂 + 跑通 + 测数据**排，第 5 节仍标出"值得自己敲"的文件。**需要用户决定**。

### 4.2 线程和所有权

| 线程 | 做什么 |
|---|---|
| 主线程 | UI、生命周期、按钮 |
| `HandlerThread("camera")` | Camera2 的状态回调和会话回调 |
| `HandlerThread("encoder")` | `MediaCodec.Callback`（`setCallback(callback, handler)`）：`onOutputBufferAvailable` 里把 `ByteBuffer` 拷成 `ByteArray`、立刻 `releaseOutputBuffer`，再交给 fan-out；文件 sink 直接在这个线程写 |
| RootEncoder 内部线程 | RTMP 握手、发送（库自己管，**推断**） |
| `HandlerThread("player")` | M3 回放：解码器回调 + `MediaExtractor` 读样本 |

所有权：`MainActivity` 持有 `CameraController`、`H264SurfaceEncoder`、`EncodedFrameFanOut`；`onResume` 里按 编码器 → 相机 的顺序创建（相机要编码器的输入 Surface），`onPause` 里按 相机 → 编码器 → sink 的顺序释放。切后台就释放（周计划第 42 周问题 3：NVR 那边会看到断流，回前台重新推，M2 实测）。不做前台 Service（第 42 周"本周不学"没列，但超出够用线，见第 8 节）。

## 5. 里程碑

### M1：采集 + 硬编，存 `.h264`（第 41 周）

- **干了什么**：`MediaFormat.createVideoFormat("video/avc", 1920, 1080)`，设 `KEY_COLOR_FORMAT = COLOR_FormatSurface`、`KEY_BIT_RATE`、`KEY_FRAME_RATE = 30`、`KEY_I_FRAME_INTERVAL = 1`（秒）、`KEY_BITRATE_MODE`；`configure(..., CONFIGURE_FLAG_ENCODE)` → `createInputSurface()` → `start()`；Camera2 会话的输出目标 = 预览 Surface + 编码器 Surface；输出回调里：`BUFFER_FLAG_CODEC_CONFIG` 的 buffer（SPS/PPS）也写进文件开头，`BUFFER_FLAG_KEY_FRAME` 标关键帧；停止时 `signalEndOfInputStream()` 等到 `BUFFER_FLAG_END_OF_STREAM` 再 release（和 MPP 编码器排空对照）。
- **输入**：后置摄像头。**输出**：手机 `getExternalFilesDir()/n14_m1.h264`；对照表 `doc/MediaCodec和MPP编码接口对照.md`；CBR / VBR 码率表。
- **关键接口**：
  ```kotlin
  data class EncoderConfig(val width: Int, val height: Int, val bitRateBps: Int, val frameRate: Int,
                           val iFrameIntervalSeconds: Int, val bitrateMode: Int)
  data class EncodedFrame(val data: ByteArray, val presentationTimeUs: Long, val isKeyFrame: Boolean, val isCodecConfig: Boolean)
  interface EncodedFrameSink { fun onOutputFormat(format: MediaFormat); fun onEncodedFrame(frame: EncodedFrame); fun close() }
  class H264SurfaceEncoder(private val config: EncoderConfig, private val sink: EncodedFrameSink, private val callbackHandler: Handler) {
      val inputSurface: Surface                      // start() 之后才有效
      fun start()
      fun requestKeyFrame()                          // setParameters(PARAMETER_KEY_REQUEST_SYNC_FRAME)；M2 推流开始时用
      fun stopAndDrain()
  }
  class CameraController(private val context: Context, private val cameraHandler: Handler) {
      fun open(cameraId: String, outputSurfaces: List<Surface>, onSessionReady: () -> Unit)
      fun close()
  }
  class AnnexBFileSink(outputFile: File) : EncodedFrameSink
  ```
- **验收**：
  ```bash
  adb -s <手机序列号> pull /sdcard/Android/data/com.tone.n14ipc/files/n14_m1.h264 .
  ffprobe -v error -count_frames -show_entries stream=codec_name,profile,width,height,r_frame_rate,nb_read_frames n14_m1.h264
  # 期望：h264，1920x1080；录 30 秒 → nb_read_frames ≈ 900；ffplay 能播
  xxd n14_m1.h264 | head -2   # 回答"Annex-B 还是 AVCC"：开头是 00 00 00 01 67 就是 Annex-B（推断是 Annex-B，以实测为准）
  ffprobe -v error -show_frames -select_streams v -show_entries frame=pict_type,pkt_size -of csv n14_m1.h264 > frames.csv  # 看 I 帧间隔、码率
  ```
  CBR / VBR 各录 30 秒，表里写设定码率、实际平均码率、最大 1 秒码率（第 41 周任务 7）。手机不支持某个模式时（`EncoderCapabilities.isBitrateModeSupported` 返回 false），表里如实写"不支持"。
- **学完能回答**：第 41 周问题 1～5。问题 5 的方向：`KEY_I_FRAME_INTERVAL` 单位是秒，MPP 的 `rc:gop` 单位是帧，30 fps 时 1 秒 = gop 30。
- **值得自己敲**：`H264SurfaceEncoder.kt`（buffer 队列、三个 flag）；样板：`CameraController`（老本行）、`MainActivity`、Gradle。

### M2：推流，接进 NVR（第 42 周）

- **方案**：选周计划的**方案 1**：手机 RTMP → Mac mediaMTX → 板子 N2 拉 RTSP。理由：N11 第 28 周已经用过 mediaMTX；方案 2（N1 用 NDK 编到手机上）对 Android 多媒体 API 没有新东西，留作可选。
- **干了什么**：
  1. `RtmpPushSink`：`onOutputFormat` 时从 `csd-0` / `csd-1` 拿 SPS / PPS 交给 RTMP 客户端（它据此发 AVC sequence header）；`onEncodedFrame` 把非 config 帧交给它（**推断** RootEncoder 的 `RtmpClient` 有"设 SPS/PPS + 送已编码帧"的入口，第一步先读它的源码确认；不行就换 FFmpeg 的 Android 构建，周计划已留这个选项）。
  2. 时间戳：FLV 用毫秒，`flvTimestampMs = (presentationTimeUs - firstPresentationTimeUs) / 1000`；RTP 90 kHz：`rtpTimestamp = (presentationTimeUs - firstPresentationTimeUs) * 90 / 1000`（mediaMTX 转 RTSP 时做，第 42 周问题 2）。
  3. 推流开始时 `requestKeyFrame()`，让 NVR 不用等满一个 GOP。
  4. VLC 拉 `rtsp://<Mac IP>:8554/phone`；N5 配置里换一路成这个地址。
  5. 异常：切后台、锁屏、关 Wi-Fi 再开；记录手机端和 NVR 端现象，NVR 靠 N2 的断线重连恢复。
  6. 延迟：手机拍秒表，板子屏幕和秒表同框拍照，记 5 次取中位数。
- **关键接口**：
  ```kotlin
  class RtmpPushSink(private val rtmpUrl: String) : EncodedFrameSink {
      fun connect()                       // 异步；连接结果走回调打日志
      val isConnected: Boolean
  }
  class EncodedFrameFanOut(private val sinks: List<EncodedFrameSink>) : EncodedFrameSink
  ```
- **验收**（周计划验收）：
  ```bash
  ffprobe -v error -rtsp_transport tcp -show_entries stream=codec_name,width,height rtsp://<Mac IP>:8554/phone   # h264 1920x1080
  ```
  - NVR 预览里手机画面连续 10 分钟不断流；N3 录像里这一路正常。
  - 手机 Wi-Fi 断开再连上（App 在前台），NVR 能自动恢复出画面。
  - 一份延迟数据，和第 32 周的协议延迟对比报告放在一起。
- **学完能回答**：第 42 周问题 1～4。
- **值得自己敲**：`RtmpPushSink.kt` 的时间戳换算和 csd 处理；样板：库的接入、fan-out。

### M3：MediaMuxer 录像 + MediaExtractor 回放（第 43 周）

- **干了什么**：
  1. `Mp4MuxerSink`：`onOutputFormat` 时 `addTrack(编码器输出的 MediaFormat)` → `start()`；之后每帧 `writeSampleData`（`BufferInfo.flags` 带关键帧标志）；config 帧不写（csd 已经在 format 里，会变成 MP4 的 `avcC`）；`stop()` / `release()`。
  2. 用 E 线的 MP4 box 遍历器看结构（moov 在前还是在后，avcC 内容），和 N3 的 MP4 对照；录到一半 `adb shell am force-stop` 杀进程，看文件能不能播（MediaMuxer 写的是普通 MP4，moov 在 `stop()` 时才写，**推断**播不了；N3 用 fMP4 解决）。
  3. `Mp4Player`：`MediaExtractor.setDataSource` → 选视频轨 → 用轨道 format 建解码器，输出到 SurfaceView → `readSampleData` / `advance` 喂解码器 → 按 PTS 节流显示；拖动时 `seekTo(positionUs, SEEK_TO_PREVIOUS_SYNC)` + `codec.flush()`。
  4. 总结表：Android 的 Camera2 / MediaCodec / MediaMuxer / MediaExtractor / Surface ↔ V4L2 / MPP / libavformat 写 / libavformat 读 / RGA+DRM（第 43 周任务 5）。
  5. 故障注入：录像中被杀；编码器抛 `MediaCodec.CodecException`（例如故意配一个手机不支持的分辨率）；相机被别的 App 抢占（`CameraDevice.StateCallback.onDisconnected` / `onError`）。三种都不崩溃，有提示。
- **关键接口**：
  ```kotlin
  class Mp4MuxerSink(private val outputFile: File) : EncodedFrameSink
  class Mp4Player(private val outputSurface: Surface, private val playerHandler: Handler) {
      fun open(inputFile: File): Long        // 返回时长（微秒）
      fun play()
      fun pause()
      fun seekTo(positionUs: Long)           // 落到前一个关键帧
      fun release()
  }
  ```
- **验收**（周计划验收）：
  ```bash
  ffprobe -v error -show_entries format=duration:stream=codec_name,width,height,nb_frames n14_m3.mp4   # 时长 ≈ 录制时长
  ffprobe -v error -select_streams v -show_entries packet=pts_time,flags -of csv n14_m3.mp4 | head    # PTS 是否均匀（E 线任务）
  ```
  手机和 Mac 上都能播、能拖动；三种故障都有处理，App 不崩溃。
- **学完能回答**：第 43 周问题 1～4。
- **值得自己敲**：`Mp4MuxerSink.kt`、`Mp4Player.kt` 的 seek 部分；样板：UI、文件选择。

## 6. 风险和还没验证的推断

1. **RootEncoder 能不能只当 RTMP 客户端用**（送外部编好的帧）：推断可以，M2 第一步读源码确认；不行的备选：FFmpeg 的 Android 构建（要自己编或找现成的 aar，周计划已标"未核对各库现状"）。
2. **手机编码器的码控支持**：有的机型只支持 VBR，或 CBR 实际也在飘；表里如实写。
3. **mediaMTX 默认端口和路径规则**：推断 1935 / 8554、路径 = 推流时的 stream key；以第 28 周 N11 的实际配置为准。
4. **N2 能不能直接拉 mediaMTX 转出来的 RTSP**：mediaMTX 的 SDP 可能带 N2 没处理过的字段（例如 `a=control` 用绝对地址），假设 N2 能处理，M2 实测。
5. **Annex-B / csd 的格式**：推断 MediaCodec AVC 编码器输出 Annex-B、`csd-0` = 带起始码的 SPS、`csd-1` = 带起始码的 PPS；M1 用 xxd 实测确认（第 41 周问题 4 本来就要求实测回答）。
6. **两台 adb 设备同时在线**：板子的运行脚本不带 `ADB_SERIAL` 时会报"more than one device"，第 42 周开始前在笔记里写好两条命令。
