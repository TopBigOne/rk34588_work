## 1. 做什么、为什么

**一句话**：板子上起一个极简 HTTP 服务，把同一路 H.264 同时输出成 HTTP-FLV（低延迟，flv.js 播）和 HLS（TS 分片 + m3u8，Safari/hls.js/手机播），并把两者加进 N11、N12 的延迟对比表。

**为什么做**：

| 对应 JD | 说明 |
|---|---|
| J10（HLS，1 份）；HTTP-FLV 0 份（`2_nvr_work/JD分析.md` 第 2 节） | 需求少，所以可选 |
| JD 1“RTSP/RTP、HLS、HTTP-FLV”“延迟、卡顿”（README 第 5 节） | 补齐“浏览器、手机怎么看 NVR”这一环；延迟表加两行 |
| J04、J09 的“MP4/TS 封装” | 手写过 TS 封装原理（TS 解包器是用户的并行任务），第 36～37 周 GB28181 的 PS 封装和它很像 |

### 4.2 线程模型和所有权

- 采集编码线程（主线程）：`readNextAccessUnit` → `PtsAssigner` → `AccessUnitFanout::publish`（帧用 `std::shared_ptr<const TimedAccessUnit>` 共用一份）。订阅者：`HlsSegmenter::writeAccessUnit`（直接写 `/tmp`，很快）和 `HttpFlvHub::publish`（把帧放进每个会话自己的 `AccessUnitQueue`）。
- HTTP 监听线程：`accept` → 每个连接起一个线程，读请求行 → 按路径分发：`/live.flv` 交给 `HttpFlvSession`（循环 `pop` 队列 → 写 chunk，直到客户端断开）；`/hls/*.m3u8`、`/hls/*.ts`、`/*.html` 读文件发出去（`Content-Length`，发完关连接）。
- 慢客户端：会话队列满 → 丢到下一个关键帧（`AccessUnitQueue` 已有的策略），不拖慢编码线程和其他客户端。
- 所有权：`runM3…` 持有 `std::unique_ptr<CameraAccessUnitSource> sourcePtr`、`std::unique_ptr<HttpServer> serverPtr`、`std::unique_ptr<HlsSegmenter> segmenterPtr`、`HttpFlvHub`；每个 `HttpFlvSession` 由它的连接线程持有，线程结束时从 hub 里注销。退出：停采集 → hub 里所有队列 `abort()` → `serverPtr->stop()`（关监听 socket，join 所有连接线程）。

## 5. 各里程碑

### M1 FLV 文件（第 33 周）

**干了什么**：摄像头（或 `/userdata/av/main_1080p.h264`）的码流 → FLV 文件头 → AVC sequence header tag → 每帧一个 video tag → `/userdata/av/n7_m1.flv`，拉到 Mac 用 ffplay 播。

**格式要点**：
- FLV 头 9 字节：`"FLV"`、版本 1、标志（视频 0x01、音频 0x04）、头长度 9（4 字节大端）；后面紧跟 4 字节的 PreviousTagSize0 = 0。已核对（`FFmpeg-6.0/libavformat/flvenc.c` 第 707～711 行；`flv.h` 第 55～56 行）。
- tag：类型 1 字节（视频 0x09，`flv.h` 第 61 行）+ 数据长度 3 字节 + 时间戳 3 字节 + 时间戳扩展 1 字节 + stream id 3 字节（=0），共 11 字节；数据之后写 4 字节 PreviousTagSize = 11 + 数据长度。字段顺序：**推断**（按 FLV 规范，写代码时对照 `flvenc.c` 的 `flv_write_packet`）。
- video tag 的数据部分和 RTMP video 消息完全一样（N11 计划 M2 的表）：`0x17`/`0x27` + AVCPacketType + CTS + AVCC 数据。

**关键接口**（`mux/` 的签名见 N11 计划第 5 节 M2，原样复用）：

```cpp
class FlvFileWriter {
public:
    bool open(const char *filePath);                                 // 写 FLV 头 + PreviousTagSize0
    bool writeSequenceHeader(const ParameterSets &parameterSets);
    bool writeAccessUnit(const TimedAccessUnit &timedUnit);         // tag 时间戳 = ptsUs / 1000（毫秒）
    void close();
private:
    FilePtr filePtr;
};
int runM1WriteFlvFile();
```

**验收**：

```bash

adb pull /userdata/av/n7_m1.flv /tmp/n7_m1.flv
ffprobe -v error -count_frames -show_entries stream=codec_name,width,height,nb_read_frames /tmp/n7_m1.flv
ffprobe -v error -show_entries packet=pts_time,flags -of csv /tmp/n7_m1.flv | head
ffmpeg -v error -i /tmp/n7_m1.flv -f null -
```

期望：`h264`、1920×1080、`nb_read_frames=300`；pts 从 0 开始，每帧 +0.033；第一个包 `flags` 带 `K`；`ffmpeg -f null` 没有输出。

### M2 HTTP-FLV（第 33 周）

**干了什么**：板子 8080 端口的极简 HTTP 服务。`GET /live.flv` → 回 `HTTP/1.1 200 OK`、`Content-Type: video/x-flv`、`Transfer-Encoding: chunked` → 先发 FLV 头 + sequence header，**等到下一个关键帧**再开始发视频 tag（新客户端从 P 帧开始解不出来），时间戳按这个客户端的第一帧归零 → 之后每个 tag 作为一个 chunk：`<十六进制长度>\r\n<数据>\r\n`。

chunked 格式的依据：RFC 9112 第 7.1 节（第 33 周计划资料里列了，本次**未打开核对**）。

**关键接口**：

```cpp
class HttpServer {
public:
    using RequestHandler = std::function<void(const HttpRequest &request, TcpSocket &clientSocket)>;
    void addRoute(const std::string &pathPrefix, RequestHandler handler);
    bool start(int listenPort);                 // 起监听线程
    void stop();
};
bool sendHttpResponseHeader(TcpSocket &clientSocket, int statusCode, const char *contentType,
                            bool isChunked, int64_t contentLengthBytes); // isChunked = true 时忽略长度
bool sendHttpChunk(TcpSocket &clientSocket, const uint8_t *data, size_t sizeBytes);
class HttpFlvSession {
public:
    void runUntilDisconnected(TcpSocket &clientSocket, AccessUnitQueue &sessionQueue,
                              const ParameterSets &parameterSets); // 时间戳按本会话第一帧归零
};
class HttpFlvHub {
public:
    AccessUnitQueue *registerSession();        // 返回这个会话的队列（hub 持有）
    void unregisterSession(AccessUnitQueue *sessionQueue);
    void publish(const SharedTimedAccessUnit &timedUnitPtr);
};
int runM2HttpFlvLive();
```

**验收**：

```bash

curl -sv http://localhost:8080/live.flv -o /tmp/live.flv --max-time 5   # 头里有 Transfer-Encoding: chunked
xxd /tmp/live.flv | head -2                                              # 以 46 4c 56 01 01 00 00 00 09 开头
ffplay -fflags nobuffer http://localhost:8080/live.flv
# Chrome 打开 http://localhost:8080/flv_player.html
```

期望：curl 拿到的文件 ffprobe 能识别为 h264；Chrome 里出画面；延迟用 N11 的计时器测 5 次。预计 flv.js 关 stash 时 0.3～1 秒（**推断**，先 probe）。开 3 个标签同时看，记录板子 `top` 里本进程的 CPU（编码只做一次，每多一个客户端只多一份发送）。

### M3 HLS（第 34 周）

**干了什么**：同一路码流再交给 `HlsSegmenter`：每帧封成 TS 写进当前分片；遇到关键帧且当前分片时长 ≥ 目标时长 → 关掉当前分片、更新 m3u8、删掉窗口外的旧分片、开新分片。HTTP 服务把 `/tmp/n7_hls/` 发出去。HTTP-FLV 同时照常输出。

**TS 要点**：

| 内容 | 要点 | 依据 |
|---|---|---|
| 包 | 每包 188 字节，第一个字节 `0x47` | 已核对（`mpegts.h` 第 29 行，`mpegtsenc.c` 第 163 行） |
| PID | PAT 固定 PID 0；PMT 和视频的 PID 自己定，照 FFmpeg 默认用 PMT 0x1000、视频 0x0100 | FFmpeg 默认值已核对（`mpegtsenc.c` 第 2301、2303 行）；PAT = 0 是标准规定，**推断**（未打开 ISO 13818-1） |
| stream_type | H.264 = 0x1b（H.265 = 0x24） | 已核对（`mpegts.h` 第 129～130 行） |
| PES | stream_id 0xE0；PTS 33 位、90 kHz；没有 B 帧所以 DTS = PTS 可以不写；视频 PES 长度可以填 0 | **推断**（写代码时对照 `mpegtsenc.c` 的 `mpegts_write_pes`） |
| PCR | 放在视频 PID 的 adaptation field 里，27 MHz（= 90 kHz × 300 + 扩展） | **推断** |
| 其他 | 每个分片开头都写 PAT、PMT（每个分片能单独解）；每帧前面没有 AUD 就补一个（FFmpeg 也这么做）；continuity_counter 每个 PID 各自 4 位循环；最后一个包用 adaptation field 填充到 188 | AUD：FFmpeg 的做法已核对（`mpegtsenc.c` 第 1884～1913 行附近 `found_aud`）；其余**推断** |

**m3u8**（滚动窗口，不写 `#EXT-X-ENDLIST`）：

```
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:2
#EXT-X-MEDIA-SEQUENCE:17
#EXTINF:2.000,
seg17.ts
#EXTINF:2.000,
seg18.ts
#EXTINF:2.000,
seg19.ts
```

标签名已核对（`FFmpeg-6.0/libavformat/hlsplaylist.c` 第 36、106～109、193 行）；`TARGETDURATION` 要 ≥ 每个 `EXTINF` 四舍五入后的值：**推断**（RFC 8216 第 4.3.3.1 节，未打开核对）。**m3u8 先写临时文件再 `rename`**（`rename` 在同一个文件系统里是原子的），否则播放器可能读到写了一半的列表。

**关键接口**：

```cpp
uint32_t computeCrc32Mpeg2(const uint8_t *data, size_t sizeBytes);
class TsMuxer {
public:
    void writePatAndPmt(std::vector<uint8_t> &tsBytes);                       // 追加 2 个 188 字节包
    void writeVideoAccessUnit(const AccessUnit &accessUnit, int64_t pts90kHz, bool shouldWritePcr,
                         std::vector<uint8_t> &tsBytes);                      // 追加若干 188 字节包
};
class HlsSegmenter {
public:
    bool open(const char *outputDirectory, int requestedTargetDurationMs, int requestedWindowSegmentCount);
    bool writeAccessUnit(const TimedAccessUnit &timedUnit); // 关键帧且时长够了就切新分片；关键帧前补 SPS/PPS
    void close();
private:
    bool finishCurrentSegment();                  // 关文件、更新 m3u8、删旧分片
    bool rewritePlaylist();                       // 写 live.m3u8.tmp → rename
};
int runM3HttpFlvAndHls();
```

## 6. 风险和还没验证的推断

| 风险 | 影响 | 退路 |
|---|---|---|
| N6 推荐的 GOP 是 2 秒或更长 | 1 秒分片做不出来 | N7 单独把 GOP 设成 30，测量条件里写明 |

## 8. 和周计划、README 不一致的地方

1. **阶段顺序**：README 第 3 节是 N11 → N7 → N12，周计划是 N11 → N12 → N7（第 33 周计划写“第 30 周起板子已经接入局域网”）。本计划按周计划，但 N7 不依赖 N12 的代码，按 README 的顺序做也能做（只是要自己先解决手机访问板子的网络问题）。
2. **TS 谁写**：README 第 2 节原则 6 的表写“TS 在 N7 手写”；第 34 周计划写“TS 封装和 HTTP 由 Claude 写”，用户手写的是 TS **解包器**（并行任务）。本计划按周计划，C 方案确认时一起定。
3. **FLV 封装谁写**：README N11 M2 说 FLV tag 在 N11 手写、N7 复用；第 33 周计划说“读 Claude 写的 FLV 封装”。取决于 N11 M2 做没做（见上一节的表）。
4. **ExoPlayer 播 HTTP-FLV**：第 34 周计划写“需要额外的扩展（未核对）”；本计划推断 ExoPlayer 自带 FLV 解析、不需要扩展（需要扩展的是 RTMP），第 34 周确认。
5. **GOP**：周计划没提 1 秒分片需要 GOP ≤ 1 秒；本计划把 N7 的 GOP 定成 30。
6. **README 第 5 节**“延迟、卡顿”一行写“对比 RTSP / HTTP-FLV / HLS”，而 N12 的报告是 RTSP / RTMP / WebRTC。N7 做完后报告是五种协议一张表；README 那一行可以改成“RTSP / RTMP / WebRTC / HTTP-FLV / HLS”（本计划不改 README）。
