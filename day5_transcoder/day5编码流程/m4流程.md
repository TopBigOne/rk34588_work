# M4（可选）抓包
* Wireshark 看 OPTIONS / DESCRIBE / SETUP / PLAY

> 前提：M3 已经能在 Mac 上播出画面。本文没有代码。
> 2026-11-08 写的时候没有实际抓过包，文中的报文是**按 RTSP 协议写的示例**，具体的值以你抓到的为准。

---

## 1. 干了什么

M3 播放的时候，用 Wireshark 把播放器和服务器之间的数据抓下来，看清两件事：

1. 播放器和 live555 之间来回说了哪几句话：RTSP 的 4 个命令
2. 视频数据是怎么一包一包送过来的：RTP 包

目的是为以后的 `cam_rtsp`（网络摄像头）预习：到时候服务器要自己写，得知道这几句话里要回答什么。**只认这几个命令和 RTP 包头的几个字段，不深入研究协议细节。**

## 2. 输入和输出

| | 内容 |
|---|---|
| 输入 | M3 正在播放的那条连接 |
| 输出 | Wireshark 里抓到的包，可以存成 `.pcapng` 文件 |

## 3. 在哪里抓

M3 的路线是：

```
播放器 ──TCP──→ Mac 的 localhost:8554 ──adb（USB）──→ 板子上的 live555
```

Mac 上能抓到的是**前半段**：播放器连的是 `localhost`，数据走 Mac 的回环网卡 **lo0**。adb 那段走的是 USB，Wireshark 抓不到，也不需要：RTSP 和 RTP 的内容在前半段已经完整了。

## 4. 操作步骤

1. 先按 m3流程.md 5.2 节在终端 1 启动服务器，**先不要打开播放器**
2. 打开 Wireshark（`/Applications/Wireshark.app`），选网卡 **Loopback: lo0**，开始抓
3. 终端 2 用 ffplay 播放：`ffplay -rtsp_transport tcp rtsp://localhost:8554/out_720p.265`
4. 看几秒画面，关掉 ffplay（会多一个 TEARDOWN 命令），Wireshark 停止抓包
5. 过滤栏输入 `rtsp`，只看 RTSP 命令；输入 `tcp.port == 8554`，看这条连接上的所有包

Wireshark 默认把 554、8554 端口上的数据当 RTSP 解析（推断）。如果显示的只是 TCP、没解析成 RTSP：右键一个包 → Decode As → 选 RTSP。

## 5. 四个命令，各看什么

每个命令都是"播放器发请求、服务器回响应"，格式像 HTTP：第一行是命令或状态码，下面是一行一行的 `名字: 值`。每对请求和响应用 `CSeq`（序号）配对。

### 5.1 OPTIONS：你支持哪些命令？

```
OPTIONS rtsp://localhost:8554/out_720p.265 RTSP/1.0
CSeq: 1

RTSP/1.0 200 OK
CSeq: 1
Public: OPTIONS, DESCRIBE, SETUP, TEARDOWN, PLAY, PAUSE, GET_PARAMETER, SET_PARAMETER
```

看：响应里的 `Public` 列了服务器支持的命令。

### 5.2 DESCRIBE：这个文件是什么？

```
DESCRIBE rtsp://localhost:8554/out_720p.265 RTSP/1.0
CSeq: 2
Accept: application/sdp

RTSP/1.0 200 OK
CSeq: 2
Content-Type: application/sdp
Content-Length: ...

v=0
...
m=video 0 RTP/AVP 96
a=rtpmap:96 H265/90000
a=fmtp:96 sprop-vps=...;sprop-sps=...;sprop-pps=...
a=control:track1
```

响应的正文是一段 **SDP**（会话描述）。重点看这 3 行：

| 行 | 意思 |
|---|---|
| `m=video 0 RTP/AVP 96` | 有一路视频，用 RTP 传，负载类型号 96（96 以上是"动态类型"，具体是什么看下一行） |
| `a=rtpmap:96 H265/90000` | 96 号就是 H.265；时间戳的时钟是 90000 Hz |
| `a=fmtp:96 sprop-vps=...;sprop-sps=...;sprop-pps=...` | VPS、SPS、PPS 的 Base64 编码。就是 MPP 编码器 `getHeader` 取出来、写在文件开头的那几个 |

最后一条说明，播放器在收到第一个 RTP 包之前，就已经从 SDP 里拿到了解码需要的参数。

### 5.3 SETUP：数据怎么传给我？

```
SETUP rtsp://localhost:8554/out_720p.265/track1 RTSP/1.0
CSeq: 3
Transport: RTP/AVP/TCP;unicast;interleaved=0-1

RTSP/1.0 200 OK
CSeq: 3
Transport: RTP/AVP/TCP;unicast;interleaved=0-1
Session: 1A2B3C4D;timeout=65
```

| 看什么 | 意思 |
|---|---|
| `RTP/AVP/TCP` | 播放器要求 RTP 走 TCP。这就是 `-rtsp_transport tcp` 的效果（m3流程.md 3.3 节） |
| `interleaved=0-1` | 在同一条 TCP 连接里，通道 0 放 RTP 数据，通道 1 放 RTCP（统计信息） |
| `Session` | 服务器给的会话号，后面的 PLAY、TEARDOWN 都要带上它 |

如果不加 `-rtsp_transport tcp`，这里会是 `RTP/AVP;unicast;client_port=xxxx-xxxx`（UDP），在 adb 转发下收不到数据。

### 5.4 PLAY：开始播

```
PLAY rtsp://localhost:8554/out_720p.265/ RTSP/1.0
CSeq: 4
Session: 1A2B3C4D
Range: npt=0.000-

RTSP/1.0 200 OK
CSeq: 4
Session: 1A2B3C4D
Range: npt=0.000-
RTP-Info: url=rtsp://.../track1;seq=...;rtptime=...
```

看：`Range: npt=0.000-` 表示从第 0 秒开始播到结尾。响应以后，服务器就开始在同一条连接上发 RTP 包了。

### 5.5 TEARDOWN：关掉

关掉播放器时，播放器发 TEARDOWN（带 Session），服务器停止发送。

## 6. RTP 包看什么

PLAY 之后，过滤 `tcp.port == 8554` 能看到大量的包。走 TCP 时，每个 RTP 包前面多 4 个字节：

```
'$'（1 字节） 通道号（1 字节，0 = RTP） 长度（2 字节） | RTP 包
```

点开一个 RTP 包，只看包头的这几个字段：

| 字段 | 意思 | 预计的值 |
|---|---|---|
| Payload type | 负载类型号 | 96，和 SDP 里一致 |
| Sequence number | 包序号，每个包加 1 | 连续，播放器靠它发现丢包 |
| Timestamp | 这一帧的时间，单位是 1/90000 秒 | 同一帧的包时间戳一样；30 fps 时，每换一帧加 3000（90000 ÷ 30，推断） |
| Marker | 1 = 这一帧的最后一个包 | 每帧的最后一个包是 1 |

一帧 H.265 常常比一个 RTP 包大，会被切成好几个包发（H.265 的分片方式），所以会看到好几个时间戳一样的包，最后一个的 Marker 是 1。分片的细节不用看。

如果 Wireshark 只显示"RTSP Interleaved Frame"、没解析出 RTP：右键 → Decode As，把它当 RTP 解析（推断，以 Wireshark 实际界面为准）。
