## 1. 函数里 `return` 一个局部变量，为什么没问题？

```cpp
Nv12Picture makeAlignedNv12Picture(const int width, const int height) {
    Nv12Picture nv12Picture;          // 局部变量，函数结束就销毁
    nv12Picture.width = width;
    ...
    return nv12Picture;               // 返回它
}
```

### 答：返回的是"值"，不是"地址"

返回类型是 `Nv12Picture`（不是 `Nv12Picture *` 或 `Nv12Picture &`），叫**按值返回**：调用的地方拿到的是**自己的一份**，和函数里的局部变量没有关系了。局部变量销毁不影响它。

出问题的是返回**指向局部变量的指针或引用**：

```cpp
Nv12Picture *makeBad() {
    Nv12Picture nv12Picture;
    return &nv12Picture;   // ✗ 返回栈上这块内存的地址；函数一结束这块栈被回收，调用者拿到悬空指针
}

Nv12Picture &makeBad2() {
    Nv12Picture nv12Picture;
    return nv12Picture;    // ✗ 引用也一样，指向已经销毁的对象（gcc 会给 warning）
}

Nv12Picture makeOk() {
    Nv12Picture nv12Picture;
    return nv12Picture;    // ✓ 按值返回
}
```

**记法：返回"值"没问题，返回指向局部变量的"指针 / 引用"有问题。**

### 会不会多拷贝一次？

`Nv12Picture picture = makeAlignedNv12Picture(1280, 720);` 这一句，编译器一般会做 **NRVO**（具名返回值优化）：直接在调用者的 `picture` 那块内存上构造，一次拷贝都没有。

- C++17 只**保证** `return Nv12Picture{...};`（返回临时对象）这种写法省掉拷贝
- 返回有名字的局部变量时，NRVO 是可选的，gcc 开优化后基本都会做（推断，没看汇编确认）
- 就算没做，也只是拷贝 1 个指针 + 4 个 int（约 24 字节），可以忽略

### 拷贝的是"句柄"，不是画面

`Nv12Picture` 里的 `mppBuf` 是 `MppBuffer`，本质是 `void*`，只是个句柄。拷贝 `Nv12Picture`：

- **不会**复制画面数据
- **不会**释放 buffer：`Nv12Picture` 没有析构函数，局部变量销毁时什么都不做

所以 `Nv12Picture` 只是一张"描述"：画面在哪块 buffer、宽高和 stride 是多少。buffer 由 `allocNv12Buffer` 返回的 `MppBufferPtr` 负责释放。

### 顺带：返回 `unique_ptr` 也没问题

`allocNv12Buffer` 里 `return MppBufferPtr(picture.mppBuf);` 返回的是 `unique_ptr`，它不能拷贝，但：

- 返回**临时对象**：C++17 保证直接构造在调用者那里，不拷贝也不移动
- 返回**有名字的局部 `unique_ptr`**：编译器会自动把它**移动**出去，也合法

## 2. `mpp_dec_cfg_init(&decoderCfg)` 不就成二级指针了吗？

```cpp
// mpp_decoder.h
MppDecCfg decoderCfg = nullptr;                      // MppDecCfg 就是 void*

// mpp_decoder.cpp:22
MPP_CHECK(mpp_dec_cfg_init(&decoderCfg), false);     // &decoderCfg 是 void**
```

### 答：对，就是二级指针，而且这里**就是要传二级指针**

因为 `mpp_dec_cfg_init` 要**新建**一个配置对象，再把它的地址**写回你的变量**。看 MPP 源码（[mpp_dec_cfg.cpp:276](../../rk_code/external/mpp/mpp/base/mpp_dec_cfg.cpp#L276)，只留关键行）：

```cpp
MPP_RET mpp_dec_cfg_init(MppDecCfg *cfg)      // 参数类型 MppDecCfg*，也就是 void**
{
    MppDecCfgImpl *p = NULL;
    p = mpp_calloc(MppDecCfgImpl, 1);         // 第 287 行：在堆上新建一个配置对象
    ...
    *cfg = p;                                 // 第 300 行：顺着地址找到"你的变量"，把新对象的地址写进去
    return MPP_OK;
}
```

调用前后：

```
调用前：  decoderCfg = nullptr                    ← 你的成员变量，配置对象还不存在
                ↑
          &decoderCfg（void**）                    ← 告诉函数："往这个格子里写"

函数里：  *cfg = p;                                ← 写进去

调用后：  decoderCfg = p ──→ [MppDecCfgImpl，堆上的配置对象]
```

如果传 `decoderCfg` 本身，函数拿到的只是 nullptr 的一份拷贝，改了拷贝，你的变量还是 nullptr。

这和 C 语言的 `int x; scanf("%d", &x);` 是一个道理：C 没有引用，函数要把结果"带出来"，只能让调用者传变量的地址。

### 什么时候写 `&`：看函数要不要写回你的变量

| 函数 | 参数类型（头文件里的声明） | 调用写法 | 为什么 |
|---|---|---|---|
| `mpp_dec_cfg_init` | `MppDecCfg *` | `&decoderCfg` | 新建对象，写回你的变量 |
| `mpp_create` | `MppCtx *`、`MppApi **` | `&decoderCtx, &decoderApi` | 同上 |
| `mpp_packet_init` | `MppPacket *` | `&rawPacket` | 同上 |
| `decode_get_frame` | `MppFrame *` | `&rawFrame` | 取出一帧，写回你的变量 |
| `mpp_dec_cfg_set_u32` | `MppDecCfg` | `decoderCfg` | 只是使用这个对象 |
| `mpp_init`、`control` | `MppCtx` | `decoderCtx` | 同上 |
| `mpp_dec_cfg_deinit` | `MppDecCfg` | `decoderCfg` | 释放对象，但不把你的变量置空 |
| `mpp_frame_deinit` | `MppFrame *` | `&frame` | 释放后**顺手把你的变量置成 NULL**，所以要地址 |

**规则：变量的类型照头文件写（`MppDecCfg`，不加 `*`）；调用时加不加 `&`，看这个参数在声明里是 `MppDecCfg` 还是 `MppDecCfg *`。**

### 这次写错过的两处，编译器都没报错

| 写错的 | 实际是什么 | 为什么编译器不报 | 后果 |
|---|---|---|---|
| `mpp_init(&decoderCtx, ...)` | 传的是 `void**`（成员变量自己的地址） | C++ 里**任何指针都能自动转成 `void*`**，参数类型 `MppCtx` 就是 `void*` | MPP 把你对象内部的地址当成解码器实例用：返回错误或段错误 |
| 成员声明成 `MppDecCfg *decoderCfg` | 变量本身是 `void**`，后面传给 `control`、`set_u32` | 同上，`void**` 自动转成 `void*` | 配置对象根本没建出来，`init` 失败 |

MPP 的句柄（`MppCtx`、`MppDecCfg`、`MppFrame`、`MppPacket`、`MppBuffer`）全是 `void*`，**多一个或少一个 `&`、`*`，编译器都不会报**。写完对着头文件的声明逐个核对参数类型。

声明的位置（CLion 里按住 ⌘ 点函数名能跳过去）：

- `typedef void* MppDecCfg;`：`rk_vdec_cfg.h:45`
- `MPP_RET mpp_dec_cfg_init(MppDecCfg *cfg);`：`rk_vdec_cfg.h:68`，同一个文件第 32～35 行的注释写了调用顺序：init → GET_CFG → set → SET_CFG

## 3. `chunk.resize(readSizeBytes)` 解决了什么问题？

```cpp
bool StreamFileReader::readChunk(std::vector<uint8_t> &chunk, bool &isLastChunk) {
    chunk.resize(chunkSizeBytes);                                               // ① 撑到 64K
    const size_t readSizeBytes = fread(chunk.data(), 1, chunkSizeBytes, filePtr.get());  // ② 读
    ...
    chunk.resize(readSizeBytes);                                                // ③ 这一行
    isLastChunk = readSizeBytes < chunkSizeBytes;
    ...
}
```

### 答：`fread` 只往内存里写字节，不会改 vector 的 size；③ 把 size 改成真正读到的字节数

- ① 先把 vector 撑到 64K，`fread` 才有地方写
- ② `fread` 是 C 函数，它只拿到 `chunk.data()` 这个裸指针，不知道外面是 `std::vector`。读了多少，只通过返回值告诉你，**`chunk.size()` 还是 65536**
- ③ 把 size 缩成 `readSizeBytes`，调用者用 `chunk.size()` 才是对的

### 去掉 ③ 会怎样：举个例子

假设文件 140000 字节，每块 65536 字节（数字是为了好算举的例子，不是 aaa.264 的实际大小）：

| 第几次读 | ① 之后 size | fread 读到 | 没有 ③ 时 `chunk.size()` | 有 ③ |
|---|---|---|---|---|
| 1 | 65536 | 65536 | 65536 ✓ | 65536 |
| 2 | 65536 | 65536 | 65536 ✓ | 65536 |
| 3 | 65536 | **8928** | **65536 ✗** | **8928** ✓ |

第 3 次时 chunk 里是：

```
[0 ～ 8927]       这次 fread 写进来的：文件真正的末尾
[8928 ～ 65535]   第 2 块留下的旧数据（① 时 size 本来就是 65536，resize 什么都不改，也不清零）
```

没有 ③，`DecodeStage` 会按 `chunk.data()` + `chunk.size()` 把整整 65536 字节送给解码器，等于把第 2 块的后半段码流又送了一遍。结果可能是解码报错、末尾多出重复的帧、帧数对不上 1803，M1 的验收（1803 帧、0 错误）就过不了。

中间的块每次都读满 64K，有没有 ③ 都一样，**只有最后一块会出问题**，所以这种错平时很难发现。

### ③ 会不会很慢？

不会。缩小 size **不释放内存**，capacity 还是 64K；下一次 ① `resize(65536)` 只是把 size 改回去，不重新申请内存。

### 代码里的 TODO 可以换成

```cpp
// fread 只往 data() 里写字节，不会改 vector 的 size；最后一块读不满 64K，
// 要把 size 缩成实际读到的字节数，不然后面会把上一块残留的旧数据也当成码流送给解码器
chunk.resize(readSizeBytes);
```

## 4. `std::vector` 不维护 size 吗？Java 的 `List.add()` 之后 size 就变了

### 答：vector 维护 size，但只在**通过它自己的成员函数**改数据时才维护；`fread` 绕过了它

vector 内部就是 3 个指针（gcc 自带的 libstdc++，`stl_vector.h` 第 93～95 行）：

```cpp
pointer _M_start;           // 第一个元素的地址（data() 返回的就是它）
pointer _M_finish;          // 最后一个元素的下一个位置
pointer _M_end_of_storage;  // 申请到的内存的末尾
```

- `size()` = `_M_finish - _M_start`（第 918～919 行）
- `capacity()` = `_M_end_of_storage - _M_start`

`size` 不是数出来的，就是 `_M_finish` 这个指针的位置。谁去挪 `_M_finish`？只有 vector 自己的成员函数：

| 操作 | 会不会改 size |
|---|---|
| `push_back`、`emplace_back` | 会（第 1194 行 `++this->_M_impl._M_finish`） |
| `insert`、`erase`、`resize`、`assign`、`clear` | 会 |
| `chunk[i] = x`、`*(chunk.data() + i) = x` | **不会**：只是往已有的位置写值 |
| `fread(chunk.data(), ...)`、`memcpy(chunk.data(), ...)` | **不会**：同上 |

`fread` 是 C 函数，它收到的只是 `chunk.data()` 这个裸指针（`uint8_t*`），等于"从这个地址开始往后写字节"。它不知道这块内存属于一个 vector，更碰不到 `_M_finish`。vector 这边也不知道有人往它的内存里写了东西，所以 size 不变。

### 和 Java 对照

`List.add()` 会让 size 变大，是因为 add **是 List 自己的方法**，它在里面做了 `size++`。对应到 C++ 是 `push_back`，它也会让 size 变大。

`fread` 对应的不是 `List.add()`，而是 Java 的 **`InputStream.read(byte[] buf)`**：

```java
byte[] buf = new byte[65536];
int n = in.read(buf);       // 最后一块可能只读到 8928 个字节
// buf.length 还是 65536，不会变成 8928
// 真正有效的只有 buf[0] ~ buf[n-1]，要靠返回值 n 自己记着
```

这和 `fread` 完全一样：

| | Java | C++ |
|---|---|---|
| 先准备好一块固定大小的内存 | `new byte[65536]` | `chunk.resize(65536)` |
| 往里读 | `in.read(buf)` | `fread(chunk.data(), 1, 65536, file)` |
| 读到多少 | 返回值 `n` | 返回值 `readSizeBytes` |
| 容器大小变不变 | `buf.length` 不变 | `chunk.size()` 不变 |
| 怎么记住有效长度 | 自己保存 `n`，或者 `ByteBuffer.limit(n)` | `chunk.resize(readSizeBytes)` |

所以第 3 节那句 `chunk.resize(readSizeBytes)`，作用就相当于 Java 里的 `ByteBuffer.limit(n)`：告诉后面用这块数据的人，有效的只有前 `readSizeBytes` 个字节。

### 为什么不一个字节一个字节 `push_back`？

那样 size 会自动对，但 64K 要调用 65536 次 `push_back`，每次都要判断容量够不够，还要另外从文件一个字节一个字节地读。`fread` 一次把 64K 整块拷进连续内存，再 `resize` 一下修正 size，快得多。用 `resize` + `data()` + `fread` 来读整块，是 C++ 里的常见写法。
