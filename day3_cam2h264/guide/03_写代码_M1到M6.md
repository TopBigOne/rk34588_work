## 2. 每一步的思路（不是完整代码，自己写）

### M2：V4L2 采集一帧

```
fd = open("/dev/video22", O_RDWR | O_CLOEXEC)
ioctl(QUERYCAP)            → 检查 V4L2_CAP_VIDEO_CAPTURE_MPLANE 和 V4L2_CAP_STREAMING
v4l2_format fmt{}          → fmt.type = V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE
                             fmt.fmt.pix_mp.width / height / pixelformat = V4L2_PIX_FMT_NV12
ioctl(S_FMT) → ioctl(G_FMT) → ⭐ 打印 fmt.fmt.pix_mp.plane_fmt[0].bytesperline 和 sizeimage，后面 M3 要用
ioctl(REQBUFS)             → count = 4, memory = V4L2_MEMORY_MMAP；检查驱动实际给了几块
for i in 0..3:
    v4l2_buffer buf{} + v4l2_plane planes[1]{}   → buf.m.planes = planes; buf.length = 1（MPLANE 必须）
    ioctl(QUERYBUF)        → planes[0].length、planes[0].m.mem_offset
    start[i] = mmap(nullptr, length, PROT_READ | PROT_WRITE, MAP_SHARED, fd, mem_offset)
for i in 0..3: ioctl(QBUF, i)
ioctl(STREAMON)
跳过 30 帧：DQBUF → QBUF
DQBUF → idx；fwrite(start[idx], 1, planes[0].bytesused, fp) → QBUF(idx)
STREAMOFF → munmap × 4 → close(fd)
```

MPLANE 类型要注意的三个地方（readme 里也提了）：
1. buffer 类型是 `V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE`，不是 `..._CAPTURE`
2. 格式读写 `fmt.pix_mp`，每行字节数在 `fmt.pix_mp.plane_fmt[0].bytesperline`
3. 每次 QUERYBUF / QBUF / DQBUF 都要给 `v4l2_buffer` 挂上 `planes` 数组，并设置 `buf.length = 1`（plane 个数），否则 ioctl 返回 `EINVAL`

### M3：零拷贝导入 + 编码 1 帧

```
for i in 0..3:
    v4l2_exportbuffer exp{}  → exp.type = MPLANE, exp.index = i, exp.plane = 0, exp.flags = O_CLOEXEC
    ioctl(EXPBUF)            → exp.fd
    MppBufferInfo info{}     → info.type = MPP_BUFFER_TYPE_EXT_DMA, info.fd = exp.fd, info.size = planes[0].length
    mpp_buffer_import(&mppBuf[i], &info)
encoder.init(cfg)            → ⭐ stride 用 G_FMT 读回来的，见第 3 节
encoder.get_header → fwrite
DQBUF → idx → encoder.encode(mppBuf[idx], false, pkt) → fwrite → QBUF(idx)
encoder.encode(nullptr, true, pkt) 直到 pkt.eos
释放：mpp_buffer_put × 4 → close(exp.fd) × 4 → STREAMOFF → munmap → close(fd)
```

> 对照 `camera_source.c` 第 266～284 行。注意 `info.size` 直接用 plane 的 length 就行，不用学它第 280～281 行的位运算（02 篇 2.3 节）。

### M4：循环 300 帧

把 M3 的"DQBUF → encode → fwrite → QBUF"放进循环。**QBUF 必须在 `encode()` 返回之后**（02 篇 3.2 节）。Day 1 的 `encode()` 是阻塞的，一帧编完才返回，所以顺序写就是对的。

### M5：参数、统计、旋转

- 参数：抄 Day 1 的 `src/app/args.*`，改成 `-d /dev/video22 -w 1920 -h 1080 -n 300 -o out.h264 -t h264|h265 -r 0|1|2|3`
- 统计：用 `std::chrono::steady_clock` 分别记 DQBUF 等了多久、`encode()` 花了多久、整个循环花了多久。实际帧率 = 编码帧数 ÷ 循环总时间。**摄像头是 30fps 时，实际帧率不会超过 30**，这和 Day 1 读文件时几百 fps 不一样，瓶颈在摄像头
- 旋转：`mpp_enc_cfg_set_s32(cfg, "prep:rotation", N)`，N = 0 / 1（逆时针 90°）/ 2（180°）/ 3（逆时针 270°）。MPP 开发参考第 658 行。转 90° 以后输出变成竖屏，宽高怎么设置、要不要交换，做实验确认

### M6：拷贝版本（对比用）

```
mpp_buffer_group_get_internal(&grp, MPP_BUFFER_TYPE_DRM | MPP_BUFFER_FLAGS_CACHABLE)   // 和 Day 1 一样
mpp_buffer_get(grp, &copyBuf, sizeimage)
循环里：DQBUF → mpp_buffer_sync_begin → memcpy(get_ptr(copyBuf), start[idx], sizeimage)
       → mpp_buffer_sync_end → QBUF（拷完就能还，比零拷贝版本还得早）→ encode(copyBuf)
```

两个版本用同样的参数各跑一次，另开一个终端 `adb shell top -d 1`，记下 `day3_cam2h264` 的 CPU 占用。1080p30 每秒要拷 3MB × 30 = 约 90MB。

## 3. ⭐ 最大的坑：stride 要跟着摄像头走

### 3.1 实测：摄像头缓冲区的 UV 从第 1080 行开始

不接摄像头也能问驱动排布（`--try-fmt-video`，2026-10-15 板子实测，见 01 篇第 4 节）：

| | 摄像头缓冲区（驱动给的） | Day 1 `MppEncoder` 默认（`mpp_encoder.cpp` 第 35～36 行） |
|---|---:|---:|
| hor_stride（每行字节数） | 1920（`bytesperline`） | `ALIGN(1920, 16)` = 1920 |
| ver_stride（UV 从第几行开始） | **1080**（`sizeimage` 3,110,400 = 1920 × 1080 × 3/2） | `ALIGN(1080, 16)` = **1088** |
| 一帧占多少字节 | 3,110,400 | 1920 × 1088 × 3/2 = 3,133,440 |

**如果直接复用 Day 1 的编码器**（按源码推断，未实测）：编码器会从第 1088 行开始读 UV，比实际位置晚 8 行，画面颜色会错位。

> 2026-10-16 补充实测：真正 `S_FMT` 以后 G_FMT 读回来的值和上表一样，但 `VIDIOC_QUERYBUF` 给的缓冲区长度是 **3,133,440**（= 1920 × 1088 × 3/2）。驱动分配内存时把高度对齐到了 16，图像本身还是按 1080 行排（UV 从第 1080 行开始，多出来的 8 行没用），所以按 1088 读**不会越界**，但颜色还是会错位。详见 [具体编码day3_cam2h264的流程.md](../具体编码day3_cam2h264的流程.md) 第 3.1 节。

> 装好摄像头以后，用 M2 打印的 G_FMT 实际值再确认一次。驱动在 S_FMT 时可能会调整宽高或者 bytesperline，**永远以 G_FMT 读回来的为准**，不要自己算。

### 3.2 怎么改 Day 1 的编码器

`MppEncoder::init` 里 stride 是写死的（`mpp_encoder.cpp` 第 35～36 行），要让调用方能传进来。建议改法：

```cpp
struct EncoderConfig {
    ...
    int horStride = 0;   // 0 = 自己按 16 对齐算（Day 1 读文件时的行为不变）
    int verStride = 0;   // Day 3：horStride = bytesperline，verStride = sizeimage / bytesperline * 2 / 3
};
```

`init` 里：`horStride = cfg.horStride ? cfg.horStride : ALIGN(cfg.width, 16);`，`verStride` 同理。默认值是 0，所以 Day 1 的行为完全不变。

> ✅ 已完成（2026-10-15，选了下表的做法 ①）：`src/encoder/mpp_encoder.*` 和 `src/common/mpp_utils.h` 从 Day 1 复制过来，`EncoderConfig` 加了 `horStride` / `verStride`（默认 0，行为和 Day 1 一样），已加进 CMakeLists.txt，交叉编译 `-Wall -Wextra` 0 warning。M3 时这样用：
> ```cpp
> EncoderConfig cfg;
> cfg.width     = fmt.fmt.pix_mp.width;
> cfg.height    = fmt.fmt.pix_mp.height;
> cfg.horStride = fmt.fmt.pix_mp.plane_fmt[0].bytesperline;
> cfg.verStride = fmt.fmt.pix_mp.plane_fmt[0].sizeimage / cfg.horStride * 2 / 3;
> ```

**怎么把 Day 1 的编码器拿过来**，两种做法：

| 做法 | 优点 | 缺点 |
|---|---|---|
| ①（建议）把 `mpp_encoder.*` 和 `common/mpp_utils.h` **复制**到 `day3_cam2h264/src/` 下，在副本里改 | 每一天的工程自成一体，改 Day 3 不会影响 Day 1 | 两份代码，Day 1 以后改了不会自动同步 |
| ② CMakeLists.txt 直接引用 `../day1_yuv2h264/src/encoder/mpp_encoder.cpp`，改 Day 1 的源文件 | 只有一份代码 | Day 1 和 Day 3 绑在一起，改一边要两边都重新验证 |

## 5. 容易踩的坑（写代码时对照）

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `open` 成功但 `STREAMON` 失败、或者 DQBUF 一直等不到帧 | 摄像头没检测到（sensor 不在链路里） | 01 篇第 2 节的 3 条检查 |
| QUERYBUF / QBUF 返回 `EINVAL` | Multiplanar 类型没挂 `planes` 数组，或者 `buf.length` 没设 | 第 2 节 M2 的三个注意点 |
| 画面很暗、发绿或者发紫 | `rkaiq_3A_server` 没在运行，或者前几帧曝光还没稳定 | 01 篇 2.4 节；跳过前 30 帧（官方跳了 50 帧） |
| 颜色错位、底部有绿条 | 编码器的 stride 和摄像头缓冲区不一致 | 第 3 节：stride 用 G_FMT 读回来的 |
| 画面撕裂（上下两半不是同一时刻） | 编码器还在读就 QBUF 了 | `encode()` 返回以后再 QBUF |
| 用错节点，打开的是别的 ISP | 摄像头插的接口对应的是 `video22` 不是 `video31` | 01 篇 2.3 节，用 media-ctl 查 |
| 程序退出后再运行报 `EBUSY` | 上次没有 STREAMOFF / close 就被杀掉了，或者 `v4l2-ctl` 还在占用 | 确认没有别的进程在用这个节点；重新插拔不了的话重启板子 |
