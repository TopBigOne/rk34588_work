## 1. 先认识 V4L2（20 分钟）

V4L2（Video for Linux 2）是 Linux 内核给摄像头这类设备提供的接口。它**没有库可以链接**：打开 `/dev/videoN`，然后全靠 `ioctl(fd, VIDIOC_xxx, &结构体)` 跟驱动说话。结构体和命令都定义在 `linux/videodev2.h`（工具链 sysroot 里有）。

本项目用到的 ioctl，按调用顺序：

| ioctl | 干什么 | 用到的结构体 |
|---|---|---|
| `VIDIOC_QUERYCAP` | 问"你是什么设备、支持什么" | `v4l2_capability` |
| `VIDIOC_S_FMT` / `VIDIOC_G_FMT` | 设置 / 读回图像格式（宽高、像素格式、**每行字节数**） | `v4l2_format` |
| `VIDIOC_REQBUFS` | 让驱动分配 N 块缓冲区 | `v4l2_requestbuffers` |
| `VIDIOC_QUERYBUF` | 查第 i 块缓冲区的大小和 mmap 偏移 | `v4l2_buffer` |
| `VIDIOC_EXPBUF` | 把第 i 块缓冲区导出成 **dma_buf fd** | `v4l2_exportbuffer` |
| `VIDIOC_QBUF` | 把一块空缓冲区交给驱动（"往这里写"） | `v4l2_buffer` |
| `VIDIOC_STREAMON` / `STREAMOFF` | 开始 / 停止采集 | `v4l2_buf_type` |
| `VIDIOC_DQBUF` | 取出一块写好画面的缓冲区（没有就阻塞等） | `v4l2_buffer` |

**缓冲区的轮转**（这是整个 V4L2 采集最核心的一张图）：

```
          QBUF（空的交给驱动）                     DQBUF（取出写好的）
 应用 ───────────────────────→ 驱动的"待写"队列 ──摄像头写满一帧──→ 驱动的"已写"队列 ───────────────→ 应用
  ↑                                                                                         │
  └──────────────────────────────── 用完（编码完）再 QBUF ←───────────────────────────────────┘
```

4 块缓冲区在这个圈里转：任何时刻，有的在等摄像头写，有的在被编码器读。应用拿着的那块，驱动不会去写。

> ⚠️ **板子上是 Multiplanar 类型**（2026-10-15 实测：`v4l2-ctl -d /dev/video31 --all` 显示 `Video Capture Multiplanar`）。所以 buffer 类型要用 `V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE`，格式要读 `fmt.pix_mp`，`v4l2_buffer` 要带 `planes` 数组。NV12 只有 1 个 plane（Y 和 UV 在同一块内存里）。

### 2.1 `camera_source_init`（第 112 行）：分 6 段读

| 段 | 行号 | 在干什么 |
|---|:---:|---|
| ① 打开设备 | 128 | `open(device, O_RDWR \| O_CLOEXEC)` |
| ② 查能力 | 145～158 | `QUERYCAP`，必须支持 CAPTURE（或 CAPTURE_MPLANE）和 STREAMING |
| ③ 设格式 | 161～206 | 有 MPLANE 就用 MPLANE 类型（164～165）；`ENUM_FMT` 打印支持的格式；`S_FMT` → `G_FMT` 读回实际值 |
| ④ 要缓冲区 | 209～221 | `REQBUFS`：`count = bufcnt`，`memory = V4L2_MEMORY_MMAP`；驱动给的数量不对就失败 |
| ⑤ ⭐ 每块缓冲区：mmap + EXPBUF + import | 224～285 | 见 2.2，**零拷贝的关键** |
| ⑥ 全部 QBUF，开始采集，丢掉前几帧 | 287～318 | 4 块都交给驱动 → `STREAMON` → 取 4 帧马上还回去（314～318，跳过不稳定的帧） |

### 2.2 ⭐ 第 224～285 行：一块缓冲区的三种身份

```c
QUERYBUF(i)                         // 236：查第 i 块的长度和 mem_offset
start = mmap(..., mem_offset)       // 244～258：身份 1：CPU 地址（CPU 想看画面时用）
EXPBUF(i) → expbuf.fd               // 266～271：身份 2：dma_buf fd（别的硬件用）
info.type = MPP_BUFFER_TYPE_EXT_DMA // 278
info.fd   = expbuf.fd               // 279
mpp_buffer_import(&buffer, &info)   // 282：身份 3：MppBuffer（交给编码器用）
```

同一块物理内存，三个"把手"：
- `start` 给 CPU 用（M2 存一帧到文件时用它）
- `export_fd` 是 dma_buf 的文件描述符，任何支持 dma_buf 的硬件（编码器、RGA、显示）都能凭它访问这块内存
- `buffer` 是 MPP 认识的包装，`mpp_frame_set_buffer(frame, buffer)` 就能送去编码

**零拷贝**就是：编码器拿到的是摄像头写的那块内存本身，不是一份拷贝。

`mpp_buffer_import` 的行为见 `mpp_buffer.h` 的注释（工具链 sysroot 里那份已经加了中文注释）：group 传 NULL，所以这块 buffer 挂在 MPP 内部的 misc group 下面；引用计数为 1；`mpp_buffer_put` 以后 MPP 解除引用，**内存本身还是摄像头驱动的**，MPP 不会释放它。

### 2.3 读的时候会发现的几处"怪代码"

这份代码是官方测试用的，有几处不严谨，自己写的时候注意：

| 行号 | 代码 | 问题 |
|:---:|---|---|
| 167～168 | `vfmt.fmt.pix.width = width` | MPLANE 类型应该写 `fmt.pix_mp`。能用是因为 `pix` 和 `pix_mp` 在同一个 union 里，前 3 个字段（width、height、pixelformat）的位置刚好一样 |
| 206 | 只打印了 width 和 height | **没读 `bytesperline`**。stride 完全没用驱动返回的值，而是由 mpi_enc_test 自己算（见第 3 节） |
| 280～281 | `info.size = buf_len & 0x07ffffff`<br>`info.index = (buf_len & 0xf8000000) >> 27` | 把长度的高 5 位当成 index，很奇怪。1080p 的缓冲区只有 3MB，高位都是 0，所以实际上 size 就是 buf_len，index 是 0 |
| 388 | `if (buf.index > ctx->bufcnt)` | 越界检查差 1，应该是 `>=` |
| 49 | `CamFrame fbuf[10]` | 最多 10 块，`bufcnt` 超过 10 会写越界，没有检查 |
| 421～425 | `QBUF` 失败也返回 `MPP_OK` | 调用方不知道缓冲区没还回去 |

### 2.4 `camera_frame_to_buf`（第 429 行）里的 `sync_end` 起作用吗？

它在返回 buffer 之前调用了 `mpp_buffer_sync_end(buf)`。按 MPP 源码推断，**对 import 进来的摄像头缓冲区，这一句什么也不做**（按源码推断，未实测）：
- `mpp_buffer_create` 里：`p->uncached = (group->flags & MPP_ALLOC_FLAG_CACHABLE) ? 0 : 1`（`mpp/base/mpp_buffer_impl.cpp` 第 444 行）
- import 时 group 是 NULL，用的是 misc group，创建时没有 `MPP_BUFFER_FLAGS_CACHABLE` 标志 → `uncached = 1`
- `check_buf_need_sync` 看到 `uncached` 就直接返回 `MPP_OK`（`mpp/base/mpp_buffer.cpp` 的 `check_buf_need_sync`）

而且 CPU 本来就没写这块内存（是摄像头硬件写的、编码器硬件读的），本来也不需要刷 CPU 的 cache。**只有 M6 的拷贝版本**（CPU memcpy 到一块 CACHABLE 的 MppBuffer）才真正需要 `sync_end`，和 Day 1 一样。

### 3.1 stride：官方是怎么"碰巧"对上的

`test_ctx_init` 第 155～158 行：命令行给了 stride 就用，没给就按 16 对齐（1080 → 1088）。但在这之前，`mpi_enc_utils.c` 第 613～616 行已经替你填好了默认值：

```c
if (!cmd->hor_stride)
    cmd->hor_stride = mpi_enc_width_default_stride(cmd->width, cmd->format);  // NV12：ALIGN(1920, 8) = 1920
if (!cmd->ver_stride)
    cmd->ver_stride = MPP_ALIGN(cmd->height, 2);                              // ALIGN(1080, 2) = 1080
```

所以命令行跑 `mpi_enc_test -w 1920 -h 1080` 时，stride 实际是 **1920 × 1080**，正好和摄像头缓冲区的排布一致（第 01 篇第 4 节实测：`bytesperline` 1920，`sizeimage` 3,110,400）。test_ctx_init 里"按 16 对齐"的那个分支根本走不到。

> 这也说明 Day 1 笔记里"mpi_enc_test 的 ver_stride 是 1088"只在直接调用 `test_ctx_init`、不经过 `mpi_enc_utils` 填默认值时才成立。Day 1 自己的 `MppEncoder` 用 1088 没问题，因为它读文件时也按 1088 摆放；但 Day 3 的缓冲区是驱动摆的，**必须用驱动的排布**。

### 3.2 为什么"编码完才能还"（第 851 行）

`QBUF` 一调用，驱动就可能马上让摄像头往这块内存写下一帧。如果编码器还在读，读到的就是"上半截旧画面 + 下半截新画面"，也就是画面撕裂。

Day 1 的 `MppEncoder::encode()` 里是 `encode_put_frame` + 阻塞的 `encode_get_packet`，`encode()` 返回时硬件已经读完了这一帧，所以**在 `encode()` 返回之后 QBUF 是安全的**。
