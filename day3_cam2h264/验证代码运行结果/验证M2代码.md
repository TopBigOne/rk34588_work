# 验证 M2 代码：V4L2 采集一帧存成 NV12

> M2 做的事：open → QUERYCAP → S_FMT / G_FMT → REQBUFS(4) → QUERYBUF + mmap → QBUF × 4 → STREAMON → 跳过 30 帧 → DQBUF → 存文件 → QBUF。
> 代码：`src/main.cpp`；写法见 [具体编码day3_cam2h264的流程.md](../具体编码day3_cam2h264的流程.md) 第 3 节。
> 测三类：**正常流程对不对**、**出错时处理得对不对**、**资源有没有泄漏**。

所有命令都在 Mac 的 day3 目录下执行：
```bash
cd /Users/dev/Documents/AV/rk_work/day3_cam2h264
```

⚠️ 摄像头装在 **MIPI CSI3** 时，节点是 **`/dev/video22`**（怎么查见 [doc/v4l2-ctl和media-ctl用法.md](../doc/v4l2-ctl和media-ctl用法.md) 第 3 节）。

## 一、正常流程（每次改完代码都跑一遍）

### ① 运行，看日志

```bash
./run_on_board_with_mac.sh
```

应该依次看到（有一行不一样就是有问题）：
```
I ... device /dev/video22: driver rkisp_v6, card rkisp_mainpath
I ... format: 1920x1080 NV12, planes 1, bytesperline 1920, sizeimage 3110400
I ... request 4 block buffer in success
I ... buffer 0: length 3133440        （0～3 四行）
I ... frame: buffer N, 3110400 bytes -> /userdata/av/cam_m2.nv12      ← N 是 0～3 中的一个
```
跳过 30 帧大约 1 秒（30 帧 ÷ 30fps），所以最后一行会晚 1 秒左右出来，正常。

2026-10-18 实测：
```

20:40:49.193 I day3_main:     format: 1920x1080 NV12, planes 1, bytesperline 1920, sizeimage 3110400
20:40:49.196 I day3_main:     request 4 block buffer in success
20:40:49.196 I day3_main:       buffer 0: length 3133440
...
20:40:50.368 I day3_main:       frame: buffer 2, 3110400 bytes -> /userdata/av/cam_m2.nv12
```

### ② 看退出码

```bash
adb shell '/tmp/CLion/run/day3_cam2h264 > /dev/null; echo "exit code: $?"'
```
应该是 `exit code: 0`。出错时 `run()` 返回 -1，`main` 把它当退出码返回；退出码只保留低 8 位，**-1 变成 255**（2026-10-18 在 M3 上实测）。

### ③ 看文件大小

```bash
adb shell 'ls -l /userdata/av/cam_m2.nv12'
```
应该**正好 3110400**（= 1920 × 1080 × 3/2）。如果是 3133440，说明写文件时错用了缓冲区长度 `length`，应该用 `bytesUsed`。

### ④ 拉回 Mac 看画面

```bash
KEEP=1 ./run_move_file_from_board_via_usb.sh /userdata/av/cam_m2.nv12
ffplay -f rawvideo -pixel_format nv12 -video_size 1920x1080 result_from_board/cam_m2.nv12
```

| 看到的 | 说明 |
|---|---|
| 画面清楚，颜色、亮度正常 | ✅ |
| 发绿 / 发紫 / 很暗 | 3A 服务没在运行（`adb shell pidof rkaiq_3A_server`），或者跳过的帧太少 |
| 画面错位，一直往上滚 | 文件大小不对（见 ③） |
| 上半张和下半张不是同一时刻（撕裂） | 写的不是刚 DQBUF 拿到的那块缓冲区（比如写成了 `g_bufs->start`） |

### ⑤ 和"标准答案" v4l2-ctl 对比

```bash
adb shell 'v4l2-ctl -d 22 --set-fmt-video=width=1920,height=1080,pixelformat=NV12 --stream-mmap=4 --stream-skip=30 --stream-count=1 --stream-to=/userdata/av/ref.nv12'
KEEP=1 ./run_move_file_from_board_via_usb.sh /userdata/av/ref.nv12
ffplay -f rawvideo -pixel_format nv12 -video_size 1920x1080 result_from_board/ref.nv12
```
两张拍的时刻不同，md5 肯定不一样，但**大小、颜色、清晰度应该一样**。

## 二、出错时的处理（故意制造错误）

**临时**改一下代码或环境，看程序能不能报出正确的错误、正常退出（不崩溃、不卡住），**退出码不是 0**（实测是 255，原因见一、②）。测完改回来。

| 怎么制造错误 | 应该看到（红色 E 日志） | 测的是哪段代码 |
|---|---|---|
| `kDevice` 改成 `"/dev/video99"` | `open /dev/video99 ...: No such file or directory` | open 失败的判断（必须是 `< 0`，不能是 `if (fd)`） |
| `kDevice` 改成没接摄像头的 `"/dev/video31"` | `VIDIOC_STREAMON: Operation not permitted` | `V4L2_CHECK`、cleanup |
| 先在板子屏幕上打开相机 App，再运行 | `VIDIOC_S_FMT` 或 `VIDIOC_REQBUFS`：`Device or resource busy` | 设备被别的程序占用 |
| `kOutputFilePath` 改成 `"/proc/cam_m2.nv12"`（不能写的目录） | `fopen /proc/cam_m2.nv12: ...` | fopen 失败时也把缓冲区 QBUF 还回去 |

出现下面任何一种，就是那段错误处理有问题：
- 打印了 success（判断写反了）
- 程序卡住不动（缓冲区没还回去，DQBUF 永远等不到）
- 崩溃

查是谁占用了设备：
```bash
adb shell 'for p in /proc/[0-9]*; do ls -l $p/fd 2>/dev/null | grep -q /dev/video22 && cat $p/cmdline; echo; done'
```

## 三、资源有没有泄漏

```bash
./run_on_board_with_mac.sh && ./run_on_board_with_mac.sh
```
**第二次也必须成功**。第一次如果没有 STREAMOFF / munmap / close，第二次可能报 `Device or resource busy`。

做完"二"里的错误测试后，也再正常跑一次，确认出错退出时也释放干净了。

## 2026-10-18 review 时修掉的 bug（回归测试时重点看）

| bug | 怎么测出来 |
|---|---|
| `fwrite(g_bufs->start, ...)`：永远写 buffer 0 | ① 的日志里 `frame: buffer 2`，但写的是 0；⑥ 画面动起来可能撕裂 |
| `if (g_bufs->start == MAP_FAILED)`：只检查第 0 块 | 代码 review（mmap 一般不会失败，很难用测试触发） |
| mmap 第 3 个参数里混了 `MAP_SHARED` | 代码 review（`MAP_SHARED` 和 `PROT_READ` 值碰巧都是 1，测试测不出来） |
| `cap.capabilities & V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE` | ① 会打印"不支持 Multiplanar"然后退出 |
| `if (g_videoFd)` 判断 open | 二、`/dev/video99` 那一项会打印 success |

细节见 [doc/C++小坑和常见写法.md](../doc/C++小坑和常见写法.md)。
