# 面试会问的问题：摄像头 → 零拷贝 → 硬件编码

> 回顾 `src/main.cpp` 时整理出来的 6 个问题，都是 Day 3 亲手踩过或实测过的。
> 每题分两部分：**30 秒版**（面试时先说这个）和**展开讲**（面试官追问时用，带实测数字）。
> 不用背流程。每一步都能回答"不做会怎样"，流程自然就记住了。

整个程序的链路（`src/main.cpp`）：

```
open → QUERYCAP → S_FMT/G_FMT → REQBUFS 4 → QUERYBUF + mmap → EXPBUF → mpp_buffer_import
     → QBUF ×4 → STREAMON → 编码器 init → 循环（DQBUF → encode → QBUF → 写文件）→ EOS → 清理
```

| 阶段 | 要解决的问题 | 对应的步骤 | 本文哪一题 |
|---|---|---|---|
| ① 谈好格式 | 驱动最终给了什么格式、每行多少字节？ | S_FMT → G_FMT | 第 2 题 |
| ② 准备内存，打通共享 | 帧放在哪？编码器怎么不拷贝就读到它？ | REQBUFS → EXPBUF → import | 第 1、3 题 |
| ③ 跑起来 | 一帧一帧地取、编、还 | DQBUF → encode → QBUF | 第 4、5、6 题 |
| ④ 收尾 | 按相反的顺序释放 | STREAMOFF → put → munmap → close | 第 1 题末尾 |

## 1. 零拷贝是怎么实现的？

### 30 秒版

摄像头驱动分配了 4 块 buffer，ISP 直接往里面写画面。我用 `VIDIOC_EXPBUF` 把每块 buffer 导出成一个 **dma_buf fd**，再用 `mpp_buffer_import`（类型 `MPP_BUFFER_TYPE_EXT_DMA`）把这个 fd 包成 `MppBuffer` 交给编码器。这样 ISP 写的和编码器读的是**同一块物理内存**，CPU 一个字节都不用搬。

### 展开讲

**先说人话**：零拷贝的意思是，摄像头写好的画面，编码器直接拿去读，不用 CPU 先复制一份。

**打个比方**：摄像头和编码器是两个部门，画面是放在仓库里的一箱货。
- 普通做法：CPU 把货从摄像头的仓库**搬**到编码器的仓库，一帧 3.1 MB，每秒 30 帧，就是每秒搬 93 MB。
- 零拷贝：不搬货，只把**仓库钥匙**复制一把给编码器。dma_buf fd 就是这把钥匙。

**代码里是哪几步**（`src/main.cpp` 第 200～240 行）：

| 步骤 | 代码 | 做了什么 |
|---|---|---|
| 1 | `VIDIOC_REQBUFS`（第 192 行） | 让摄像头驱动分配 4 块 buffer。内存是**驱动**分配的（`V4L2_MEMORY_MMAP`） |
| 2 | `VIDIOC_QUERYBUF` + `mmap`（第 209～214 行） | 拿到 buffer 的大小，并映射一个**本程序 CPU 能用**的地址（M2 存 NV12 文件时用。M3 编码用不到它） |
| 3 | `VIDIOC_EXPBUF`（第 226 行） | 把 buffer 导出成 dma_buf fd。**这个 fd 可以交给别的硬件用** |
| 4 | `mpp_buffer_import`（第 235 行） | 把 fd 包成 `MppBuffer`，类型填 `MPP_BUFFER_TYPE_EXT_DMA` |
| 5 | `encoder.encode(g_bufs[index].mppBuf, ...)`（第 301 行） | 编码器直接读这块内存 |

**`EXT_DMA` 是什么意思**：MPP 的头文件 `inc/mpp_buffer.h` 第 121 行写的是 `ext_dma : the DMABUF(DMA buffers) come from the application`，也就是"内存是应用从外面带进来的"，MPP 只是借用，不负责分配。第 126 行还写了：`MPP_BUFFER_TYPE_EXT_DMA is only used for general external dma_buf fd import`。

**怎么证明真的是零拷贝**（见 [验证M3代码_零copy导入.md](../验证代码运行结果/验证M3代码_零copy导入.md) 第二节）：
- `main.cpp` 里搜不到 `memcpy`，也没有 `fwrite(g_bufs...)`。送给编码器的是 `mppBuf`，不是 `start` 指针。
- 日志里 4 块 buffer 各有一个不同的 fd（实测 12、13、14、15）。

**清理顺序**（`clear_up()`，第 341～371 行）：STREAMOFF → `mpp_buffer_put` → `munmap` → `close(dmaFd)` → `close(videoFd)`。跟申请的顺序相反：后拿到的先还。

**面试官可能追问**

| 追问 | 答 |
|---|---|
| mmap 拿到的指针为什么不能直接给编码器？ | 那是**本进程虚拟地址**，只有 CPU 能用。编码器是另一块硬件，它要的是能找到物理内存的东西，也就是 dma_buf fd |
| 还有别的零拷贝方式吗？ | 有。`V4L2_MEMORY_DMABUF`：先由 MPP（或 DRM）分配内存，再把 fd 交给摄像头去写，方向正好反过来。见 [guide/04](../guide/04_摄像头和V4L2知识.md) 6.3 节 |
| import 填 `MPP_BUFFER_TYPE_DRM` 行不行？ | 实测也能编（2026-10-18），因为 dma_buf fd 是通用的。但语义上内存是外面来的，应该写 `EXT_DMA` |

## 2. stride 是什么？填错了会怎样？

### 30 秒版

stride 是图像在内存里**实际**的宽和高：`hor_stride` 是每行占多少字节，`ver_stride` 是 Y 平面占多少行，**UV 平面就从第 ver_stride 行开始**。这两个值必须用驱动 `G_FMT` 返回的，不能自己猜。我实测过：摄像头的 UV 从第 1080 行开始，如果按 16 对齐填成 1088，编码器会从错误的位置读 UV，画面底部出现**绿条**，颜色也偏了。

### 展开讲

**先说人话**：图像在内存里是一行接一行放的。为了让硬件读起来快，每行末尾、整张图末尾可能会多留一些空位。stride 就是"算上空位以后的尺寸"。

**NV12 在内存里长什么样**（1920×1080）：

```
偏移 0                 ┌──────────────── 1920 字节 ────────────────┐
                       │ Y 平面：1080 行（亮度）                    │
偏移 1920×1080         ├────────────────────────────────────────────┤  ← UV 从这里开始
     = 2,073,600       │ UV 平面：540 行（颜色，U V 交替）          │
偏移 3,110,400         ├────────────────────────────────────────────┤  ← sizeimage 到这里结束
                       │ 空位（驱动按高度 1088 分配，多出 23,040 字节） │
偏移 3,133,440         └────────────────────────────────────────────┘  ← buffer 长度
```

数字都是板子实测的（M2/M3 日志）：

| 值 | 实测 | 怎么来的 |
|---|---|---|
| bytesperline（= hor_stride） | 1920 | G_FMT |
| sizeimage | 3,110,400 | G_FMT，= 1920 × 1080 × 1.5 |
| buffer 长度 | 3,133,440 | QUERYBUF，= 1920 × **1088** × 1.5（驱动按 16 对齐分配） |
| ver_stride | **1080** | `sizeimage / bytesperline × 2 / 3`（`main.cpp` 第 259 行） |

**填成 1088 会怎样**：编码器以为 UV 从 1920 × 1088 = 2,088,960 开始读，比真实位置晚了 15,360 字节，也就是 8 行 UV。
- 每一行的颜色都取自下面 16 行图像的颜色，所以**颜色偏**。
- 读到最后 8 行 UV 时已经越过真实数据，读进了末尾的空位。空位里是 0，U=V=0 在 YUV 里就是**绿色**，所以**底部出现绿条**。
- 不会越界崩溃：2,088,960 + 1920 × 1088 / 2 = 3,133,440，正好等于 buffer 长度。

2026-10-18 实测复现过（[验证M3代码](../验证代码运行结果/验证M3代码_零copy导入.md) 三、A）。

**陷阱**：buffer 长度 3,133,440 看起来像是高度 1088，很容易让人以为 ver_stride 是 1088。但驱动实际是从第 1080 行开始写 UV 的，**buffer 分配得大，不代表 UV 从后面开始**。所以 ver_stride 要按 sizeimage 算，不能按 buffer 长度算。2026-10-17 用 v4l2-ctl 抓帧，画面颜色正常，确认了这一点。

**MPP 文档里的定义**（《MPP 开发参考》第 214～215 行）：
- `hor_stride`：垂直方向相邻两行之间的距离，单位是字节
- `ver_stride`：图像分量之间间隔的行数

更多见 Day 1 的 [stride.md](../../day1_yuv2h264/doc/stride.md) 第 4 节"ver_stride 决定了 UV 从哪里开始"。

**面试官可能追问**

| 追问 | 答 |
|---|---|
| Day 1 编文件时 ver_stride 为什么是 1088？ | 文件里的 YUV 是我自己读进 MPP 分配的 buffer 的，**排布由我决定**，按 16 对齐就行。摄像头的 buffer 是**驱动**排的，排布由驱动决定，必须照着它填 |
| 怎么知道驱动的排布？ | 只看 `G_FMT` 返回的 bytesperline 和 sizeimage。不要用 S_FMT 时自己填的值，驱动可能改过 |

## 3. 为什么要 4 个 buffer，不用 1 个？

### 30 秒版

buffer 在三个地方轮转：驱动手里空着等写的、驱动写好等取的、程序手里正在编码的。只有 1 块的话，程序拿着它编码时，驱动手里没有空 buffer，这段时间来的帧全部丢掉。我实测过：只给 1 块，程序什么都不做，也只能收到 **10fps**（摄像头是 30fps）。给 4 块就能收满 30fps，偶尔处理慢一点也能扛住。

### 展开讲

**先说人话**：摄像头每 33 毫秒拍一帧，它需要一块**空的** buffer 才能往里写。程序拿走一块去编码时，这块就不能写了，必须还有别的空 buffer 顶上。

**打个比方**：食堂打饭，餐盘就是 buffer。阿姨（摄像头）每 33 毫秒盛一份，你（程序）端走一盘去吃（编码），吃完把盘子还回去（QBUF）。只有 1 个盘子的话，你吃饭的时候阿姨没有盘子可盛，这份饭只能倒掉（丢帧）。

轮转示意图见 [guide/04](../guide/04_摄像头和V4L2知识.md) 第 7 节（`img/v4l2/05_buffer_rotation.svg`）。

**2026-10-21 实测**：写了一个探针程序，DQBUF 以后故意 `usleep` 一段时间（模拟编码耗时），再 QBUF。用 `v4l2_buffer.sequence`（摄像头给每帧编的序号）数丢了多少帧，每组收 90 帧：

| buffer 个数 | 每帧处理时间 | 收到的帧率 | 丢帧 | sequence 实测 |
|:---:|:---:|:---:|:---:|---|
| **1** | 0 ms（什么都不做） | **10.0 fps** | 每 3 帧丢 2 帧 | 90, 93, 96, 99… |
| 1 | 20 ms | 10.0 fps | 每 3 帧丢 2 帧 | 90, 93, 96… |
| 2 | 20 ms | 20.1 fps | 134 帧里丢 44 帧 | 45, 46, 48, 49, 51… |
| **4** | 0 ms | **30.0 fps** | 0 | 30, 31, 32, 33… |
| **4** | 20 ms | **30.0 fps** | 0 | 30, 31, 32, 33… |

**结论**：
- 1 块时，就算程序立刻还回去也只有 10fps。**原因按现象推断（板子上没有内核源码，未核实）**：ISP 在一帧开始之前就要把"下一帧写到哪块 buffer"配置好。只有 1 块时，它正在被写或者在程序手里，配置的时刻总是赶不上，于是 3 帧里只能抓到 1 帧。
- 2 块、每帧处理 20 ms，比一帧的时间 33 ms 还短，照样丢帧。原因同上：除了正在写的那块，还得有一块**提前**排好队。
- 4 块：正在写 1 块 + 排队 1～2 块 + 程序手里 1 块，够用了。

**面试官可能追问**

| 追问 | 答 |
|---|---|
| 那给 10 块是不是更好？ | 多出来的 buffer 只能扛**短时间**的慢（比如偶尔有一帧编了 50 ms）。如果**每帧**都比 33 ms 慢，再多 buffer 也会被耗光，见第 6 题。而且每块 3 MB，多了浪费内存，延迟也会变大（排队的帧越多，最新画面离你越远） |
| 4 这个数是从哪来的？ | MPP 官方的 `mpi_enc_test` 也用 4 块：`test/mpi_enc_test.c` 第 190 行 `camera_source_init(cmd->file_input, 4, ...)`。这是经验值，不是硬性规定 |
| 驱动会不会改你要的块数？ | 会。所以 `main.cpp` 第 193 行检查了 `req.count != kBufCount`。实测要 1、2、4 块，驱动都照给了 |

## 4. 忘了 QBUF 会怎样？

### 30 秒版

DQBUF 是从驱动借一块 buffer，QBUF 是还回去。只借不还，4 块借完以后驱动手里一块都没有，第 5 次 DQBUF 就会**一直阻塞**，程序卡死，不报错也不退出。我实测过，用 `timeout 8` 才把它杀掉。另外，QBUF 必须放在 **encode 返回之后**，提前还的话，摄像头可能在编码器读的同时往里写下一帧，画面会撕裂。

### 展开讲

**先说人话**：buffer 只有 4 块，是借用关系。DQBUF 借一块，QBUF 还一块，借了不还就没得用了。

**实测**（2026-10-18，[验证M3代码](../验证代码运行结果/验证M3代码_零copy导入.md) 三、B）：
- 在副本上删掉编码循环里的 `queue_buffer(index)`，`kFrames` 改成 10
- 结果：程序卡住不动，8 秒后被 `timeout` 杀掉，退出码 124
- 日志最后一行是 `frame 0`。因为日志每 30 帧才打一行，看不出到底编了几帧。按 4 块 buffer 推算，应该是前 4 帧编完、第 5 次 DQBUF 卡住

**为什么是"卡死"而不是"报错"**：程序是用阻塞方式打开 `/dev/video22` 的（没加 `O_NONBLOCK`），DQBUF 没有写好的帧时就会一直等。驱动没有空 buffer，就永远写不出新帧，所以会永远等下去。

**`main.cpp` 里的写法**（第 300～308 行）：

```cpp
if (!encoder.encode(g_bufs[index].mppBuf, false, packet)) {
    queue_buffer(index);   // 失败也要还
    return -1;
}
// ⭐ encode() 返回时硬件已经读完这一帧，现在才能还给摄像头
if (!queue_buffer(index)) {
    return -1;
}
```

两个要点：
1. **成功、失败都要还**。失败那条路也有 `queue_buffer(index)`。
2. **顺序是 encode 之后再 QBUF**。QBUF 以后，这块 buffer 随时可能被摄像头写入下一帧。如果编码器还在读，就会读到半张旧图、半张新图（撕裂）。零拷贝时这一点尤其重要，因为编码器读的就是摄像头的原始内存，中间没有副本保护。

**面试官可能追问**

| 追问 | 答 |
|---|---|
| 怎么避免卡死后查不出原因？ | DQBUF 之前先用 `poll()` 等 fd 可读，并设置超时（比如 2 秒），超时就打印日志退出，不会无声无息地卡住。MPP 的 `camera_source.c` 没有这么做：它也是阻塞打开（第 212 行），遇到 EINTR/EAGAIN 就每 10 ms 重试（第 149～165 行），同样可能一直等下去（`poll` 的写法未实测） |
| 跳过开头的 30 帧时也要 QBUF 吗？ | 要。`main.cpp` 第 284～289 行，取出来马上还回去 |

## 5. 摄像头侧着装怎么办？

### 30 秒版

用 MPP 编码器的预处理旋转：`prep:rotation` 设成 1 或 3（逆时针 90° 或 270°），由硬件转，不占 CPU。`width`、`height`、`stride` **仍然填摄像头的 1920×1080**，它们描述的是输入。MPP 会自动把输出改成 1080×1920。摄像头芯片自带的 flip 只能做镜像或 180°，转不了 90°。我们这块板子用的是 `rotation = 3`。

### 展开讲

详细见 [画面旋转_prep_rotation和sensor翻转.md](画面旋转_prep_rotation和sensor翻转.md)，这里只列面试要点。

**实测结果**（2026-10-18 四个值都试过，2026-10-21 用 `rotation = 3` 跑 500 帧复测）：

| rotation | 意思（《MPP 开发参考》第 658 行） | 输出分辨率（ffprobe） |
|:---:|---|---|
| 0 | 不转 | 1920×1080 |
| 1 | 逆时针 90° | 1080×1920 |
| 2 | 180° | 1920×1080 |
| **3** | **逆时针 270°** | **1080×1920**，画面是正的 |

2026-10-21 复测：500 帧、8,227,043 字节、High profile、解码没有错误。

**代码**（`main.cpp` 第 254～259 行）：只加了一行 `cfg.rotation = 3;`，其他参数不变。

**两种方法怎么选**

| | 编码器 `prep:rotation` | 摄像头 flip |
|---|---|---|
| 在链路哪一站 | 最后一站（编码器） | 第一站（摄像头芯片） |
| 能转多少 | 90° / 180° / 270° | 水平镜像、垂直镜像、两个都开 = 180° |
| 影响范围 | 只有这一路编码输出 | 所有出口（主路、副路、抓帧） |
| 适合 | **侧着装**（90°） | **倒着装**（180°）、镜像 |

**面试官可能追问**

| 追问 | 答 |
|---|---|
| 为什么 flip 转不了 90°？ | flip 只是让芯片换个方向读像素（从右往左、从下往上），行还是行、列还是列。转 90° 要把行变成列，芯片做不到 |
| 预览画面（video23）会跟着转吗？ | 不会。prep:rotation 只作用在这一路编码上。要所有出口都转，就用 RGA 旋转（Day 4），代价是多一次处理 |
| 转 90° 以后有什么要注意的？ | 输出变成竖屏，播放端、推流对端要支持竖屏分辨率 |

## 6. 编码速度跟不上摄像头怎么办？

### 30 秒版

先说会发生什么：摄像头不会等你。驱动手里没有空 buffer 时，新来的帧直接**丢掉**，用 `v4l2_buffer.sequence` 能看出跳号。我实测过：每帧处理 50 ms（比一帧的 33 ms 慢），收到的帧率就掉到 **20fps**，每帧 100 ms 就掉到 **10fps**。多加 buffer 只能扛短时间的慢，扛不住持续的慢。解决办法：先测出编码到底多慢，再选降分辨率/帧率、多线程流水线，或者换更快的编码参数。

### 展开讲

**先说人话**：摄像头 30fps，意思是每 33 毫秒必须有一块空 buffer 给它写。程序处理一帧要是超过 33 毫秒，还 buffer 的速度跟不上，buffer 迟早被借光，后面的帧就没地方放了。

**2026-10-21 实测**（同第 3 题的探针，4 块 buffer，每组收 90 帧）：

| 每帧处理时间 | 收到的帧率 | 摄像头实际拍了 | 丢了 | 开头几帧的 sequence |
|:---:|:---:|:---:|:---:|---|
| 0 ms | 30.0 fps | 90 帧 | 0 | 30, 31, 32, 33, 34, 35 |
| 20 ms | 30.0 fps | 90 帧 | 0 | 30, 31, 32, 33, 34, 35 |
| **50 ms** | **20.1 fps** | 134 帧 | 44 帧 | 30, 31, 32, 33, 34, **36** |
| **100 ms** | **10.2 fps** | 263 帧 | 173 帧 | 30, 31, 32, 33, **36, 39** |

从表里能看出三件事：
1. **收到的帧率 ≈ 1000 / 每帧处理时间**。处理成了瓶颈，摄像头再快也没用。
2. **开头 4 帧没丢**：4 块 buffer 事先都排好了队，先把这一段扛过去了，之后才开始跳号。这就是"多加 buffer 只能扛短时间"。
3. **驱动不报错**。DQBUF 照常返回，只是 sequence 跳号。不主动检查的话，你根本不知道丢了帧。

**我们的程序跟得上吗？** 跟得上。2026-10-21 跑 500 帧的日志：`frame 0` 在 21:18:34.232，`frame 480` 在 21:18:50.234，480 帧用了 16.0 秒，正好 30fps。RK3588 的硬件编码器编 1080p 远快于 33 ms。精确的每帧耗时等以后做"性能对比"时再测。

**怎么发现丢帧**：DQBUF 以后比较 `buf.sequence` 和上一帧的差，不等于 1 就是丢了。`main.cpp` 现在没有做这个检查，以后加帧率统计时一起加。

**跟不上时的办法**

| 办法 | 说明 |
|---|---|
| 先测量 | 打印每帧 encode 的耗时、统计 sequence 跳号。先确认是不是真的慢、慢在哪一步 |
| 降输入 | 降低分辨率（比如改用 selfpath 出小图），或者降低摄像头帧率 |
| 流水线 / 多线程 | 一个线程专门 DQBUF/QBUF，一个线程专门编码，中间用队列连起来（Day 5 的 `mpi_enc_mt_test`）。注意：这时 buffer 要等编码线程用完才能还，buffer 个数要相应增加 |
| 主动丢帧 | 业务允许的话，比如只要 15fps，就每两帧编一帧，另一帧直接 QBUF 还回去。这比被动丢帧更可控 |
| 找真正的瓶颈 | 硬件编码一般不是瓶颈（见上面：1080p 跑满 30fps），瓶颈常在 CPU 处理，比如 CPU 拷贝帧数据、软件画 OSD、写慢速存储。所以零拷贝本身就是在防这个问题 |

**面试官可能追问**

| 追问 | 答 |
|---|---|
| 丢帧是丢最新的还是最旧的？ | 按实测现象，是没有空 buffer 的那段时间里拍的帧没地方写，被丢掉了。已经写进 buffer 等着被取的帧不会被覆盖（sequence 一直是递增的，没有回退） |
| 怎么证明是编码慢，而不是摄像头本身掉帧？ | 处理时间设成 0，收到的是 30.0fps、0 丢帧，说明摄像头本身没问题 |
